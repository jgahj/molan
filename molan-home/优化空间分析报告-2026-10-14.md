## 二、优化空间清单（按优先级）

### P0-1 前端 Cache-Busting 版本戳过期——安全修复触达不了回访用户

| 项 | 内容 |
|---|---|
| **事实** | 版本戳 `?v=20261011_dock_v2` 由 `ac9e292`（10-11 23:45）引入；`8749cd2`（10-12 16:52）修改了 `completion-editor.js`（677KB，含 AI 开关胶囊、客户端防套取 Fail-Fast、创作参数核对）**但未升版本戳**。而 `services/static-service.js:87` 对带版本戳的静态资源返回 `max-age=31536000, immutable` |
| **影响** | 10-11 23:45 ～ 10-12 部署之间访问过站点的用户，浏览器把旧 `completion-editor.js` 不可变缓存至今——**阶段二十五的客户端安全层与新交互对这批用户完全失效**，且无自然过期（immutable + 一年）。服务端防护（chat-service 探针 + 系统提示词硬围栏）仍在，属"防御降级"而非"门户大开"，但 UI 新功能（开关胶囊/参数核对）同样不到达 |
| **根因** | 前端内容变更与版本戳变更之间没有强制联动机制，靠人工记得升戳 |
| **建议方案** | ① 立即升戳（如 `20261014_sec_v3`）并重新部署；② 建立防再发：CI 校验"git diff 前端文件 ↑ 则 index.html 戳必须变"，或改为构建时按内容 hash 自动生成戳 |
| **工作量** | 升戳+部署 ~10 分钟；CI 校验 ~0.5 天 |

### P0-2 登录/注册接口无限流——暴力破解与 CPU 消耗面

| 项 | 内容 |
|---|---|
| **事实** | 全站仅 chat 有准入限流（`CHAT_RATE_LIMIT=30`，chat-admission-service）。`/api/auth/login`、`/api/admin/auth/login`、注册接口**无 IP/账号维度限流、无失败锁定**（grep 全库无 429 分支） |
| **影响** | ① 口令可在线爆破；② scrypt 每次校验 ~数十毫秒 CPU（N=16384），无速率限制时攻击者可用登录请求持续消耗 ECS CPU，变相 DoS |
| **建议方案** | 登录/注册按 IP+邮箱双维度限流（如 5 次/分钟、连续失败指数退避、超阈值 429 + Retry-After）；管理后台登录更严格（3 次/分钟）。与现有 chat-admission-service 同风格实现，加测试 |
| **工作量** | ~0.5 天 |

### P1-1 知识页实体列表：每个实体 4~6 次全本正则扫描，且搜索无防抖

| 项 | 内容 |
|---|---|
| **事实** | `completion-editor.js` `renderKnowledgeList` 单次渲染中：filter 调 1 次（L9348）、citation 排序比较器每次比 2 次（L9357，O(n log n) 次调用）、cited/unused 统计各 1 次（L9366-9367）、行渲染每行 1 次（L9375）、详情 1 次（L9411）——`citationStats` 内部对**全本每章每场景**做正则匹配。搜索框 `input` 事件（L10154）**无防抖**，每敲一个字全量重算 |
| **影响** | 100 章 × 200 实体的作品，单次渲染即数十万次正则匹配、重复解析同一批正文；搜索输入会持续卡顿。本机开发书体量小不易暴露，线上大书必然 jank |
| **建议方案** | ① 单次渲染内预计算 `Map<entityId, stats>`（一遍扫描服务全部消费者）；② 跨渲染按 state 版本号 memoize（state 未变直接复用）；③ 搜索防抖 150~200ms |
| **工作量** | ~0.5 天 + 基准测试 |

### P1-2 `RenderedPromptPackage` ≠ 真实 Provider 请求（优化.txt P0-1 遗留，仍开放）

| 项 | 内容 |
|---|---|
| **事实** | `content-engine.js` 产出两条 message 的 renderedPromptPackage；`services/model-call-service.js:51-52` 又重拼为三条（追加 `DYNAMIC_PROMPT_MARKER` 前缀与"请直接输出内容，不要解释"第三条） |
