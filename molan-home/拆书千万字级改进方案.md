# 千万字级拆书与高质量创书改进方案

**项目：** 墨阑 AI 小说创作平台

**方案版本：** 1.0

**日期：** 2026-08-22

**状态：** 技术方案，待分阶段实施

## 1. 方案结论

当前项目已经具备深度拆书的基础设施：文本清洗、分片、SQLite 持久化、批次任务、断点续跑、拆书 Skill、结果导出和编辑器章节调用表都已经存在。

但当前实现还不能把“可接收千万字”等同于“高质量处理千万字”。下一阶段的核心不是把一整本书一次性塞进更大的上下文，而是建立以下闭环：

```text
原文全量覆盖
  -> 稳定文本单元与字符偏移
  -> 带证据的事实库
  -> 人物、事件、关系、伏笔图谱
  -> 章节 / 故事弧 / 分卷 / 全书分层摘要
  -> 可迁移文风与创作约束
  -> 分卷规划 / 章节合同 / 场景合同
  -> 正文生成
  -> 连续性、伏笔、人物状态、文风审计
  -> 修订后提交全书状态
```

本方案默认“千万字级别”指单本输入约 1000 万中文字符，并且要求所有文本单元都被处理、每条重要结论都能够回溯到来源。若目标是千万 Token 输入或一次输出千万字，则需要额外扩大算力、存储、队列和成本方案，不属于本版的默认范围。

## 2. 建设目标

### 2.1 功能目标

1. 支持约 1000 万中文字符的完整导入，不因标题缺失、章节过长或分片上限而静默丢失文本。
2. 全量抽取章节事实，记录人物、事件、设定、关系、伏笔、情绪和章节状态。
3. 支持章节、故事弧、分卷和全书四级分析，不依赖一次全书级长提示词。
4. 所有重要结论保留来源单元、字符偏移、证据类型、置信度和状态。
5. 支持中断、失败重试、批次级断点续跑和版本化重算。
6. 拆书结果可以生成新的原创作品框架，不带入原书专属人物、地点、势力、物品和事件。
7. 正文生成必须维护人物当前状态、时间线、关系变化和伏笔生命周期。

### 2.2 质量目标

首版验收建议设置以下门槛，实际数值应使用黄金测试集校准：

| 指标 | 首版目标 |
| --- | --- |
| 文本单元覆盖率 | 100% |
| 已完成批次事实覆盖率 | >= 99% |
| 重要结论证据可追溯率 | >= 95% |
| 人物别名消歧 F1 | >= 0.90 |
| 关键事件章节定位准确率 | >= 0.90 |
| 关键时间线硬冲突 | 0 |
| 伏笔“误判已回收”比例 | 持续下降，严禁默认全部通过 |
| 生成章节合同通过率 | >= 90% |
| 生成正文严重连续性错误 | 0 |

### 2.3 非目标

1. 第一阶段不引入独立图数据库、向量数据库、Redis 集群或微服务拆分。
2. 第一阶段不训练专用大模型，不把模型微调当作主要解决方案。
3. 不把原书全文重新拼接进新作品，不复制原书专属表达和剧情顺序。
4. 不用随机抽样冒充全量拆书。

## 3. 当前技术栈与现状

### 3.1 当前技术栈

| 层级 | 当前实现 | 方案建议 |
| --- | --- | --- |
| 运行时 | Node.js >= 22.5 | 保持不变 |
| HTTP 服务 | Node 原生 `http` / `https` | 保持不变，按模块拆分拆书服务 |
| 持久化 | Node 内置 `node:sqlite` | 保持 SQLite，启用 WAL、索引和 FTS5 |
| 模型调用 | DeepSeek Chat Completions / OpenAI 兼容模型 | 保持兼容层，增加阶段模型路由 |
| 前端 | 原生 JavaScript、现有页面组件 | 保持不变，增加覆盖率、证据和失败批次展示 |
| JSON 处理 | 当前安全解析与自动修复 | 增加阶段级结构校验和 schema 版本 |
| 测试 | Node 内置 `node:test` | 增加固定夹具、黄金样本和回归测试 |
| 任务执行 | Node 进程内任务 + SQLite 断点 | 增加数据库租约、心跳、重试和有限并发 |
| 观测 | 任务元数据、积分和错误字段 | 增加批次、覆盖、模型、版本和耗时指标 |

### 3.2 当前实现位置

- 拆书分片、清洗和深度模式：`server.js` 的拆书分析区域。
- 章节、事实、批次表：`server.js` 的 SQLite 初始化区域。
- 深度事实抽取和全局聚合：`server.js` 的流水线区域。
- 拆书结果校验和任务展示：`completion-import.js`。
- 从拆书创书：`pages/editor.js` 的 `openCreateFromDissection`。
- 编辑器动态上下文、章节调用表、知识图谱和伏笔状态：`pages/editor.js`。
- 文风证据、canon 边界和可迁移规则：`skills/extract-transform-fiction-style/`。

### 3.3 当前主要缺陷

1. 深度流水线只对 `chapter-*` 建立章节库，无标题文本生成的 `segment-*` 不能稳定进入同一条链路。
2. 批次事实只检查模型是否返回了数组，没有校验是否覆盖批次内全部章节。
3. 聚合失败或空结果可能仍被标记为 `aggregated` 和 `completed`。
4. `validation.conclusion` 被硬编码为 `passed`。
5. 人物、伏笔、开篇和文风在进入全局模型前被截断，无法覆盖全书。
6. 伏笔降级合并依赖描述前缀，容易误合并或漏合并。
7. 深度流水线的自定义提示词没有完整复用文风 Skill 的证据账本和未知项规则。
8. 创书入口主要依赖一次 JSON 调用，缺少分卷、人物、伏笔和连续性审查。
9. 编辑器上下文偏重当前章节附近内容，缺少截至当前章的长期状态快照。

## 4. 目标架构

### 4.1 分层架构

#### A. 导入层

负责读取 TXT、MD、DOCX、EPUB 等文本，统一编码和换行，清洗确定性噪音，并建立原文偏移映射。

必须保存：

- 原文哈希和清洗后哈希；
- 文件名、文件顺序、文件偏移；
- 清洗前后字符映射；
- 文本单元类型；
- 单元起止字符位置；
- 单元字数、Token 估算和清洗版本。

#### B. 文本单元层

不要把所有输入都强制称为“章节”。统一为 `unit`，类型包括：

- `preface`：正文前置内容；
- `volume`：卷或部标题；
- `chapter`：明确识别的章节；
- `scene`：章节内部的场景边界；
- `segment`：没有标题时按段落和字符上限生成的稳定单元。

每个单元必须拥有不随重试变化的 `unitId`。模型返回时使用 `unitId`，不使用模糊的章节名称作为唯一标识。

#### C. 事实层

对每个单元全量提取客观事实。事实层只回答“文本中发生了什么”，不直接写全书评价和人物完整弧线。

建议事实类型：

- `event`：发生的事件；
- `entity_mention`：人物、地点、势力、物品、术语提及；
- `state_change`：人物能力、关系、位置、持有物和身份变化；
- `world_fact`：新增或改变的世界观信息；
- `foreshadow_action`：伏笔埋设、强化、误导、回收或后果；
- `emotion_beat`：情绪变化、爽点、虐点、钩子和高潮；
- `narrative_signal`：视角、叙事时间、信息隐藏和反转信号。

#### D. 图谱和状态层

将事实转换为稳定实体和关系：

- 人物别名和实体消歧；
- 人物关系及其发生章节；
- 事件之间的因果、阻碍、揭示、回收关系；
- 人物在每个故事阶段的状态快照；
- 伏笔的生命周期和证据；
- 叙事位置与故事世界时间的双重时间线。

#### E. 分层摘要层

按照以下层级生成摘要，每一层只读取下一级的结构化结果和证据：

```text
文本单元事实
  -> 章节摘要
  -> 故事弧摘要
  -> 分卷摘要
  -> 全书地图与全书摘要
```

每份摘要必须记录子节点 ID、生成版本、模型、输入覆盖率和未解决问题。

#### F. 创作层

把“原书观察”和“可迁移规律”分开，经过用户选择或证据筛选后，生成新的创作简报。创作简报再进入分卷、章节合同和场景合同，不直接把拆书 JSON 拼进正文提示词。

## 5. 数据模型设计

当前表可以兼容升级，但建议增加版本和证据层。第一阶段继续使用 SQLite，不迁移数据库类型。

### 5.1 `dissection_runs`

记录一次拆书运行，而不是只记录一条最终任务。

```text
id
dissection_id
pipeline_version
skill_version
prompt_version
model_policy_version
source_hash
status
unit_total
unit_completed
fact_coverage
created_at
updated_at
```

同一本原文可以使用不同模型、提示词和规则版本重新运行，旧结果保留，便于对比。

### 5.2 `dissection_units`

替代目前只按章节组织的输入层。

```text
id                  稳定 unitId
dissection_id
parent_id           卷或章节父节点
unit_type           volume / chapter / scene / segment
ordinal             原文顺序
title
source_file
source_start
source_end
clean_start
clean_end
text_hash
char_count
token_estimate
```

### 5.3 `dissection_claims`

事实和分析的统一证据入口。

```text
id
dissection_id
unit_id
claim_type
subject_id
predicate
object_value
evidence_type       direct / inferred / model_summary
source_start
source_end
confidence
status              confirmed / candidate / unknown / conflicted
run_id
```

### 5.4 实体和事件表

建议增加以下实体：

- `dissection_entities`：规范实体；
- `dissection_entity_aliases`：别名、称谓和候选名称；
- `dissection_entity_mentions`：每次文本提及；
- `dissection_events`：事件节点；
- `dissection_event_edges`：因果、转折、揭示、阻碍、回收关系；
- `dissection_entity_states`：人物或设定在章节范围内的状态。

实体必须使用稳定 ID，不能以名称作为唯一主键。模型不确定时保留候选实体，不立即合并。

### 5.5 伏笔表

```text

first_unit_id

evidence_ids

```

“已回收”必须有回收事件和回收证据，不能只因为两个描述相似就判定回收。

### 5.6 摘要表

```text
id
dissection_id
summary_type        unit / chapter / arc / volume / book / style
owner_id
child_ids_json
content_json
evidence_ids_json
coverage_json
status
version
created_at
```

最终 `result_json` 只作为前端报告的物化视图，不作为唯一事实来源。大数组应通过分页 API 查询，避免一次性加载全部结果。

## 6. 拆书流程如何实现

### 6.1 导入和切分

1. 读取原文并计算原始哈希。
2. 进行确定性清洗，同时生成清洗前后偏移映射。
3. 识别卷、章和场景标题。
4. 无标题时按段落边界和字符上限生成 `segment`，不能静默丢弃。
5. 按 4,000 到 12,000 字生成基础单元，尽量不切断自然段和对白。
6. 将相邻单元组成批次，批次按 Token 预算自适应，不仅按字符数判断。
7. 生成输入清单，记录总单元数、总字符数和预计批次数。

禁止使用 `array.slice(0, N)` 作为静默截断。达到系统上限时，任务必须明确失败，并显示“输入超出当前容量”。

### 6.2 局部事实抽取

建议默认策略：

- 快速模型负责逐单元事实抽取；
- 每批 6 到 12 个单元，或输入不超过模型上下文预算的 40% 到 55%；
- 输出预算按批次单元数量动态分配；
- 每个输出必须返回 `unitId`，并且只能返回输入批次中的 ID；
- 对缺失、重复、越界和 JSON 不合法进行局部重试；
- 五次重试仍失败时保留失败批次，不得直接完成全书。

建议的事实输出结构：

```json
{
  "units": [
    {
      "unitId": "chapter-0001",
      "events": [],
      "entityMentions": [],
      "stateChanges": [],
      "worldFacts": [],
      "foreshadowActions": [],
      "emotionBeats": [],
      "uncertain": []
    }
  ]
}
```

模型输出后执行本地校验：

1. 单元覆盖集合必须等于输入集合，允许明确标记 `no_observable_fact`，不允许漏掉。
2. 枚举值必须合法。
3. 事件、角色和设定描述不能超过设定长度。
4. 引用偏移必须在对应单元范围内。
5. 事实不能包含没有证据的全书评价。

### 6.3 实体消歧

采用三级策略：

1. 本地规范化：去除称谓、空格、全半角差异，识别明显别名。
2. 规则和上下文匹配：比较角色类型、关系、首次出现位置、共同出场人物和行为上下文。
3. 模型复核：只把低置信度候选交给强模型，不让强模型重复处理所有原文。

消歧结果必须包含 `confirmed`、`candidate` 或 `conflicted` 状态。不能因为名称相同就直接合并，也不能使用描述前十个字符作为唯一合并键。

### 6.4 事件和时间线

每个事件保存：

- 叙事位置：第几卷、第几章、第几个单元；
- 故事世界时间：明确时间或相对时间；
- 参与人物；
- 事件前状态；
- 事件后状态；
- 结果和代价；
- 证据来源；
- 与其他事件的关系。

倒叙、插叙和回忆必须同时保存“文本出现位置”和“事件发生时间”，不能只按文本顺序生成时间线。

### 6.5 伏笔分析

伏笔分析分三步完成：

1. 局部层识别埋设、强化、误导和疑似回收动作。
2. 实体和事件层把线索连接到人物、物品、地点或事件。
3. 全书层判断状态，并列出支持“已回收”或“疑似烂尾”的证据。

输出必须允许 `unknown` 和 `conflicted`。高质量拆书不能为了填满报告而把所有伏笔都归类为已回收。

### 6.6 分层聚合

章节摘要只读取本章事实和本章证据；故事弧摘要读取连续章节摘要；分卷摘要读取故事弧摘要；全书摘要读取分卷摘要、全书图谱和冲突清单。

每一层都要保留：

- 子节点覆盖率；
- 主要结论；
- 证据 ID；
- 冲突和未知项；
- 生成模型与版本；
- 是否需要人工复核。

这样可以避免当前人物摘要、伏笔摘要、开篇摘要和文风样本被单次 `slice` 截断后失去全书信息。

## 7. 文风提取与原书边界

现有 `extract-transform-fiction-style` Skill 的规则应成为深度拆书的唯一文风标准。

### 7.1 文风统计

以下指标可以全量或低成本计算，不应全部交给模型：

- 平均句长和句长分布；
- 对白比例；
- 动作、描写、心理和解释比例；
- 段落长度；
- 章节开头和结尾的事件类型；
- 视角变化；
- 反转前的信息释放节奏；
- 高潮、缓冲和章末钩子间隔。

### 7.2 分层文风样本

文风样本不能只抽开头、中段和结尾。应按以下维度分层：

- 每个分卷至少抽取若干章；
- 高冲突、低冲突、对白密集、动作密集、心理密集场景；
- 不同主要人物视角；
- 章节开头、转折段和结尾；
- 高置信度重复出现的写法。

最终只把经过证据筛选的规律放入 `styleProfile` 和 `craftConstraints`。原书人物、地点、事件、术语和剧情顺序必须保留在 `canonConstraints` 或 `dissectionMap`，不能写入通用风格包。

## 8. 从拆书到创书的实现方案

当前一次性创书调用应改为多阶段任务。

### 8.1 创作简报

先生成只包含可迁移内容的简报：

- 目标题材；
- 目标读者；
- 节奏模型；
- 开篇推进方式；
- 冲突升级方式；
- 成长和奖励机制；
- 可迁移文风；
- 禁止复制的原书内容；
- 用户指定的微创新方向。

### 8.2 分卷和人物规划

强模型生成：

- 全书分卷地图；
- 每卷目标、转折、高潮和终点；
- 主线和支线进入、推进、退出位置；
- 主要人物目标、缺陷、关系变化和代价；
- 每卷的伏笔埋设与预定回收计划。

规划结果先经过结构审计，再生成章节，不直接创建正文。

### 8.3 章节合同

每章生成结构化合同：

```json
{
  "chapterNo": 1,
  "goal": "本章目标",
  "protagonistAction": "主角主动行为",
  "opposition": "主要阻力",
  "informationChange": "读者或人物获得的新信息",
  "escalation": "冲突如何升级",
  "irreversibleResult": "不可逆结果",
  "characterStateChanges": [],
  "foreshadowActions": [],
  "continuityInputs": [],
  "continuityOutputs": [],
  "mustAvoid": []
}
```

### 8.4 场景和正文

一章拆成多个场景，每个场景只完成一个主要功能。正文生成只读取：

```text
固定创作约束
+ 当前分卷摘要
+ 当前故事弧摘要
+ 当前人物和关系状态
+ 当前时间线
+ 未回收伏笔
+ 最近两章结尾
+ 本章合同
+ 当前场景合同
+ 可迁移文风规则
```

不要把整本原文或整本拆书结果放进每次正文请求。长文本生成研究表明，分解任务、逐段生成和连续状态维护比单次超长输出更稳定。

### 8.5 审计和状态提交

正文生成后依次执行：

1. JSON 或正文格式检查；
2. 章节合同检查；
3. 人物状态和关系检查；
4. 时间线和空间位置检查；
5. 伏笔埋设、推进和回收检查；
6. 文风和禁用模式检查；
7. 与上一章承接检查；
8. 失败时生成问题清单并定向重写一次；
9. 审计通过后，才同步 `knowledge`、`foreshadows`、章节调用表和当前状态快照。

现有 `chapterCalls`、`stateSync`、知识图谱和伏笔表可以作为这套流程的基础，不需要另建一套编辑器状态系统。

## 9. 模型路由与成本控制

### 9.1 阶段模型分工

| 阶段 | 推荐模型 | 原因 |
| --- | --- | --- |
| 文本清洗、切分、统计 | 本地规则 | 零成本、可重复 |
| 单元事实抽取 | 快速模型 | 调用量大，任务结构简单 |
| 实体消歧 | 快速模型 + 强模型复核 | 只把低置信度候选升级 |
| 事件关系和伏笔合并 | 强模型 | 需要跨章节判断 |
| 分卷、全书结构 | 强模型 | 需要全局抽象 |
| 章节合同 | 强模型或高质量模型 | 直接影响后续正文 |
| 正文初稿 | 根据成本选择中速模型 | 按场景生成 |
| 严重冲突审计 | 强模型 | 审计错误代价高 |

### 9.2 缓存和估算

固定的 Skill、schema 和稳定的作品事实摘要放在提示词前部，动态问题放在后部，继续利用模型的前缀缓存。

积分估算必须按实际 Token 用量校准，不能只使用字符数比例。前端应同时显示：

- 预计批次数；
- 已完成批次；
- 实际 Token；
- 实际积分；
- 缓存命中量；
- 失败重试成本。

### 9.3 任务执行

第一阶段保留单 Node 服务，但将进程内 `activeDissections` 扩展为数据库租约：

- `queued`、`running`、`retrying`、`needs_review`、`completed`、`failed`、`cancelled`；
- 每个任务有 `lease_until` 和心跳；
- 进程重启后，过期租约自动恢复；
- 同一批次使用幂等 ID，重复执行不重复写入事实；
- 并发数按模型和账号限制，不让多个千万字任务把服务打满。

只有当未来出现多实例部署、跨机器并发和任务量明显超过 SQLite 能力时，才考虑 Redis + BullMQ 或独立任务服务。

## 10. API 和前端改造

### 10.1 API 建议

保留现有拆书接口，增加以下能力：

```text
POST /api/dissections
GET  /api/dissections/:id
GET  /api/dissections/:id/coverage
GET  /api/dissections/:id/units?cursor=...
GET  /api/dissections/:id/entities?cursor=...
GET  /api/dissections/:id/foreshadows?status=...
GET  /api/dissections/:id/summaries?type=volume
GET  /api/dissections/:id/validation
POST /api/dissections/:id/retry
POST /api/dissections/:id/rebuild?stage=entity_resolution
```

结果接口应返回真实状态，而不是只返回一个 `aggregated: true`：

```json
{
  "status": "needs_review",
  "pipeline": {
    "unitTotal": 2400,
    "unitCompleted": 2392,
    "factCoverage": 0.996,
    "failedBatches": [17],
    "aggregationStatus": "completed",
    "validationStatus": "needs_review"
  }
}
```

### 10.2 前端展示

拆书页面应显示：

- 原文字数和文本单元数；
- 已处理单元 / 总单元；
- 已完成批次 / 总批次；
- 事实覆盖率；
- 失败批次及错误原因；
- 未消歧实体数；
- 时间线冲突数；
- 未解决伏笔数；
- 预计与实际成本；
- 当前运行版本。

只有通过完整性门禁的任务才能开放导出、带入编辑器和“从拆书创书”。部分完成结果可以查看，但必须明确标记为部分结果。

## 11. 完整性门禁

拆书任务只有同时满足以下条件才能标记为 `completed`：

1. 输入清单已生成，未发生静默截断。
2. 所有文本单元都有成功事实结果，或明确记录为无需事实。
3. 所有失败批次已完成重试或由用户确认跳过。
4. 人物、事件、伏笔和摘要的输入覆盖率达到阈值。
5. 聚合阶段返回结构合法且字段满足 schema。
6. 关键结果都有证据引用。
7. 校验阶段完成，并给出 `passed`、`needs_review` 或 `failed`。
8. 缺失项、冲突项和未知项已写入报告。

如果聚合成功但存在证据不足，任务应为 `needs_review`，不能伪装为完整成功。

## 12. 测试方案

### 12.1 单元和回归测试

必须覆盖：

1. 无章节标题的长文本不会丢失，也不会被错误计为零章节。
2. 章节跨分片时，字符偏移和单元顺序正确。
3. 模型漏返回一个单元时，批次不会完成。
4. 模型返回重复或越界单元时，批次进入重试。
5. 聚合返回空值时，任务不会标记为完成。
6. 失败后重试不会重复写入事实或重复扣费。
7. 改变 Skill 或 pipeline 版本后，旧缓存不会被错误复用。
8. 伏笔没有回收证据时不能被标记为 `recovered`。
9. 不同别名在有冲突证据时保持 `candidate` 或 `conflicted`。
10. 不完整拆书结果不能进入创书流程。

### 12.2 黄金测试集

建立至少三种题材的人工标注集，每种题材包含：

- 100 到 300 章的连续文本；
- 人物和别名标注；
- 关键事件和时间线；
- 伏笔埋设与回收；
- 分卷和故事弧边界；
- 若干已接受的文风改写样本。

评测任务分为：单文档定位、多跳人物追踪、伏笔回收判断、时间线排序、全书结构聚合、章节续写和连续性修订。

不能只测试“模型能否在长文本中找到一个字符串”。应参考 LongBench 和 RULER 的思想，增加多跳、聚合、跨层摘要和长文本生成测试。

## 13. 分阶段落地计划

### 阶段 0：正确性修复

- 统一 `unitId` 和章节 / 段落单元模型；
- 修复无标题文本的深度流水线；
- 加入批次覆盖检查；
- 移除 `aggregated` 直接代表完整结果的逻辑；
- 移除硬编码 `validation.passed`；
- 增加失败、部分完成和需要复核状态；
- 增加上述回归测试。

### 阶段 1：事实库和证据层

- 增加 `dissection_runs` 和 `dissection_units`；
- 将现有章节事实升级为带证据的 claims；
- 保存字符偏移、版本、置信度和状态；
- 加入实体提及和别名表；
- 增加批次覆盖率和证据覆盖率接口。

### 阶段 2：分层聚合和图谱

- 实现章节摘要；
- 实现故事弧和分卷摘要；
- 实现实体、事件、关系和伏笔生命周期；
- 将当前人物、伏笔和世界观的截断聚合改为分层聚合；
- 使用强模型处理低置信度冲突，而不是处理全部原文。

### 阶段 3：高质量创书

- 生成 portable creative brief；
- 生成分卷、人物、主线和伏笔计划；
- 生成章节合同和场景合同；
- 把章节状态快照接入编辑器动态上下文；
- 生成后执行多项审计并同步状态。

### 阶段 4：性能和运营

- 增加数据库租约和心跳；
- 增加有限并发和模型级限流；
- 增加 Token、积分、缓存和耗时统计；
- 增加大数组分页和结果按需加载；
- 在黄金测试集上持续比较模型和提示词版本。

## 14. 完成标准

本方案完成不以“页面显示深度拆书”作为标准，而以以下结果为准：

1. 1000 万中文字符输入能生成完整单元清单，不静默截断。
2. 任务中断后可以从失败批次继续，不重复已完成批次。
3. 任何报告结论都能定位到来源单元和证据区间。
4. 事实缺失、聚合失败和验证冲突不会被标记为完整成功。
5. 人物、事件、伏笔和时间线可以按章节范围查询。
6. 创书过程经过简报、分卷、章节合同、正文、审计和修订多个阶段。
7. 编辑器生成下一章时能读取当前故事弧、人物状态、时间线和未回收伏笔。
8. 黄金测试集达到预设指标，并且严重连续性错误为零。
