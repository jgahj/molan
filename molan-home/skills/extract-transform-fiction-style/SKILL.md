# 小说文风提取与转化

建立基于证据的小说文风档案，不把文字风格和故事设定混在一起。最优先学习用户的明确纠错和亲手精修文本；证据不足的特征先标为暂定，通过聚焦提问或短篇 A/B 改写校准；用户要求导出时，生成模型中立的可复用包。

## 选择模式

除非用户明确指定，否则从请求中判断模式：

- `identify`：根据现有证据概括最明显的文风特征。
- `analyze`：输出有证据支撑的详细文风分析，但不固化规则。
- `define`：创建或更新结构化文风档案。
- `calibrate`：通过互动解决不确定或互相冲突的文风特征。
- `apply`：用已有档案改写、续写或评估小说文本。
- `dissect`：按明确目的拆解整本书或连续章节的框架、节奏、人物和感情线，并筛选其中可迁移的写作规律。
- `export`：生成可移植文风包或可复用写作 Skill。

不要要求用户重复对话或文件里已有的信息。用户直接要求改写时，若证据足够，直接使用 `apply`，不要强行先访谈。

## 拆书分析工作流

用户要求拆书、分析爆款结构、寻找某个写作问题的解决方案，或提供了整本书的章节材料时，使用 `dissect`。拆书的对象是可观察的写法和结构，不是复述故事，也不是照搬某位作者的独特表达。

### 1. 先明确拆书目的

根据目标选择样本数量、阅读深度和输出重点：

- **新作者入门**：优先选择同类型、完成度高且经过较长连载或完结验证的三本左右作品，重点观察书名与简介、基础设定、人物塑造、剧情逻辑、主线与支线结构，以及开篇如何让读者继续阅读。
- **老作者进阶**：优先选择新书榜或畅销榜上的同类型作品，快速定位高阅读量段落、节奏控制、爆点频率和钩子铺垫；分析要服务于改进，不追求把套路原样搬回自己的书。
- **解决具体问题**：围绕“开篇拖沓”“支线失控”“人物关系不推动剧情”等已知问题选书，不受榜单限制，只记录能回答该问题的证据，并尝试至少一种不同处理方式。

样本选择要记录作品类型、完结或连载状态、阅读范围和选择理由。读者评论可用于判断哪些段落产生了共鸣或疑问，但评论是反馈证据，不直接等同于作者意图或客观结论。

### 2. 建立全局框架

先做全书地图，再进入逐章分析：

1. 记录书名、简介、字数或章节范围、开局设定、目标读者、作品卖点和读者评价中重复出现的优点与问题。标出值得学习的书名/简介写法和设定亮点。
2. 梳理主线、支线和阶段目标。记录每条线进入与离开的章节或字数位置、出现频率、持续篇幅、关键人物、冲突和结束时主角的实际收获。
3. 在每条支线结束处记录它对主线的影响：推进、延迟、提供人物关系、补充世界、制造代价，或暂时不影响主线。允许支线只是一个独立的小世界，不强行把所有内容解释成主线服务。
4. 区分“作者反复使用的结构手法”和“这本书独有的事件、设定、角色关系”。前者进入候选 `craft_constraints`，后者留在 `dissection_map` 或 `canon_constraints`。

### 3. 划分节奏与爆点

按三个区段记录，所有判断都尽量落到章节、字数、场景和结果：

1. **开篇至第一个危机或强驱动事件**：记录用了多少字、主角的人设如何立住、危机以何种形式出现、背景交代是否足够、主角的阶段目标和短期目标是否清楚，以及读者情绪在哪个具体段落被调动。这里的“危机”也可以是必须尽快处理的机会、任务或诱因，不限定为坏事。
2. **开篇之后至第一个大爆点**：统计小爆点的频率和篇幅，记录每个小爆点引出的新人物与新危机、对后续的影响、和支线的结合方式，以及主角在这段中的成长、收获和付出。收获可以是信息、关系、主动权、能力变化或情绪回报，不限于物质奖励。可参考章节评论验证读者是否感到推进、回报或等待过久，但不要用评论替代文本证据。
3. **大爆点之后的下一阶段**：记录主角的新目标、新加入的人物、转折的触发方式和信息增量，检查作品如何保持新鲜感与继续阅读动力。关注主角核心定位是否稳定，变化是否由事件和选择造成，而不是只靠标签宣告。

每个节奏记录至少包含：位置、事件、主角目标、阻力、信息变化、情绪或期待变化、结果、代价、与主线/支线的关系。不要只写“这里很爽”“这里很拖”，要写出可复核的原因。

### 4. 做元素专项拆解

- **人物**：分析主角的性格、身份、能力边界和价值取向如何影响决策；再分析这些因素给主角带来的具体麻烦、机会和代价。单独列出配角对主线、支线和主角成长的作用。配角若主要承担功能，就记录其功能和出场收益，不为配角堆砌与主线无关的篇幅。
- **感情线**：标记主角与朋友、亲属、伴侣或对手之间改变关系状态的互动节点，记录互动前后的信任、距离、承诺、冲突或行动变化，以及关系变化如何推动剧情。当主角的性格或身份使其难以采取某个行动时，检查朋友或伴侣是否提供了劝阻、推动、资源、情感压力或新的选择。

### 5. 输出拆书记录并转换为文风证据

`dissect` 的输出按以下顺序组织：

1. 拆书目的与样本范围；
2. 作品定位和全局框架表；
3. 主线/支线时间轴与收获、代价、影响；
4. 开篇、首个大爆点和下一阶段的节奏记录；
5. 人物作用表和感情线节点表；
6. 可迁移的 `craft_constraints` 候选，逐条附章节或场景证据、适用范围、例外和置信度；
7. 仅属于该书的 `canon_constraints` 与仍未知的问题；
8. 可执行的下一步实验，例如一个开篇、节奏或人物关系的 A/B 微改写。

拆书观察先放入 `dissection_map`，不要直接升级为硬性文风规则。只有当同一规律在多个独立位置重复出现、被用户明确认可，或通过改写测试后稳定有效，才进入证据账本并提升为 `craft_constraints` 或 `style_profile`。单本书的剧情顺序、角色姓名、世界设定、专属名词和偶然爆点不得导出为通用风格。

## 保护文风与设定边界

抽取规则前，先给每条输入事实分类：

- 对整本书的主线/支线位置、爆点分布、人物作用和关系节点的观察，放入 `dissection_map`；它记录作品结构，但本身不等于通用文风。
- 可迁移的用词、节奏、视角、信息过滤、对白、情绪表达、冲突逻辑、改稿习惯，放入 `style_profile`。
- 人名、关系、势力、地点、物品、修炼体系、剧情事件、时间线和项目专属术语，放入 `canon_constraints`。
- 用户接受过或由改稿证据支持的通用写作技巧，放入 `craft_constraints`。
- 当前任务的临时要求，如目标字数、场景结果，放入 `task_constraints`。

不要把项目 canon 导出成通用文风规则。示例中用中性角色标签代替专名，如 `[主角]`、`[亲属]`、`[对手]`、`[势力]`、`[关键物品]`。只有在同一项目内应用文风时，才保留该项目 canon。

## 建立证据账本

把证据记录成小而可审计的条目。每条记录包含：

- 来源类型：`explicit_correction`、`user_final_edit`、`accepted_rewrite`、`repeated_sample`、`single_sample` 或 `general_advice`；
- 原片段或观察到的模式；
- 用户修订或偏好行为；
- 推导出的规则；
- 理由；
- 影响的特征轴；
- 适用范围和例外；
- 置信度和证据数量；
- 状态：`candidate`、`confirmed`、`hard_rule`、`conflicted` 或 `retired`。

规则冲突时按以下优先级处理：

1. 最新的用户明确纠错。
2. 用户亲手精修后的最终文本。
3. 多次被接受的改写模式。
4. 多个独立样本中重复出现的特征。
5. 单一样本或通用写作建议。

不要把偶然措辞升级成硬规则。只有用户明确要求、反复纠正，或在多次改稿中稳定保留时，才提升规则状态。维护长期档案时，把被新偏好替代的规则保留为 retired 历史。

处理纠错库、前后改稿或疑似 AI 写作问题时，先读 [correction-patterns.md](references/correction-patterns.md)。

## 提取文风档案

做详细分析、创建档案、校准、导出或更新档案前，先读 [feature-schema.md](references/feature-schema.md)。

每个文风判断都要做到：

1. 至少引用或概述一条支持证据。
2. 区分“样文确实如此”和“用户偏好如此”。
3. 说明适用范围与不适用范围。
4. 给出正向写法，而不只列禁忌。
5. 区别细微时，给出简短正例和反例。
6. 赋予 `0.00` 到 `1.00` 的置信度。

提取维度包括视角、信息过滤、句段节奏、用词、对白、内心质地、设定进入时机、描写、情绪、冲突、反转、动作机制、伏笔、收尾和禁用模式。不要因为字段填满就声称档案完整；证据不足的字段标为 `unknown`。

## 提问式校准

用户要求多轮文风发现、重要特征冲突，或高影响特征置信度低于阈值时，读取 [interaction-workflow.md](references/interaction-workflow.md)。

执行规则：

- 每轮最多问三个高影响问题。
- 用文本中的具体证据说明歧义。
- 优先给出能暴露真实取舍的选项，并允许自由回答。
- 一次只问一个特征轴；除非两个特征无法拆开。
- 当“简洁”“有张力”等标签过于模糊时，用 100 至 250 个中文字符的 A/B 微改写测试。
- 每次回答后，简短说明更新后的规则，并在下一次测试中应用。
- 当剩余不确定性不再显著影响输出、达到用户指定深度，或用户要求继续写作时停止。

不要暴露隐藏推理链。只报告证据、简短理由、结论和未解决选项。

## 学习用户改稿

用户修改生成文本后，按功能比较原稿和修订稿，而不是只看字数变化：

1. 识别删除、增加、替换、重排和保留的部分。
2. 判断逻辑、紧迫感、人物塑造、节奏、证据处理或设定注入发生了什么变化。
3. 推导能解释该修改的最小可复用规则。
4. 判断该修改属于文风、canon 修正、事实修正还是局部场景修补。
5. 更新账本中的置信度和状态。
6. 用早前已接受文本反查，避免过度泛化。

用户解释“为什么这样改”时，其证据强度高于单纯改稿结果。

## 应用档案

写作前先确定参数。用户提供值则使用用户值，否则使用默认值：

```yaml
mode: apply
interaction_depth: standard
style_strength: 75
preserve_plot: true
preserve_pov: true
preserve_terms: true
preserve_length: flexible
dialogue_density: inherit
exposition_density: inherit
thought_explicitness: inherit
rhythm_variation: inherit
description_density: inherit
de_ai_strength: 80
evidence_threshold: 0.70
uncertainty_policy: conservative
output_bundle: markdown
```

`style_strength` 表示可迁移文风特征的执行强度，不代表可以改事实。`0` 只做正确性编辑；`100` 强力执行所有已确认文风规则，同时仍服从剧情、视角、术语、安全与用户约束。

规则执行顺序：

1. 当前任务的最新明确指令。
2. canon 与事实保留约束。
3. 硬性文风规则。
4. 已确认文风偏好。
5. 高于证据阈值的软偏好或暂定偏好。
6. 通用模型默认值。

规则仍不确定时，按 `uncertainty_policy` 处理：

- `ask`：遇到会影响结果的歧义时暂停并提问。
- `preserve`：保留原文行为。
- `conservative`：只做已确认规则支持的最小修改。

返回正文前，检查因果、证据边界、视角越界、人物专属口吻、身体机制、冗余解释、模板化反差，以及每段是否有实际功能。

## 输出结果

按模式匹配输出：

- `identify`：给出紧凑特征概述、证据、置信度和未知项。
- `analyze`：按特征轴列出发现、冲突、常见问题和建议实验。
- `define`：输出档案、硬规则、软偏好、禁用模式、示例和待解问题。
- `calibrate`：输出当前档案变化，以及下一轮一到三个问题或 A/B 测试。
- `apply`：优先返回转化后的文本；只有用户要求或确有帮助时附简短说明。
- `dissect`：按拆书目的输出全局框架、节奏区段、人物作用、感情线节点、证据和可迁移规律候选；不把拆书说明混入小说正文。
- `export`：按 [portability-spec.md](references/portability-spec.md) 执行，并使用 `assets/` 中模板。

分析和正文必须清楚分开。不要把说明写进小说正文。

## 导出可复用包

跨平台导出前，读取 [portability-spec.md](references/portability-spec.md)。使用：

- [style-profile.schema.json](assets/style-profile.schema.json) 做结构验证；
- [portable-style-skill-template.md](assets/portable-style-skill-template.md) 生成模型中立说明文档。

导出 UTF-8 Markdown 和 JSON。JSON key 保持 ASCII，值可以使用多语言。标准档案不得依赖 Codex 指令、专有工具、隐藏提示词或特定厂商角色语法。平台适配器只能作为中立档案外层的薄包装。

`dissection_map` 默认是拆书阶段的工作记录，不写入可移植的 `STYLE_PROFILE.json`；只有其中已经经过证据筛选的可迁移规律，才分别进入 `craft_constraints` 或 `style_profile`。用户明确要求保留拆书地图时，将其作为独立附录导出，并标明作品范围和不可迁移的 canon。

## 质量维护

- 保留证据可追溯性，但不要复现长篇受版权保护文本。
- 分析和导出中优先使用短摘录或概述。
- 区分“样文这样写”和“用户想要这样写”。
- 禁忌必须配套可执行的替代写法。
- 素材足够时，用至少一个代表场景和一个压力场景测试固化档案。
- 对重要档案变化做版本记录，并在 profile metadata 中写简短变更说明。
- 不要静默抹掉矛盾；通过优先级、适用范围或校准解决。
