## 1. 先锁定边界，不让Luna自行扩大任务

### 1.1 最终目标

一套多用户、多工作区、多私有作品的小说创作系统，能完整维护六类49项资料，驱动章/场景生成，保存正文与事实，处理修改冲突、撤权、故障、导入导出和恢复。

### 1.2 允许后续改变

- 数据库结构、迁移机制、存储访问层。
- 身份与权限映射、项目/资料API、旧接口适配。
- 资料中心、编辑器引用、生成/审计/提交、后台任务。
- 必要的新依赖、测试和本地基础设施，但实施前列明版本、用途及隔离方法。

### 1.3 默认仍然禁止

- 未经当前执行任务授权，直接修改真实用户数据库、删除旧数据、部署云端或提交代码。
- 扫描或迁移无关小说原文、凭据、其他工作区数据。
- 为让测试通过而删掉原需求、放宽跨用户权限或把失败改为已通过。
- 因请求未知而自动更换ID重发付费推理。
- 把本报告的建议路径当作已经存在的代码；把历史124项或668项结果当作新版本验收。

后续实施时，空库和脱敏克隆库迁移属于正常验证。真实切换必须满足T14前置条件，并在执行任务中明确目标数据库及回退安排。

## 2. 技术决策清单

| 决策 | 本方案默认选择 | 不应误解为 |
| --- | --- | --- |
| 应用形态 | Node模块化单体，API与worker可分进程，共享领域模块 | 现在就拆几十个微服务 |
| 正式多用户数据库 | PostgreSQL 18主版本；实施时核验并锁定受支持安全补丁 | 当前机器已经安装、迁移已成功，或未核验补丁也能上线 |
| 旧SQLite | 迁移源；确有单机需求时可保留单机模式 | SQLite完全不能多用户，或SQLite测试能替代PostgreSQL并发/RLS测试 |
| 数据访问 | 异步repository＋显式事务，参数化SQL，迁移版本可追踪 | 用Promise伪装原同步 `db.prepare().get()` |
| 租户 | workspace；个人用户注册后拥有个人workspace | 一个用户永久只属于一个租户 |
| 作品权限 | project显式成员；workspace管理权不自动赋予私有正文访问 | 加上 `user_id` 就完成隔离 |
| 实时协作 | 第一版使用版本冲突检测与显式合并 | 必须立即实现CRDT/多人同光标 |
| 检索 | 先结构化条件、引用、全文搜索；按实际需要增加向量索引 | 先建向量库就能解决事实记忆 |
| 队列 | 第一版可用PostgreSQL持久任务＋短事务领取＋租约/围栏版本 | 进程内Map可作为多实例权威队列 |
| 缓存/限流 | 权威共享状态；可先PG，确有瓶颈再引入Redis | 缓存可绕过授权或把各进程计数相加当全局限额 |
| 资料存储 | 稳定实体ID、结构化payload、显式关联、不可变版本 | 每个页面维护一份独立资料副本 |
| 费用 | 工作区预算＋项目/用户限额＋预留/结算账；精确整数或定点小数 | 浮点余额、未知用量补零、任意管理员免费无限调用 |

如Luna要改变默认方案，先新增ADR，说明原因、兼容性、受影响用例和迁移代价；不得边改边隐式更换设计。

## 3. 多用户权限：必须采用两级成员关系

### 3.1 三种身份不要混在一起

1. 平台身份：稳定 `userId`；email是可修改属性，不是外键身份。
2. 工作区成员：`owner/admin/member`，控制工作区成员、设置与预算。
3. 项目成员：`owner/admin/editor/reviewer/viewer`，控制某一本作品。

个人workspace与首个项目由一个事务创建，用户分别成为对应owner。加入工作区**不代表**自动加入其所有私有项目。工作区owner/admin默认也不能读取未加入的私有作品。平台运维默认不读正文；未来若有紧急访问，必须单独、限时、可审计授权。

### 3.2 项目角色默认矩阵

| 动作 | owner | admin | editor | reviewer | viewer |
| --- | --- | --- | --- | --- | --- |
| 读被授权项目资料/正文 | 是 | 是 | 是 | 是 | 是 |
| 编辑资料、保存草稿 | 是 | 是 | 是 | 否 | 否 |
| 创建审查意见/问题 | 是 | 是 | 是 | 是 | 否 |
| 正式采纳正文/批准事实 | 是 | 是 | 是 | 否 | 否 |
| 发起推理 | 有预算且获准支出 | 同左 | 同左 | 否 | 否 |
| 邀请项目成员/改低级角色 | 是 | 有限制 | 否 | 否 | 否 |
| 转移owner/彻底删除项目 | 是，需专项确认 | 否 | 否 | 否 | 否 |
| 导出 | 另需 `canExport`，默认有 | 同左 | 需显式授予 `canExport` | 否 | 否 |

角色授权必须与动作、资源归属、成员有效状态共同判断。`canSpend/canExport`不是客户端声明；由授权数据计算。管理员不得把自己提升为owner，也不得修改最后一名owner而留下无主项目。

项目admin只能在工作区批准的上限内管理该项目预算，不能修改workspace总余额或其他项目预算。workspace预算管理只暴露获准的总额/政策，不因此返回未加入私有项目的标题、正文或逐项目财务详情。

项目默认 `approvalPolicy=author_owned`，允许有该项目编辑权的owner/admin/editor作出自己的明确确认，保留理由、风险和审计记录；不能强迫个人工作区寻找第二位用户才能写作。协作编辑者可以确认其有权编辑的候选，原作者归属不变，确认者必须记为实际操作者，不能冒用原作者。团队可显式启用 `two_person`：不可变changeset的proposedBy不能担任该变更的独立审查者，审查通过后仍由具备正式采纳权限的owner/admin/editor执行commit。reviewer能批准/驳回审查意见，不因此获得修改正文或执行commit的权限。策略版本属于审计/采纳基线，切换策略后旧审批是否仍有效必须重新检查。

### 3.3 隔离不是只检查GET接口

以下内容全部携带workspace/project范围并重新授权：

- 单条、列表、搜索、统计、自动补全、关系图、回收站和历史版本。
- 生成请求、审计、用量、任务轮询、取消、SSE/订阅事件。
- 缓存、向量召回、上下文拼装、导入导出、附件下载。
- webhook回调、后台worker、错误信息、审计日志和管理工具。

不信任请求体内的owner/tenant字段。路径ID只是候选定位，仍需服务端验证。资源不存在与无权限应采用一致的隐藏策略；同项目已认证但动作权限不足可以返回403。

### 3.4 控制面接口：补齐项目数据API之外的生命周期

下面是目标接口，不是当前路由已实现声明；资料等24条项目数据接口详见 `DATABASE_AND_API.md`。T01须将下表纳入同一API契约和集成测试。

| 方法与路径 | 权限及关键限制 |
| --- | --- |
| POST `/api/v2/auth/register` | 按既有产品注册策略完成验证；先建稳定userId，创建个人workspace/首项目采用受控事务 |
| POST `/api/v2/auth/login` | 建立共享可撤销会话；登录限流，响应不泄露凭据和密码哈希 |
| GET `/api/v2/auth/me` | 仅返回本人可公开的身份与已授权容器信息，不返回全部项目 |
| POST `/api/v2/auth/logout` | 使当前会话在所有实例失效，不只清浏览器token |
| GET `/api/v2/auth/sessions` | 仅本人会话元数据，不返回token；撤销操作按账号安全策略确认 |
| DELETE `/api/v2/auth/sessions/:sessionId` | 仅本人会话；撤销后不可在另一个节点继续使用 |
| GET `/api/v2/workspaces` | 仅本人有效成员工作区 |
| POST `/api/v2/workspaces` | 已登录且有创建额度；原子创建workspace及owner成员 |
| POST `/api/v2/workspaces/:workspaceId/invitations` | 有相应成员管理权；绑定接收身份、目标角色、有效期和单次使用语义 |
| POST `/api/v2/invitations/:invitationId/accept` | 当前身份匹配接收者，验证有效期/未撤销；幂等且不顺带授予项目成员 |
| PATCH `/api/v2/workspaces/:workspaceId/members/:userId` | 工作区权限矩阵与版本条件；撤销成员同步使其全部项目访问失效 |
| GET `/api/v2/workspaces/:workspaceId/projects` | 仅显式加入的可见项目；管理员不能借列表发现未加入私有项目 |
| POST `/api/v2/workspaces/:workspaceId/projects` | 有效成员、有创建能力和配额；只赋创建者项目owner，不提升workspace角色 |
| DELETE `/api/v2/workspaces/:workspaceId/projects/:projectId` | 项目owner、If-Match、影响确认；先软删和停止新任务，历史保留政策另控 |
| POST `/api/v2/workspaces/:workspaceId/projects/:projectId/restore` | 授权owner与有效工作区成员、If-Match，校验恢复后引用/成员/配额 |

注册验证、登录防护、密码或身份提供方方案沿用经过核验的现有能力并修复共享状态问题；不在资料重构中未经评估重写密码算法。旧账号无法可靠映射或验证时进入人工处理，不按显示名/近似email自动合并。

### 3.5 必须一致的错误与导出协议

- 未登录/失效会话401；无scope访问资格或对象不属于scope统一404；有项目访问权但动作不允许403。
- 缺少必须的If-Match为428；格式错误400；If-Match已经过期412。
- 幂等键异载荷、审计/设定基线不符或预算不足为409，并使用不同业务code；不要把这些混成普通限流。
- 数据结构/引用非法422；纯请求速率或并发限流429；依赖暂不可用503。
- 单次请求/文件体积超限413，不支持的媒体类型415；总存储等业务配额冲突用独立409业务code，不与速率限制混淆。
- 正文和字段错误不能泄露SQL、其他项目是否存在、原始凭据或供应商密钥。
- 项目/工作区业务POST使用对应范围的幂等键。认证凭据请求不进入该通用回包缓存；登录、注册验证使用单独的短期重放/验证码消费策略，不能把密码请求或完整会话token写入通用幂等表。
- 导出创建、清单、下载都要求当前 `canExport`；不能因为知道exportId或曾有权限就继续下载。
- 默认下载经应用代理并再次授权，不直接把永久对象地址交给浏览器。若将来改用短期签名地址，必须明确撤销延迟窗口并重新验收，不能同时声称签名地址离线可用又声称立即撤权。

### 3.6 浏览器换账号、跨标签页和未保存稿

多用户不能只测两个独立浏览器登录。还必须在同一浏览器中A退出、B登录，保留另一个A的编辑标签页和迟到响应，验证：

- 缓存键使用稳定userId/workspaceId/projectId及必要版本，不用email、标题或“default”混作所有权。
- 请求发起时冻结认证epoch与目标scope；账户/项目切换后停止旧自动保存、取消旧订阅，迟到结果不能写入新账号或新作品。
- 客户端可携带expectedActorId用于检测会话切换，但服务端只与实际会话actor比较，不把它当授予身份的依据；不匹配就拒绝旧动作。
- 同一项目的两个协作者也不能因为换账号而把旧用户的未确认自动保存归到新用户；应重新确认当前操作者与版本。
- V2不保留旧“localStorage优先覆盖服务端”的权威模式。私有缓存不跨账号显示；未批准的离线能力不承诺可跨退出登录保留。
- 退出前提示未同步稿并给出保留/放弃路径，不静默丢稿，也不在新账号登录后自动认领。游客稿迁移需要明确认领流程，不能根据同一台浏览器就推断所有权。

离线加密存储若以后单独建设，需另行定义解锁、密钥、撤销和共享设备边界；不能声称普通localStorage等同安全私密数据库。T03/T13应把同浏览器换账号及跨标签页作为SEC-06等案例的参数化变体。

## 4. 49项资料如何落实为产品，而不是只补字段

`implementation-plan.json`逐项列出了：

- 原需求ID与名称；
- 目标逻辑字段；
- 所属实体/文档；
- 界面入口；
- 负责的工作包；
- 必须保持的往返不变量；
- 参数化验收实例 `DATA-01/A01` 等。

每项的最小完成定义是：

```text
字段契约
→ 服务端校验
→ 数据持久化/版本
→ 页面新增编辑
→ 引用与权限
→ 重开恢复
→ 导出再导入
→ 自动化与人工检查
```

某项不适用时由题材/作者明确标记并保留理由，不用空字符串伪装完成。不应让49项全部成为起草第1章的必填项，但其管理能力必须有验收。

### 4.1 通用字段与文本保真

- 主键稳定，名称/昵称/笔名变化不能改变引用。
- schema与业务版本分开；正文原文哈希的编码、换行及富文本到纯文本规则要固定。
- 迁移不得先 `trim/slice` 再声称原文未变；需要转换时保留前后版本及原因。
- 核心类型有明确schema，自定义扩展放入命名空间；旧未知字段进入保留区和迁移报告。
- 人物资料只能有一个权威实体；浏览器工作区是缓存，必须带服务端revision，不再优先覆盖新数据。
- 相同姓名不自动合并；显式合并先展示所有受影响引用和可逆映射。

### 4.2 故事语义的边界

严格分开：设想、计划、已批准设定、正文事实、角色认知。故事发生时间、叙述顺序、系统修改时间也要分开。

伏笔有计划与实际状态；未到回收期不等于失败。台词中的谎言不等于客观事实。后记不是故事事实；平行设定番外以 `continuityId` 隔离，不混入主线。第一版不要求实现完整Git式创作分支，但必须能表示主线/非主线事实作用域。

## 5. 数据库与API实施的禁止事项

详细定义见 `DATABASE_AND_API.md`。下面这些错误必须作为代码审查阻断项：

1. 只给主表加tenant列，版本/关系/审计/任务表没有范围。
2. 外键只检查实体ID存在，不检查属于同一workspace/project。
3. 用表owner、superuser或BYPASSRLS角色跑普通应用，再声称RLS测试通过。
4. 把RLS仅限定workspace，却宣称实现了项目私有权限。
5. 跨请求复用带上一个用户会话变量的连接。
6. 在不同连接上执行同一事务；或在事务内等待AI网络返回数分钟。
7. 只检查客户端传来的 `passed/userId/role/delta`。
8. 不带基线版本直接覆盖作品；或旧API仍能覆盖新资料。
9. 同一数据库修改成功后，认为远端推理也具备“恰好一次”。
10. 用新JSONB包住旧巨型state，却不解决实体ID、引用和版本问题。

同步SQLite改异步PG时，必须审查完整调用链：repository返回Promise后，上层判断、循环、事务、错误回滚、HTTP结束均须正确await。禁止通过返回假同步值骗过原字符串测试。

## 6. 正式提交事务：给Luna的步骤级要求

### 6.1 起草前

1. 认证会话，验证workspace和project成员以及支出能力。
2. 读取当前正文/规划/设定/状态版本。
3. 按场景、人物认知、故事时间、事实依赖构造上下文。
4. 记录所用资料ID和版本、未纳入资料及原因、模型配置/提示版本和预算。
5. 保存持久任务及请求指纹，预留额度；提交短事务。
6. 事务外调用供应商。不可为等待模型持有项目行锁。

### 6.2 审计对象

审计绑定 `workspaceId/projectId/continuityId/chapterId/manuscriptRevisionId`，以及正文哈希、设定/计划/状态版本、上下文哈希、增量哈希和策略版本。审计覆盖状态与问题严重性分开；正文/资料被改后，旧审计标过期而不是沿用。

### 6.3 正式采纳

1. 认证和成员资格重新检查，不相信任务开始时的权限。
2. 取得同一PG连接并BEGIN；按固定顺序锁定需保证一致性的成员/项目/预算等行，避免不同端点相反加锁顺序。
3. 校验所有expected revision。失败返回明确的冲突/过期，不默默基于新版本重做。
4. 校验审计对应实际正文、资料和已审核增量。缺失状态字段不代表清空。
5. 从确认的delta推导事实、关系、时间线和伏笔变化，不接收任意客户端快照覆盖。
6. 同事务写正文版本、状态版本、事实/引用、提交记录及outbox。
7. COMMIT后返回稳定回执；如果响应丢失，客户端按原幂等键查询/重放。
8. worker处理派生索引/提示等outbox；重放必须幂等，失败可恢复，正文提交不回滚。

角色撤权与提交的竞争必须定义并测试：已完成的事务不倒带；撤权完成后不能再发起新的有效读写或完成尚未授权的正式提交。长任务在领取、读取输入、展示结果、最终提交时都要重检；无法中断的既有远端调用要隔离结果并保留真实费用记录。

### 6.4 作者修改自由

允许保存待复核草稿。作者确认语义例外时记录理由和后果，并对设定建立修订；不得篡改机器审计结果。结构损坏、跨用户引用、假哈希、账本不一致等技术约束不能靠“作者同意”绕过。

### 6.5 接口字段合同：不能留给实现时自由猜测

T01将下面字段转为正式请求/响应schema。所有ID需通过所属scope检查；仅验证UUID格式不够。示例字段是目标协议，不声称旧接口已经兼容。

**资料PATCH**：路径 `P/resources/:type/:id`，强 `If-Match` 绑定对象ID和revision。请求只含允许修改的payload字段及 `changeReason`；不得修改 `workspaceId/projectId/createdBy/revision` 等服务端字段。响应包含完整资源头、revision、强ETag和本次changeSetId。PATCH未提供字段保持原值，null仅在schema明确允许清空时有效；数组是显式替换还是ID级操作须按类型冻结。

**生成POST**：路径 `P/jobs`，请求至少包含 `kind`、目标chapter/scene/continuity ID、expected资料版本、生成选项及客户端可接受的预算上限。服务端确定调用模型许可、最终上限、actor、请求摘要及contextSnapshot。响应202包含稳定 `jobId/state/eventsCursor`。轮询/SSE均重新授权，不能返回原始供应商凭据或未授权资料。

**正式采纳POST**：路径 `P/commits`，请求合同如下：

| 字段 | 必填与验证 |
| --- | --- |
| `manuscriptId/chapterId/continuityId` | 必填，同一项目内有效对象且相互关系正确 |
| `manuscriptRevisionId/manuscriptHash` | 必填，指向已经保存的候选版本；服务端按固定文本规则重算 |
| `expected.manuscriptRevision` | 必填，与If-Match及实际文稿头一致 |
| `expected.bibleRevision/planRevision/stateRevision` | 必填，均与冻结上下文、审计、当前可提交状态一致 |
| `expected.aclRevision/approvalPolicyRevision` | 必填；变化后重新授权和检查审批，不能只沿用旧成功结果 |
| `contextSnapshotId/contextHash` | 必填，指向服务端保存的不可变输入快照；不能接收客户端伪造完整上下文 |
| `deltaId/deltaHash` | 必填，指向服务端保存并经审查/作者确认的增量；不接收任意客户端state快照代替 |
| `auditId` | 机器审计路径必填；审计实际状态、策略版本和源版本由服务端读取 |
| `authorDecision` | 需要作者确认/例外时包含理由和风险确认；actor和时间由服务端赋值，不能伪造他人的确认 |
| `reviewApprovalId` | two_person模式必须有独立审查者的有效批准；默认author_owned不要求第二个人 |

请求不得带客户端自报 `passed=true`、任意角色、余额或可信 `actualCost` 来覆盖服务端判断。响应包含 `commitId/manuscriptRevision/stateRevision/bibleRevision/planRevision/aclRevision/replayed` 及派生任务状态。响应正文和状态来自同一提交结果；即便后续索引待恢复，也不能返回虚构的新版本。

**手工稿不能被迫调用模型才能取得deltaId**：editor+先POST `P/change-sets`，提交已保存候选的引用、基线及作者提出的增量；服务端进行schema/权限/引用/证据校验，存成不可变提案并返回deltaId/hash，不自动确立事实。GET `P/change-sets/:id`读取提案；POST其 `/reviews` 写入有权审查者的结论；POST其 `/author-decisions` 记录当前操作者的确认。两条决策路径均绑定完全相同的版本元组，最终再由POST commits执行原子采纳。没有模型审计的合法手工路径标记为人工确认，不能伪造auditId或机器PASS。

费用按任务用量账本唯一结算，正式采纳不能再次扣除同一笔生成费用，也不信任旧客户端的 `actualCost`。如果未来产品另收某种业务费用，必须成为独立定价事件并单独验收，不得混入token结算。

**资源类型白名单**：第一版可注册 `profiles/world-documents/characters/places/factions/power-systems/rules/abilities/items/terms/relations/storylines/plot-nodes/calendars/story-events/foreshadows/materials/writing-tasks/issues/manuscripts`，每类映射固定schema与服务。`audits/commits/billing/members/outbox`等敏感或派生对象不能通过通用resources路径任意增改；正式事实/认知写入通过受控changeset/commit，不把账本暴露为任意表编辑器。

### 6.6 字符、证据和派生索引的规范

正文版本以明确UTF-8文本表示保存，记录换行/富文本提取算法版本；不得在审计后重新trim或改换行。服务端资料证据统一记录具体文稿版本和UTF-8字节区间，并保留段ID/摘录哈希。旧JS代码的UTF-16索引必须显式换算，不能把字符下标当字节偏移。

验收包含中文、emoji、组合字符、CRLF/LF、引号和多段重复引文。仅有同一段文字出现不证明引用位置唯一；只要正文版本或提取算法改变，旧偏移就不能无条件沿用。

资料搜索、关系图和语义索引都是派生结果，必须记录源revision；过期索引不能被称为当前事实。派生任务失败允许重建，原始文稿和批准事实不能被索引覆盖。

## 7. 多实例任务、预算与故障恢复

### 7.1 任务状态

冻结任务状态：`queued → claimed → running → succeeded / failed / provider_unknown`；取消通过 `cancel_requested → cancelled` 表达。正文另有draft/review/accepted等状态，不能与任务是否结束混用。文中的unknown描述外部结果未知这一语义，数据库状态统一使用 `provider_unknown`。

- 多worker领取使用短事务，持久化租约及递增的 `attempt/fencingToken`。
- worker写结果必须匹配当前围栏版本；旧worker复活不能覆盖新结果。
- 外部请求发出前持久化attempt/request标识；外部已执行而回包丢失属于unknown。
- unknown先核对供应商可查凭证或人工处理，不直接租约到期就重发。
- 只有已知可安全重试的内部幂等步骤才自动重试。
- 如果采用 `SKIP LOCKED`，仅用于队列领取等允许跳过锁行的场景，不作为所有业务读取的通用隔离方法。
- outbox事件幂等键包含来源对象和版本/事件序号；同一job可以发生多次相同类型的状态事件，不能用 `UNIQUE(job_id,event_type)`吞掉后续事件。手工正式采纳没有AI job，也必须能够产生绑定commit的outbox事件。

### 7.2 费用

工作区、项目、用户分别设额度和并发上限。余额/预留/实际结算在PG中原子更新，额度不足时拒绝，不能两个实例同时读到余额后都扣款。

- 用量未知不补零；估算只用于预留，不冒充实际账单。
- request/attempt/usage唯一约束防止重复结算。
- unknown预留需对账；不能超时就释放后无限再次调用。
- 供应商价格/模型别名/参数版本须追踪；项目owner不等于旧全站admin无限免费。
- 取消后是否发生真实费用按供应商可观测结果记录，不能承诺取消必然免费。

### 7.3 多实例基础

会话、撤销、成员关系和共享限流不能只存在单进程Map。启动两个API实例、两个worker，验证任意节点读到一致的授权和任务状态。不以粘性会话掩盖基础状态缺失。

第一版可PG共享任务和额度；若追加Redis，需明确失败时的保守策略及重建来源。缓存不作为权限权威，每次返回前检查当前访问范围和必要权限版本。

### 7.4 调度者和执行者不能获得相同的全库权限

跨项目调度需要知道哪些任务待执行，但不需要读取所有人的正文。T09应明确拆开：

- `job_dispatch`等受控调度元数据：只含workspace/project/job标识、可领取时间、优先级、租约和围栏等，不含标题、正文、prompt、原始结果或费用详情；与任务创建在同一事务登记。
- scheduler身份：只能领取/更新这些调度字段；不能查询资料、正文、成员凭据或项目账本，也不对终端用户暴露全局列表。
- execution身份：只能根据有效claim进入该job对应scope；验证持久化的发起者、项目能力、任务类型、租约/围栏、预算和当前权限，再通过相同授权仓储读取输入。不能接受调用者自行指定的任意actor/scope来伪造任务。
- 后台结果和outbox都保留来源job/commit及scope；恢复、重建索引、取消和重放沿用这些边界，不授予worker数据库owner权限。

用户退出登录只撤销会话，默认不取消已经被服务端接受的后台任务；重新登录后仍按当前项目权限查看。用户被禁用或项目/工作区权限被撤销则阻止后续授权操作和正式提交。任务取消是单独动作，已发出的远端调用无法证明未执行时进入 `provider_unknown` 或保留取消待对账，不因退出浏览器就伪造“零费用失败”。

这些是需要在真实多进程环境验证的要求；调度元数据的有限跨项目权限不是应用正文权限的例外通道。

## 9. Luna每个工作包的标准操作

### 开始前

1. 读取当前AGENTS、对应任务卡、相关数据库/API契约、关联验收用例。
2. 定向查看git状态，记录用户改动；建立此次改动的文件范围。
3. 确认依赖已验收，以及测试使用的是哪个临时库/账号/模型适配器。
4. 针对本任务写出输入/输出、禁止变化、失败方式和恢复方式。
5. 先写能复现缺口的测试；既有功能退化也要覆盖。

### 实施中

1. 优先在新的领域模块完成逻辑，再薄适配旧路由。
2. mutation都走授权、校验、基线版本、事务和审计；UI禁用按钮不是授权。
3. 避免大范围机械替换同步数据库调用；逐调用链迁移并测试。
4. 真正执行失败时先定位，不能删除断言或反复盲重试。
5. 模型/外部系统结果未知时冻结对应动作，保留请求和成本证据。

### 交付时

必须给出：

```text
工作包ID：
修改文件：
实现到的需求ID：
数据库/接口变更：
测试命令与实际结果：
测试基于的代码/迁移/schema/fixture版本：
新风险或未验证项：
回滚/恢复方法：
下一可执行任务：
是否可进入下一门禁：是/否及理由
```

只贴“测试全绿”不算交付。主集成人复核子任务，运行组合测试，检查共享接口与schema是否发生不兼容变化。

## 10. 数据迁移：可以重构，但不能遗失作者的工作

### 10.1 必须盘点的来源

用户/会话、novels、creation_books/bibles/versions/snapshots、各JSON工作区、人物库、事实/伏笔/债务、生成回执、审计、费用、正文历史、附件引用。未通过授权的原书/范本不自动归入用户作品包。

用户映射使用稳定映射表，不根据显示名合并。旧email规范化冲突、无主作品、游客草稿认领、同名人物、丢失章ID、已截断字段均进入人工冲突清单；不能伪造恢复不存在的原文。

通过API从另一个项目复制/导入资料时，必须分别检查来源项目的读取/导出授权和目标项目的导入权限；不能凭“我是目标项目owner”读取来源私有数据。外部用户上传文件作为不可信输入校验，不自动读取文件中声称的其他项目或本机路径。整包恢复默认进入隔离空目标；向既有项目合并需显式映射/冲突预检，不能整份覆盖。

### 10.2 迁移流程

1. 只读盘点并计算源快照与正文哈希。
2. 生成迁移计划及冲突报告；明确哪些可自动映射、哪些要人工确认。
3. 在隔离PG导入，保留不可变源payload与 `legacy_id_map`。
4. 校验数量、完整字段、版本、关联、人物/时间/伏笔及费用守恒。
5. 重复运行同一迁移，不新增重复用户/实体/收费记录。
6. 完成导出再导入与恢复演练。
7. 切换前建立项目级写入围栏或短维护窗口，处理增量变化；不长期开启双主写入。
8. 逐项目切换，旧读路径只作兼容/回查，所有新写进入一个权威服务。
9. 切换后出现的数据也要能保留/迁出；简单恢复旧备份可能丢新稿，不可称无损回滚。

### 10.3 必须停止切换的条件

正文哈希不符、人物/关系/伏笔缺失、任何跨用户泄漏、费用不守恒、无法恢复、旧接口仍能绕过权限/版本、关键用例未运行、已有高风险缺陷未关闭。

## 11. 如何审查“真的达标”

详细用例在 `ACCEPTANCE_PLAYBOOK.md`，所有初始结果均为NOT_RUN。

### 门禁G1：契约与数据

49项每项有schema、UI、持久化、关联、重开和往返证据。不是“49个字段存在”，也不是“建了49个空表”。

### 门禁G2：多用户安全

跨workspace、同workspace跨项目、不同角色、旧端点、检索/缓存/任务/导出均有负向测试。**任何未经授权的数据读取、写入或费用操作都阻断放行**。

### 门禁G3：一致性与故障

真实PG中验证CAS、复合FK、RLS、事务回滚、双worker、撤权、断线、unknown及预算竞争。内存mock不能替代。

### 门禁G4：用户操作闭环

浏览器中用多个真实测试身份，完成资料维护→章纲→模拟生成→审查→正式采纳→改旧资料→冲突处理→导出恢复。UI、网络响应和数据库结果相互对应。

### 门禁G5：容量与恢复

先运行固定负载与背景数据规模下的压力测试，再据实标注容量。区分普通CRUD延迟和供应商生成耗时。恢复演练需从备份真正恢复并校验权限、数据与正文，不只检查文件存在。

### 门禁G6：内容质量

工程门禁通过后才进入有预算的真实题材生成、长距离知识/时间/伏笔检查和真人阅读。原P0/P3/P4与整章精读任务仍未自动完成；不能用本次多用户改造替代它们。

### 阶段划分，避免互相等待或偷换验收范围

- T13必须完成49个工程系统案例（50个固定ID中除AI-08外）和49项 `DATA-01/<需求ID>` 参数化实例，满足G1–G5。
- AI-08的真实供应商与真人切章安排在T14；T13记录其NOT_RUN/待预算不算通过，也不能把它从总清单删除。
- 因此“T13工程范围通过”不等于“全部50个系统案例通过”。只有AI-08也有有效证据，才能宣布包含真实生成链路的全范围技术验收完成。
- T14有真实生成预算或目标切换未授权时明确BLOCKED。可以保留已通过的工程范围结论，但不得宣布正式生成能力或真实迁移已完成。
- 若计划切换后向用户开放真实生成，须在受控环境先完成AI-08的技术闭环；文学好坏仍是独立的人审结果，不能靠技术闭环自动通过。

### 结果状态与证据

每项使用PASS、FAIL、BLOCKED、NOT_RUN、NOT_APPLICABLE；另标证据是否stale。BLOCKED/NOT_RUN不是PASS。不适用必须给条件与审查批准，不能用来绕过跨租户或数据完整性必测项。

证据包至少含：任务/需求/案例ID，代码指纹，依赖锁定信息，数据库版本/角色/RLS设置，迁移与schema版本，fixture版本，命令/退出码，必要HTTP/数据库断言，脱敏截图或日志，运行时间及审查者。修改相关实现、授权配置或migration后，受影响证据重新运行。

## 13. 官方设计依据及其适用边界

本项目选择PG18和异步Node仓储属于设计决策，不是数据库已经迁移。以下资料在2026-09-15核验：

- PostgreSQL版本支持：`https://www.postgresql.org/support/versioning/`
- RLS及owner/BYPASSRLS边界：`https://www.postgresql.org/docs/current/ddl-rowsecurity.html`
- 事务隔离与并发重试：`https://www.postgresql.org/docs/current/transaction-iso.html`
- 行锁与SKIP LOCKED：`https://www.postgresql.org/docs/current/sql-select.html`
- node-postgres事务必须使用同一client：`https://node-postgres.com/features/transactions`
- OWASP授权：`https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html`
- OWASP多租户：`https://cheatsheetseries.owasp.org/cheatsheets/Multi_Tenant_Security_Cheat_Sheet.html`

RLS不替代动作授权，不防所有SQL注入，也不保证应用代码正确；事务重试仅适用于可安全重放的数据库工作，不表示远端生成也可重发。官方文档不替代本项目真实环境的安全、性能与恢复测试。
