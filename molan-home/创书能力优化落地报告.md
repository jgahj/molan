## 一、创书能力现状诊断（基于实际代码与实测）

### 1.1 当前创书链路（已实现，实测跑通）

```
拆书结果 result_json
  └─ POST /api/dissections/:id/creative-brief   → 创作简报（brief + 分卷/人物/伏笔规划 + forbiddenCopy）[gpt-5.6-luna]
       └─ editor.js openCreateFromDissection    → 新书框架（title/oneLine/themes/volume/chapters）[gpt-5.6-luna]
            └─ POST /api/creation-books         → creationBook + Bible v1（服务端持久化）[新增]
                 └─ 新书 state（localStorage）  → 后续正文生成（缺闭环）
```

### 1.2 各环节弱项（实测证据）

| 环节 | 现状 | 问题 |
|---|---|---|
| 创作简报 | 已实现且质量高 | 无；简报正确产出 forbiddenCopy/人物/伏笔/文风 |
| 新书框架 | 已实现，实测产出 20 章带钩子 | 仅是**规划层**，未生成任何正文 |
| 创作圣经 | **本轮新增**持久化（4 表 + API） | 编辑器写章尚未真正读 Bible / 状态快照 |
| 章节合同 | 无源书此前返回 `null`（静默跳过） | **本轮修复**为本地最小合同 |
| 连续性审计 | 无源书此前返回 `{skipped,passed:true}` 假通过；且服务端审计因 `req.body` bug 审空正文 | **本轮修复**（本地确定性审计 + readBody 修复） |
| 动态上下文 | `refreshDissectionContext()` 此前是死代码 | **本轮修复**为读新书 Bible/状态快照 |
| 原创检查 | 仅 **词面匹配** forbiddenCopy | 无法判定"结构/功能级复刻"（见 P3） |
| 人物聚合 | 仅 **Top30** 完整档案（需 1931 实体） | 覆盖不足，任务被标 `needs_review`（见 P4） |
| 成本 | 无预算上限；person 聚合 O(角色数/10) 模型调用 | 整书聚合约 7 小时（见 P5） |
| 评测 | 无黄金集 | `scripts/eval` 骨架已建，待接入真实 pipeline（见 P5） |

### 1.3 隐蔽重大 bug（本轮发现并修复）

**本代码库从未设置 `req.body`**：正确模式是 `readBody(req).then(p => …)`（如 `handleNovelCreate`），但以下 6 个 handler 直接读 `req.body`，导致**永远拿到空 body**：

- `handleDissectionCreativeBrief` / `handleDissectionChapterContract` / `handleDissectionAudit`
- `handleCreationBooksCreate` / `handleCreationBookBiblePut` / `handleCreationBookCommit`

后果：服务端连续性审计实际在审**空正文** → 模型大概率返回 `passed:true`，即**服务端审计也处于假通过状态**（与前端 `skipped+passed` 是同一个反模式的两个出口）。已全部改为 `await readBody(req)`，云端 12 项 HTTP 验证通过。

## 五、落地实施计划（按优先级，每项含 目标/改动/验收）

### P1 · 正文生成闭环（最关键，直接决定"创书能力"强弱）

**目标**：能基于新书 Bible + 状态快照真正"写出一章"，且 合同→正文→审计→提交快照 全程有状态。

**改动点**
1. `pages/editor.js` 生成下一章时：
   - 用 `state.creationBookId` 拉 `/api/creation-books/:id/state?chapterNo=` 取 Bible + 截至前章快照，喂入 `buildDynamicContext`（已具备注入能力，需接通真实数据）
   - 场景级生成：`chapterContract.goal` 按场景切分，逐场景流式输出（方案 8.5 场景预算）
2. 正文审计后提交：
   - 审计通过 → `POST /api/creation-books/:id/commit`（CAS），写 `characterStates/timeline/openForeshadows` 快照
   - 冲突 409 → UI 提示 `needs_rebase`
3. `requestChapterAudit` 对有 `creationBookId` 的书改用服务端 `/audit`（已修复 body 读取）
4. **框架沿用简报人物名**：框架提示词显式要求"人物名必须沿用创作简报 characterPlan 中的名字，不得自行重命名"（修复《烬潮铸命》人物名不一致问题）

**验收**
- [ ] 新建书后连续写 3 章，每章均产生状态快照（`creation_state_snapshots` 递增）
- [ ] 快照 chapterNo 单调递增，CAS 冲突能 409
- [ ] 下一章提示词包含前章人物状态 + 未回收伏笔 + 当前弧（从 Bible 读取）
- [ ] 框架 chapter 人物名与简报 characterPlan 一致（重跑创书抽样验证）
- [ ] 回归测试：`buildDynamicContext` 注入含 `creationBookId` 数据

### P2 · 动态上下文真实接入正文生成

**目标**：把 Bible（人物/伏笔/世界规则）+ 状态快照变成正文提示词的"硬约束"。

**改动点**
1. `buildDynamicContext` 增加 Bible 区块：characters（含缺陷/弧光）、forbiddenCopy、volumePlan、foreshadowLedger
2. 把 `forbiddenCopy` 注入系统提示词：生成时即要求不触发禁止项（前置约束，而非仅事后审计）

**验收**
- [ ] 生成提示词含 `【创作圣经·禁止复制项】` 区块
- [ ] 生成的正文不含 forbiddenCopy 词面项（抽样 20 章，命中率 0）

### P3 · 原创偏离审计升级（结构级）

**目标**：能识别"换名复刻"（角色功能组合、事件链顺序、金手指等价迁移是否成立）。

**改动点**
1. 服务端 `divergenceMatrix` 计算：原书功能清单（拆书 `characters.function` + 事件链）vs 新书（Bible characters.role + 框架章节事件）做**功能组合相似度**比对
2. 低置信度样本交模型复核（`/api/chat` 一次调用），输出 `{diverged: bool, riskLevel, evidence}`
3. 结果写入 `creation_bible_versions` 的 `divergenceMatrix` 字段，并在审计接口展示

**验收**
- [ ] 对已知复刻样本（构造"萧炎改名"案例）能标记风险
- [ ] `false_pass_rate`（原创）在评测 runner 中为 0

### P4 · 人物聚合覆盖修复

**目标**：次要人物也有可用档案，消除 `needs_review` 误报。

**改动点**
1. 聚合按**出现频次分层**：TopN 用模型档案，其余用"档案骨架 + 证据统计"（首登场章/出场频次/状态变化），不强制全量模型调用
2. 修正 `characterAggregationComplete` 判定：允许"模型档案缺失但证据统计存在"时标记 `ok`（而非 `needs_review`）

**验收**
- [ ] `characters` 覆盖 > 95%（按 entities 计）
- [ ] 复跑 1647 章聚合后 `validation.conclusion` 不含 `characters aggregation coverage`

### P5 · 成本与评测

**目标**：成本可测、质量可评。

**改动点**
1. `model_usage` 补 `credit_cost`（从 `molan_usage.estimatedCreditCost` 取，当前为 0）；`/api/usage` 汇总按 stage/unit_id 输出成本报告
2. 预算上限：按任务预估积分设置阈值，超限自动暂停（写入 `dissections.estimated_credits` 校验）
3. `scripts/eval` 接入真实 pipeline：`evaluate(sample)` 替换为调用本地纯函数/云端 API；用《节点回响》框架 + 抽样章节建首版黄金集（30 条）

**验收**
- [ ] 一次创书任务的成本可精确到"每章/每阶段"
- [ ] 评测 runner 对黄金集输出 9 项指标，`false_pass_rate=0`
- [ ] 预算超限任务自动暂停并提示
