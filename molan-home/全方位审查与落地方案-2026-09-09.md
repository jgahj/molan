## 二、工程侧优化（P0 → P2）

### P0-1 修复看护重启风暴（预计 0.5 天）

根因：`watchdog-node22.bat` 只要 `curl` 4 秒内拿不到 `/api/health` 就 `start` 一个新 `start-node22.bat`，新实例绑定 3000 失败退出，旧实例若卡住则持续循环；两份看护并行让频率翻倍。

落地：
1. `start-node22.bat` 增加互斥：启动前查 `netstat -ano | findstr :3000`（或写 `data/server.pid`），端口已占用则直接退出。
2. `watchdog-node22.bat` 增加单实例锁（`data/watchdog.lock`，启动时若锁存在且对应 cmd 进程存活则退出）；连续 3 次失败才重启，重启前先 `taskkill` 占用 3000 的僵死 node。
3. `/api/health` 增加 `uptime`、`pid`、`activeChatStreams` 字段，便于区分“挂了”与“忙”。
4. 把 `watchdog.log` 加轮转（>2MB 改名 `.1`）。

验收：人工 `taskkill` 主服务后 60 秒内恢复且只有一个 node/一个 watchdog；空跑 24h `watchdog.log` 新增 ≤3 行。

### P0-2 恢复可用的测试基线（预计 1 天）

1. `package.json` 的 `test` 改为 `node --experimental-sqlite --no-warnings --test test/`，排除 `scripts/`。
2. `test/v31-stage0.test.mjs`：不再复制 112MB `index.json`，改用 fixture 抽样 200 条（或标记为 `--test-name-pattern` 手动运行的 slow 组）。
3. 修复 `structural-originality.test.js:16`：`callMolanChat` 收到非 JSON/非 SSE 的上游 HTML 时应 `throw new Error('上游返回无法解析…')`，当前实现把 HTML 当正文返回（定位 `server.js:13062` 附近的响应解析分支）。
4. 增加 `npm run test:fast`（<60s 子集）与 `npm run test:full`。

验收：`npm test` 5 分钟内完成且 0 fail；`test:fast` <60s。

### P1-3 仓库与配置卫生（预计 0.5 天）

1. `git gc --prune=now` 清理 13.66MB 垃圾 pack（只读操作，不改历史）。
2. `data/genre-lab/corpus-*.json`、`data/paragraph-samples.json`、`data/style-fingerprints.json` 二选一：加入 LFS，或迁到 `resources/` 并由 `scripts/build-*.mjs` 生成；`.gitignore` 同步。
3. `server.js:396` 的绝对路径改为 `process.env.MOLAN_CORRECTION_FILE || path.join(__dirname, '..', '纠错库.md')`。
4. `data/config.example.json` 补齐 `platformModels/modelPolicy/cloudApiBase` 字段示例，README 补“密钥全部走环境变量或 config.json，两者优先级”。

### P1-4 静态资源传输（预计 0.5 天）

在 `server.js` 静态文件分支（约 1216–1273 行）增加：`Accept-Encoding` 含 `br/gzip` 时用 `zlib.brotliCompressSync/gzipSync` 并缓存到内存 Map（key=path+mtime）；JS/CSS 在文件名带 `?v=<mtime>` 时改 `max-age=31536000, immutable`，HTML 保持 `must-revalidate`。

验收：编辑器首屏传输从 ~1.3MB 降到 <400KB（DevTools Network 核对）。

### P2-5 `server.js` 拆分（预计 3 天，可与生成优化并行）

按现有函数簇平移到 `lib/routes/`：`creation-books.js`（10756–12700）、`chat.js`（1749–2500）、`auth.js`（4100–4200）、`genre-lab.js`（13940–14100）。只做移动 + `module.exports`，不改逻辑；每移一簇跑对应 `test/creation-*.test.js`、`chat-stream-*.test.js`。

## 三、生成小说质量优化（核心）

当前链路（`completion-editor.js:1613–2260`）：`fetchStylePack`（genre-lab → xuanhuan-lab → local-style 三级降级）→ 起草（maxTokens 2200/6000）→ 审计（服务端确定性 + 三视角模型审）→ 文风距离分 → 前三章双稿择优 → 修订 → 账本合并。

已具备但**没接进来**的能力：`lib/causal-debt-tracker.js`（因果债务）、`genre-engine.js` 的场景能级/生理动作配比门禁（e34d0ca 只落在实验脚本 `generate-fanren-10-chapters.mjs`）、`sanitizeAiFlavor`。

### G0 把实验室能力接入正式创书（预计 2 天，性价比最高）

1. **因果债务接入**：`handleCreationBookChapterAudit`（`server.js:12384`）审计通过后，用 `CausalDebtTracker` 登记本章“新开的账”（承诺/威胁/未解释异常），存 `data/causal-debts/<bookId>.json`；起草上下文 `buildContext` 追加 `【未兑现因果债务（按到期章排序）】` 区块，≤600 字。
2. **场景能级门禁进审计**：把 `genre-engine.js` 中的能级/躯体动作配比检查包装成确定性 issue（`category:'somatic'`），低能级场景出现 ≥3 处“指骨发白/瞳孔骤缩”类词即 warning，与现有 `redundancy` 并列。
3. **默认写作 Skill 按题材切换**：`ensureDefaultWritingSkill`（`server.js:5833`）目前只有一个 default；按 `bible.taskConstraints.genre` 选 `skills/<genre>/` 存在则用之，否则回落。

验收：新建一本书跑 3 章，`run.creationAudit.issues` 出现 `somatic` 类目；第 2 章起草 system prompt 含债务区块；债务文件随章增长。

### G1 状态连续性规划（对应 quality-gap 缺口 1，预计 3 天）

问题：`井底回班` 类错误——断电设备继续工作、无工具割钢缆——现有审计查“事实矛盾”但不查**物理状态链**。

落地：
1. 章纲扩展提示（`creationPlanExpansionPrompt`，`server.js:10756`）为每章增加 `stateTable`：`{entity, location, holds:[], power/energy, constraints}` 的**起始/结束**两份表，由规划模型输出，客户端不做推断。
2. 起草提示注入“本章状态表（起点）”与“必须到达的终点状态”；正文不得凭空改变未列出的资源。
3. 审计增加确定性“状态引用检查”：正文出现 `stateTable` 中标记为 `unavailable/lost` 的工具或能力名时报 `category:'state'` warning（关键词匹配即可，零模型成本）。
4. 模型审计视角增加第四项 `stateflow`：只审供电/受力/位置/持有物变化是否有交代。

验收：用 quality-gap 里的《井底回班》原文回放审计，能命中至少 2 处状态错误。

### G2 证据驱动的修订闭环（缺口 2，预计 2 天）

现状：`!audit.passed` 时整章重写（`completion-editor.js:2230+`，maxTokens 3500），无法验证旧问题是否解决。

落地：
1. 审计 issue 强制带 `quote`（原文 ≤40 字定位），服务端用 `indexOf` 校验，找不到的 issue 降级为 `unverified` 不进入修订。
2. 修订改为**局部**：按 issue 的 `quote` 切出 ±2 段窗口，让模型只重写窗口，返回 `{quote, replacement}`；客户端拼回。
3. 修订后自动复审：只把原 issue 列表 + 新窗口文本送审，返回 `resolved[]/unresolved[]/new[]`；连续 2 轮 `unresolved` 不减则保留 `status:'needs-human'`，不再重写。
4. `run` 记录 `revisionRounds[]`，UI “本章审计”弹窗展示每轮解决/遗留。

### G3 人物关系与阅读体验复核（缺口 3，预计 2 天）

1. 人物卡 `stance` 字段（已有）升级为**章级关系账本**：审计 `factLedgerDelta.byEntity` 新增 `kind:'关系'` 的条目自动进 `relationLedger`；起草简报改为“上章关系 → 本章要推进到”。
2. 冷读审补两问：“本章哪一句让读者更在乎某个人物”“有没有直接请求/真心关心/不聪明回答”（对应 quality-gap 第 3 点，防全员机锋）。
3. 每 5 章触发一次“连续审读”：把 5 章摘要 + 关系账本送审，只出 `relationDrift/promiseDrift/toneDrift` 三类，写入卷级质量报告。

### G4 长篇稳定性验证（缺口 4，预计 3 天，含跑费）

1. 用 `scripts/generate-lab-sample.mjs` 的模式新增 `scripts/run-longform-eval.mjs`：对同一核心包连续生成 10 章（走正式 `/api/creation-books/*` 接口而非实验路线），每章落盘 + 审计 JSON。
2. 指标固化到 `scripts/eval/baselines.json`：`stateIssuesPerChapter ≤0.5`、`unresolvedDebtAge ≤3 章`、`nameOverlap=0`、`styleDistance ≥75`、`repeatedPhraseWarnings ≤1`。
3. 先做 2 本（玄幻 + 都市）各 10 章，记录 token 用量，作为后续每次改提示词的回归基线。

### G5 提示词预算与字数校准（预计 1 天）

1. 现状：上下文只靠 `clipContextText` 逐块裁，无总预算。新增 `assemblePrompt(blocks, budgetTokens)`：按优先级（执行卡 > 状态表 > 事实账本 > 演绎简报 > 债务 > 范文 > 历史快照）依次装入，按 `字数×0.7` 粗估 token，超出即从低优先级裁。
2. 非玄幻起草 `maxTokens:2200` 对“2000–3000 字”目标偏紧（3000 汉字约 2000–2400 token），改为按目标字数动态 `Math.ceil(targetChars*0.9)+300`，并在审计 `contentLength` 偏离 ±20% 时给出“被截断”专门提示。
3. 双稿择优不再仅限前 3 章：`styleDistance <65` 或 `blocker>0` 时任意章触发，但总次数受作品级配额（`bible.taskConstraints.secondDraftQuota`）限制。
