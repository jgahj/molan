# 拆书到创书一体化优化方案

**项目：** 墨阑 AI 小说创作平台
**方案版本：** 4.1（商业可执行·代码核验版）
**日期：** 2026-08-23
**定位：** 基于当前项目最新实现、前两轮问题审计和 GitHub 案例调研的商业化可执行落地方案

## 1. 方案结论

当前项目已经拥有千万字拆书和创书闭环的核心能力：文本清洗、分片、SQLite 持久化、批次任务、断点续跑、事实抽取、分层摘要、知识图谱、伏笔记录、编辑器章节合同和审计入口。这些领域能力应继续保留，但生产基础设施不能继续以单进程和单机 SQLite 作为最终形态。

商业化版本采用“本地工作台 + 云端平台”双模式：本地模式保留 SQLite，方便个人写作和离线试用；商业生产模式使用多租户、可横向扩展的云原生架构。两种模式共享领域模型、任务协议、提示词版本和质量门禁，避免出现两套业务逻辑。

真正需要升级的是“拆书结果如何可靠地转化为新书”，以及“任务如何在多人、多书、多模型和故障环境下稳定运行”。当前实现更接近“一次生成新书初始结构”，还没有形成独立、可审计、可持续更新、可计费和可恢复的创作平台。因此，本方案将系统改造成下面这条闭环：

```text
原书导入
  -> 稳定文本单元
  -> 全量事实与证据
  -> 实体 / 事件 / 关系 / 时间线 / 伏笔状态
  -> 章节 / 故事弧 / 分卷 / 全书分层摘要
  -> 可迁移规律筛选
  -> 原创迁移简报
  -> creationBible（独立创作圣经）
  -> 分卷规划
  -> 故事弧规划
  -> 章节合同
  -> 场景合同
  -> 场景级正文生成
  -> 事实抽取与多维审计
  -> 定向返工
  -> 人工确认
  -> 提交新书状态快照
```

本方案默认商业目标为多租户 SaaS，同时支持私有化部署；“千万字级别”指单本约 1000 万中文字符，规模化目标扩展到单本 1 亿字符、单个工作区 10 亿字符级 corpus。大规模任务全部异步化、分片化和可恢复化，不把整本原文一次塞进模型上下文，也不把一次长输出当作高质量创作。最终容量必须以固定硬件、固定模型和压测结果为准，而不是以文档中的数字自我宣称。

3.0 版本主要描述目标架构；4.0 版本增加当前实现对齐矩阵、质量优先路径、商业最小路径、规模采用门槛、可运行评测、成本账本和迁移细节。文中的容量与 SLO 均是待验证假设，只有通过对应的 PoC、压测和成本评估后，才能升级为正式承诺。

## 2. 现状、优势与关键缺口

### 2.1 应保留的项目优势

| 现有能力 | 保留原因 | 优化方向 |
| --- | --- | --- |
| Node.js 原生服务和原生 JavaScript | 已积累大量业务能力，迁移成本低 | 逐步迁移到 TypeScript + Fastify 模块化服务；保留现有接口适配层 |
| SQLite、WAL、索引和 FTS5 基础 | 本地模式和离线试用仍有价值 | 生产权威数据迁移到 PostgreSQL；SQLite 作为本地模式、导入缓存和可导出格式 |
| 批次任务和断点续跑 | 千万字处理必须可恢复 | 增加幂等键、心跳、重试和覆盖率门禁 |
| 拆书 Skill 与文风提取能力 | 有利于把风格规则与项目专属设定分离 | 为每条规则附证据和置信度 |
| 章节调用表、动态上下文、知识图谱、伏笔状态 | 已具备创作期状态管理的入口 | 统一接入 `creationBible` 和提交前审计 |
| DeepSeek / OpenAI 兼容调用 | 可按任务选择模型，迁移成本低 | 增加模型路由、缓存、结构化校验和成本记录 |
| 单机任务日志和状态表 | 为领域行为提供了可迁移的原型 | 迁移为 Temporal 工作流、Kafka 事件和可观测性事件 |

### 2.2 当前最影响质量的问题

| 问题 | 直接后果 | 必须采取的方案 |
| --- | --- | --- |
| `buildNovelFromDissection()` 已迁移卷章、portable blueprint、伏笔规划和角色规划，但当前只保存 `title`、`sourceType`、`createdAt` 等本地状态 | 新书没有独立持久化的 `creationBible`、版本和质量状态 | 创建并持久化独立 `creationBible`，新书绑定 `bibleId` |
| `requestChapterContract()`、`requestChapterAudit()`、`refreshDissectionContext()` 通过 `dissectionSourceId()` 读取 `dissectionId`，而当前构书函数没有写入该 ID | 衍生新书会跳过合同和动态上下文；无来源时审计可能返回 `skipped + passed`，造成假通过 | 原书 ID 只作 provenance；合同、审计和上下文必须改读新书 Bible 与状态快照，`skipped` 不能等价于 `passed` |
| `creative-brief` 主要传压缩结构、卖点和模板 | 证据、置信度、未知项、冲突项和不可迁移内容丢失 | 生成带来源引用和边界声明的 portable brief |
| 创书接近一次性 JSON 调用 | 结构、人物、章节、伏笔无法相互校验，失败难以定位 | 简报、分卷、故事弧、章节合同、场景合同分阶段生成 |
| 章节蓝图只有标题、简介和标记 | 正文缺少目标、阻力、信息变化和不可逆结果 | 采用可执行的章节合同和场景合同 |
| 超长正文审计偏向开头 / 中段 / 结尾抽样 | 中间关键矛盾、状态变化和伏笔可能漏检 | 对正文分单元抽取事实，再进行局部语义审计和全局状态比对 |
| 没有原创偏离矩阵 | 可能只改名字，却复刻原书角色功能、冲突顺序和关键事件 | 对人物功能、世界规则、事件因果和节奏结构做显式差异化设计 |
| 失败或异常结果可能被标记为通过 | 用户会误信不完整结果，错误继续污染后续阶段 | 所有验证默认 `needs_review`，只有满足门禁才可 `approved` |
| unitId 规范化、批次覆盖检查、伏笔落库、人物状态、事件边、章节 / 故事弧 / 分卷 / 全书摘要和 `creation-context` 等基础能力已存在 | 这些不再是“从零建设”的 P0，但仍缺独立创书状态、证据账本、版本和评测闭环 | 方案必须区分已完成、部分完成、待验证和新增，不重复安排已完成工作 |

### 2.3 重要边界

原书拆书结果和新书创作状态必须分开：

- `dissectionId`、原书实体、原书事件和原书原文属于溯源区，不能直接成为新书正文上下文。
- 新书必须拥有独立的 `creationBible`、人物状态、时间线、伏笔账本、章节状态和审计记录。
- 只有经过筛选的写作规律、叙事机制和抽象结构可以迁移。
- 原书专属的人名、地名、势力、物品、事件、原句、连续剧情顺序和角色功能组合必须进入禁止复制清单。

### 2.4 当前实现对齐矩阵

| 能力 | 当前代码 / 测试证据 | 当前状态 | 仍需补齐 |
| --- | --- | --- | --- |
| 稳定 `unitId` 与批次覆盖 | `server.js` 的 `normalizeDissectionUnitId()`、覆盖检查；`test/dissection-units.test.js`、`test/dissection-graph.test.js` | 已实现，需持续回归 | 覆盖率指标进入统一评测 runner，记录 pipeline 版本 |

| 多租户和商业账本 | 当前方案有目标表设计，现有代码仍以单用户 / SQLite 为主 | 未落地 | 账户到租户映射、RLS、配额、用量和迁移脚本 |

## 3. 建设目标

### 3.1 产品目标

1. 支持约 1000 万中文字符原书稳定导入、拆分、处理和导出，不静默丢失文本。
2. 让用户能够查看每条重要拆书结论的证据来源、置信度、未知项和冲突项。
3. 一键从拆书结果创建新书，但创建过程必须经过可暂停、可恢复、可审阅的多个阶段。
4. 新书生成的每一章都能够读取截至当前章的长期状态，而不是只依赖最近几章文本。
5. 生成后自动检查合同、人物、关系、时间线、伏笔、文风和原创偏离，失败时只返工受影响部分。
6. 允许用户在关键节点修改创作圣经，后续章节能读取最新版本并保留修订历史。
7. 支持多租户、团队协作、角色权限、项目配额、用量计量和订阅 / 充值计费。
8. 支持 1000 万字符单书稳定运行，并通过水平扩展逐步支持 1 亿字符单书和 10 亿字符工作区 corpus。
9. 大文件支持断点上传、跨服务处理、索引重建、模型故障转移和任务人工恢复。
10. 对外提供版本化 API，对内通过领域事件和工作流解耦拆书、检索、创书和审计。

### 3.2 质量目标

下表是首版验收目标，应通过项目黄金测试集校准，而不是直接用模型自评替代人工标注。

| 指标 | 首版目标 | 说明 |
| --- | --- | --- |
| 文本单元覆盖率 | 100% | 每个输入单元必须有处理状态和最终结果 |
| 已完成单元事实覆盖率 | >= 99% | 不允许只返回部分单元却标记整批成功 |
| 重要结论证据可追溯率 | >= 95% | 能定位到 `unitId`、字符区间或可复核摘要 |
| 关键人物别名消歧 F1 | >= 0.90 | 低置信度结果进入复核队列 |
| 关键事件定位准确率 | >= 0.90 | 支持按章节范围回查 |
| 硬性时间线冲突 | 0 | 出现即阻断提交 |
| 严重人物状态冲突 | 0 | 出现即阻断提交 |
| 章节合同通过率 | >= 90% | 首轮不通过要有结构化原因 |
| 审计后严重错误 | 0 | 允许一般文风问题进入人工修订，不允许严重连续性错误提交 |
| 失败任务恢复率 | 100% | 已完成单元不重复计费，失败单元可重试 |
| 非 AI API 可用性 | >= 99.9% | 不包含第三方模型自身不可用 |
| 任务状态持久化成功率 | >= 99.99% | 任务状态以数据库和工作流检查点为准 |
| 任务提交接口 P95 | <= 500 ms | 只负责创建异步任务，不同步等待模型完成 |
| 进度可见延迟 | <= 5 s | 用户看到的阶段和进度不能长时间滞后 |
| 重复计费率 | 0 | 同一幂等任务不能重复扣费 |
| 商业容量 | 以压测门槛为准 | 至少覆盖 100 个并发重任务和 1 亿字符单书分阶段处理 |
| 灾备 RPO / RTO | RPO <= 5 min，RTO <= 30 min | 生产环境目标，需通过演练验证 |

### 3.3 性能和成本目标

1. 任何阶段都不要求单次请求携带整本原文。
2. 单元任务使用稳定幂等键，重复运行只重算变更版本或失败任务。
3. 高成本模型只处理低置信度实体、跨章节冲突、全书聚合和严重审计问题。
4. 前端按需加载长结果，不能把千万字结果一次性注入页面。
5. 生产任务使用持久化工作流和弹性 Worker；本地 SQLite 模式与生产 PostgreSQL 模式共享领域协议。
6. 派生索引允许异步重建，权威数据、原始文件和不可替代的创作版本必须具备备份和恢复能力。

### 3.4 非目标

- 不因为追求规模而把每个函数拆成独立微服务；服务边界必须围绕领域、吞吐和故障隔离划分。
- 不训练专用大模型，也不把微调作为解决长文本一致性的首要方案。
- 不把原书全文、整本拆书 JSON 或原书连续剧情顺序直接拼进新书提示词。
- 不以“模型返回 JSON”作为质量证明。
- 不把派生搜索索引或图数据库当作唯一事实源。
- 不允许单一模型供应商、单一云厂商或单一队列实现成为不可替换的硬依赖。

## 4. 推荐技术栈（商业化生产版）

### 4.1 总体选型

| 层级 | 推荐技术 | 选择理由 |
| --- | --- | --- |
| Web 产品 | Next.js + React + TypeScript + TanStack Query | 支持商业控制台、任务进度、权限和按需加载；新模块类型安全 |
| 编辑器 | Tiptap / ProseMirror | 保留结构化章节、场景和批注能力，便于审阅和版本 diff |
| 实时协作（可选） | Yjs + Hocuspocus 或等价协作服务 | 只有明确需要多人同时改稿时启用，避免把协作状态混入核心事实库 |
| API | TypeScript + Fastify | 高吞吐、schema 驱动、适合从当前 Node 服务渐进迁移 |
| 领域服务 | TypeScript 模块化单体 + 独立 Worker | 先稳定领域契约，再按吞吐和故障域拆服务 |
| 工作流 | Temporal Cloud 或自托管 Temporal | 长任务、重试、定时、人工审核、信号和检查点都有持久语义 |
| 事件总线 | Kafka 或 Redpanda | 支持大规模 fan-out、回放、分区扩展和跨服务事件解耦 |
| 生产数据库 | 托管 PostgreSQL | 权威保存租户、项目、事实、状态、版本、计费和审计数据 |
| 原始文件与中间产物 | S3 兼容对象存储 | 大文件直传、分片上传、生命周期、版本和跨区域复制 |
| 全文 / 向量检索 | OpenSearch | 支持中文全文、过滤、向量和混合检索；索引可从权威库重建 |
| 图谱投影 | Neo4j Aura / 自托管 Neo4j（按需） | 支持多跳关系查询；只做派生投影，不承担唯一事实源职责 |
| 缓存与临时协调 | Redis 或 Valkey | 限流、短期缓存、幂等窗口和租约；不保存不可恢复业务状态 |
| 模型网关 | 自研 TypeScript Model Gateway | 统一模型路由、预算、重试、fallback、缓存、审计和供应商适配 |
| 结构化输出 | JSON Schema + Ajv / TypeBox | API、事件和模型输出共享契约，降低跨服务解析差异 |
| 容器与弹性 | Docker + Kubernetes + Helm + KEDA | 按队列积压和工作流负载扩缩不同 Worker 池 |
| 观测 | OpenTelemetry + Prometheus + Grafana + Loki + Sentry | 关联请求、工作流、模型调用、成本和用户可见错误 |
| CI/CD | GitHub Actions + Terraform + Argo CD 或等价方案 | 基础设施、迁移、应用和回滚可审计 |
| 测试 | Node `node:test` / Vitest + Playwright + k6 | 单元、契约、浏览器流程、压力和容量测试分层执行 |
| 本地模式 | SQLite + 本地对象目录 | 个人离线和开发模式，不能与生产权威库混用 |

### 4.2 数据职责必须分离

| 数据类型 | 权威位置 | 派生位置 | 原则 |
| --- | --- | --- | --- |
| 租户、项目、任务、状态和版本 | PostgreSQL | Redis 缓存 | Redis 丢失后可以从 PostgreSQL 恢复 |
| 原书原文、章节正文、导出包 | S3 兼容对象存储 | CDN / 临时缓存 | 数据库只保存 URI、哈希、大小和权限元数据 |
| 事实、实体、关系、伏笔和审计 | PostgreSQL | OpenSearch / Neo4j | 所有索引都必须可重建 |
| 关键词、向量和证据检索 | OpenSearch | 无 | 记录 embedding、分词和索引版本 |
| 运行事件 | Kafka 长期保留策略 + 对象存储归档 | ClickHouse（可选） | 业务状态不能依赖日志查询才能恢复 |
| 模型调用与用量 | PostgreSQL 用量账本 | ClickHouse / BI | 计费以不可变账本为准，报表允许最终一致 |

### 4.3 商业化部署原则

1. **权威库与派生库分离：** PostgreSQL 和对象存储保存不可替代数据，OpenSearch、Neo4j、缓存和报表可以删除后重建。
2. **控制面与数据面分离：** 控制面管理租户、权限、配额、计费和工作流；数据面处理具体拆书、检索、生成和审计。
3. **按领域拆 Worker：** 导入、抽取、消歧、聚合、索引、规划、生成和审计使用独立队列和并发上限。
4. **按租户做资源隔离：** 每个任务携带 `tenantId`、`projectId`、`workflowId`，大客户可以绑定专用 Worker 池或专用数据库分区。
5. **所有外部调用可替换：** 模型、对象存储、搜索、支付和身份提供商都通过接口适配，不把供应商 SDK 直接散落到业务代码。
6. **本地和云端共享契约：** SQLite 只替换存储适配器，不能产生另一套字段、状态或提示词语义。

### 4.4 模型网关与模型路由

| 阶段 | 默认模型级别 | 原因 |
| --- | --- | --- |
| 编码、清洗、分片、哈希、统计 | 本地规则 | 确定性强，零模型成本 |
| 单元摘要和事实抽取 | 快速模型 | 任务量大、字段稳定 |
| 实体别名候选 | 快速模型 + 规则 | 先缩小候选集合 |
| 实体消歧、事件合并、伏笔判断 | 强模型 | 需要跨单元语义判断 |
| 分层摘要和全书结构 | 强模型 | 需要综合多个局部结果 |
| 章节 / 场景合同 | 强模型或高质量模型 | 直接约束后续正文 |
| 正文初稿 | 按用户选择的创作模型 | 读取合同和状态，不负责规划全书 |
| 严重问题审计与返工 | 强模型 | 返工错误的代价高于初稿节省的成本 |

模型网关必须提供以下能力：

- 供应商适配：DeepSeek、OpenAI 兼容接口、其他商业模型和本地模型统一为同一协议；
- 路由策略：按任务质量、延迟、价格、地区和租户策略选择模型；
- 故障转移：超时、限流、5xx 和内容不合格时按策略切换备用模型；
- 预算控制：任务级、章节级、租户级 token / 金额预算，超预算进入暂停或人工确认；
- 结果缓存：按输入哈希、提示词版本、schema 版本、模型版本和温度生成缓存键；
- 安全和审计：记录请求引用而不是无限复制原文，保存模型、版本、耗时、token、价格、状态和输出哈希；
- 批量与流式：抽取任务支持批量，正文和进度支持流式，二者不能共用无界队列。

所有模型调用都必须记录 `tenantId`、`workflowId`、`model`、`promptVersion`、`schemaVersion`、输入引用、输出哈希、耗时、token、费用估算和重试次数。

### 4.5 引入节奏

| 能力 | 本地模式 | 商业生产模式 | 升级收益 |
| --- | --- | --- | --- |
| 数据库 | SQLite | PostgreSQL 集群 / 托管 PostgreSQL | 多实例并发、事务、备份和水平读扩展 |
| 文件 | 本地目录 | S3 兼容对象存储 | 分片上传、生命周期和大文件容量 |
| 任务 | 进程内任务 | Temporal + Kafka + Worker | 长任务恢复、回放、扩缩和人工节点 |
| 检索 | FTS5 | OpenSearch + 可选 Neo4j | 混合检索、多租户和大 corpus 查询 |
| 缓存 | 进程内 / SQLite | Redis / Valkey | 跨实例限流、缓存和短期协调 |
| 部署 | Node 进程 | Docker + Kubernetes | 灰度发布、自动扩缩和故障隔离 |

不是所有用户都必须使用商业生产模式，但所有新功能都必须先定义跨模式的领域协议。

### 4.6 三档部署与采用门槛

商业目标不等于首日部署全部基础设施。采用以下三档，按真实指标升级：

| 档位 | 适用阶段 | 必备组件 | 暂不引入 | 升级条件 |
| --- | --- | --- | --- | --- |
| Q：质量工作台 | 当前单机 / 小团队验证 | 当前 Node + SQLite、`creationBible`、评测 runner、成本账本、结构化审计 | Kafka、Neo4j、Kubernetes | 质量指标和单任务成本稳定，真实用户开始持续使用 |
| C：商业最小平台 | 首批付费用户和团队协作 | PostgreSQL、S3、模型网关、持久 Worker、Redis/Valkey、OpenTelemetry、租户 / 配额 / 账本 | Kafka、Neo4j、复杂多区域 | 单机队列、SQLite 写入或索引查询达到明确瓶颈 |
| S：规模平台 | 多租户高并发和大 corpus | Temporal、Kafka/Redpanda、OpenSearch、Kubernetes/KEDA、按需 Neo4j、灾备 | 无 | PoC 证明吞吐、成本和运维收益大于复杂度 |

每个组件引入前必须有四项记录：基准负载、PoC 结果、月度固定成本、故障恢复演练。没有这四项证据时，技术只能写成候选，不得写成上线依赖。

## 5. 目标架构和数据流

### 5.1 六个边界

1. **输入边界：** 原文只在拆书区处理，建立稳定 `unitId` 和字符偏移。
2. **证据边界：** 任何事实、关系、设定和伏笔判断都必须带来源和置信度。
3. **迁移边界：** 只把抽象规律迁移到 portable creative brief，原书专属内容进入禁止区。
4. **创作边界：** 新书只读取自己的 `creationBible` 和状态快照。
5. **审计边界：** 未通过审计的正文不能更新正式人物、时间线和伏笔状态。
6. **发布边界：** 只有人工确认或满足自动门禁的章节才能进入 `committed` 状态。

### 5.2 核心流水线

```text
DissectionRun
  -> DissectionUnit
  -> Claims + Entities + Events + Relations + Foreshadows
  -> HierarchicalSummaries + Timeline
  -> PortableCreativeBrief
  -> CreationBible
  -> VolumePlan + ArcPlan + ChapterContract + SceneContract
  -> Draft
  -> ExtractedFacts + AuditReports
  -> RevisionTask
  -> HumanApproval
  -> BookStateSnapshot
```

### 5.3 任务状态

建议统一使用可解释的状态，而不是用一个 `completed` 表示所有情况：

```text
draft
queued
running
partially_completed
needs_retry
needs_review
needs_rebase
approved
generating
audit_failed
revision_required
committed
legacy_completed
cancelled
```

状态转换必须带 `reason`、`runVersion`、`actor`、`createdAt` 和相关证据。`legacy_completed` 只表示旧链路结束，`not_run` 审计只能进入 `needs_review`；任何异常、空结果、覆盖率不足、版本冲突或审计未执行都不能自动转换为 `approved`。

### 5.4 商业化生产架构

```text
Web / CLI / Open API
        |
API Gateway + OIDC + Tenant / Quota / Billing
        |
TypeScript Application Services
  Catalog | Dissection | Creation | Review | Usage
        |
Temporal Workflows <--> Kafka / Redpanda Event Bus
        |
+------------------- Worker Pools -------------------+
| ingest | unitize | extract | resolve | aggregate   |
| index  | plan    | generate| audit   | export      |
+----------------------------------------------------+
        |
+-------------------- Data Plane --------------------+
| PostgreSQL: authoritative state, facts, versions   |
| S3: source files, drafts, artifacts, snapshots      |
| OpenSearch: lexical / vector / evidence retrieval  |
| Neo4j: rebuildable graph projection                 |
| Redis/Valkey: cache, rate limit, short leases       |
+----------------------------------------------------+
        |
OpenTelemetry -> Metrics / Logs / Traces / Cost BI
```

关键调用原则：

1. 文件通过签名 URL 直接上传对象存储，API 不接收千万字正文作为单个请求体。
2. API 只创建任务和返回 `workflowId`，Temporal 负责长流程，Kafka 负责可回放事件。
3. 每个 Worker 都是无状态容器，状态写入 PostgreSQL / 对象存储，依据队列积压自动扩缩。
4. 搜索和图谱是异步投影；投影滞后时界面显示索引版本和一致性状态，不能伪装为最新。
5. 大租户可以绑定专用队列、模型预算和 Worker 池，防止 noisy neighbor 影响普通用户。

### 5.5 事件和工作流契约

事件使用 JSON Schema 或 Avro 版本化，至少包含：

```json
{
  "eventId": "evt_xxx",
  "eventType": "dissection.unit.completed",
  "eventVersion": 1,
  "tenantId": "tenant_xxx",
  "projectId": "project_xxx",
  "workflowId": "wf_xxx",
  "aggregateId": "run_xxx",
  "idempotencyKey": "run_xxx:extract:unit_xxx:v4",
  "occurredAt": "2026-08-23T00:00:00Z",
  "payloadRef": "s3://bucket/artifacts/evt_xxx.json"
}
```

使用事务 outbox 保证“数据库状态提交”和“事件发布”不会一边成功、一边丢失。Kafka 使用至少一次投递；业务层通过幂等键、唯一约束和结果哈希实现实际效果上的一次处理。Temporal 工作流负责超时、重试、补偿、人工信号和检查点，不把跨服务流程写成无法恢复的 Promise 链。

## 6. 数据模型设计

商业生产模式以 PostgreSQL 为权威数据库，S3 兼容对象存储保存原文和大体积产物，OpenSearch / Neo4j 只保存可重建投影。本地模式继续使用 SQLite，但必须通过存储适配器共享相同的领域接口。每张表和每个事件都应有 `schemaVersion` 或迁移编号，保证旧拆书结果可以逐步升级。

### 6.0 商业化数据分层

| 层级 | 内容 | 存储建议 | 保留策略 |
| --- | --- | --- | --- |
| L0 原始层 | 原书文件、清洗文本、用户正文 | S3 版本对象 | 用户可配置，默认长期保留 |
| L1 单元层 | 单元边界、哈希、偏移、处理状态 | PostgreSQL + S3 内容引用 | 永久保留元数据，内容按套餐保留 |
| L2 事实层 | claims、实体、事件、关系、伏笔和证据 | PostgreSQL 分区表 | 版本化，不覆盖历史 |
| L3 检索层 | 倒排索引、向量、图投影 | OpenSearch + Neo4j | 可删除重建，记录索引版本 |
| L4 创作层 | Bible、合同、正文版本、状态快照 | PostgreSQL + S3 | 用户版本永久可回溯 |
| L5 运营层 | 任务事件、模型调用、用量账本、审计日志 | PostgreSQL + Kafka + 归档库 | 计费和合规所需时长内不可篡改 |

千万字以上的正文和证据不要直接塞进 PostgreSQL 行内。数据库保存 `contentRef`、哈希、长度、压缩方式和权限元数据；只有小型查询字段、结构化事实和当前工作集保存在行内。

### 6.1 拆书域

#### `dissection_runs`

记录一次原书拆解运行：

```text
id, source_book_id, input_hash, cleaned_hash, pipeline_version,
prompt_version, status, total_units, completed_units,
coverage_ratio, evidence_ratio, tenant_id, project_id,
source_object_key, created_by, created_at, updated_at
```

#### `dissection_units`

统一章节、段落和场景输入，避免只支持 `chapter-*`：

```text
id, run_id, tenant_id, unit_type, parent_id, ordinal, title,
source_start, source_end, content_hash, content_ref, preview_text,
content_size, status, attempt_count, last_error,
pipeline_version, created_at, updated_at
```

`id` 必须由稳定的 `runId + ordinal + contentHash` 或等价方案生成，重试不能改变。模型返回结果必须引用 `unitId`，不能只使用章节标题。

#### `dissection_claims`

每条事实或判断至少保存：

```text
id, run_id, tenant_id, unit_id, claim_type, subject_id, predicate, object_value,
evidence_text, evidence_start, evidence_end, confidence,
status, source_model, prompt_version, extraction_version,
valid_from, valid_to, supersedes_id, source_unit_id, state_version,
created_at
```

其中 `status` 至少区分 `candidate`、`verified`、`conflict`、`rejected`、`unknown`。

#### 实体、事件、关系和状态

建议逐步完善以下表：

- `dissection_entities`：规范实体、实体类型和别名。
- `dissection_mentions`：实体在单元中的出现位置和上下文。
- `dissection_events`：事件、参与者、地点、时间和因果关系。
- `dissection_relations`：人物关系或实体关系，以及发生范围。
- `dissection_entity_states`：实体在章节范围内的状态变化。
- `dissection_summaries`：章节、故事弧、分卷和全书摘要。

涉及状态演化的事实应增加以下字段，保留历史而不是覆盖旧值：

```text
valid_from, valid_to, supersedes_id, source_unit_id, state_version
```

这吸收 Graphiti 的时间有效期和事实替代思想；生产环境由 PostgreSQL 事务和分区表承载，本地模式再映射到 SQLite。

#### `dissection_foreshadows`

伏笔至少包含：

```text
id, run_id, key, setup_unit_id, setup_evidence,
expected_payoff, payoff_unit_id, status, confidence,
related_entity_ids, supersedes_id, created_at, updated_at
```

状态建议使用 `seeded`、`reinforced`、`misdirected`、`paid_off`、`open`、`abandoned`、`conflict`，禁止把“未找到回收”自动标为已回收。

### 6.2 创书域

#### `creation_books`

```text
id, tenant_id, project_id, title, bible_id, source_brief_id, status,
current_chapter, current_state_version, visibility, created_by,
created_at, updated_at
```

`source_brief_id` 用于查看迁移来源；正文生成不直接读取原书 `dissectionId`。

#### `creation_bibles`

这是当前系统最关键的新增实体。它是新书自己的、可版本化的创作约束和状态入口：

```json
{
  "schemaVersion": "2.0",
  "bibleId": "bible_xxx",
  "version": 1,
  "provenance": {
    "sourceDissectionId": "dissection_xxx",
    "sourceRunVersion": "run_v3",
    "derivedBriefId": "brief_xxx",
    "originalContentExcluded": true
  },
  "taskConstraints": {
    "genre": "用户指定类型",
    "audience": "目标读者",
    "targetLength": "目标字数",
    "ratingAndTaboos": [],
    "outputLanguage": "zh-CN"
  },
  "styleProfile": {
    "rules": [],
    "evidenceRefs": [],
    "confidence": 0.0,
    "unknowns": []
  },
  "craftConstraints": {
    "pacingRules": [],
    "conflictEscalation": [],
    "chapterCadence": [],
    "rewardCadence": []
  },
  "forbiddenCopy": {
    "entities": [],
    "events": [],
    "quotedText": [],
    "sequencePatterns": [],
    "roleCombinations": []
  },
  "divergenceMatrix": [],
  "bookPremise": {},
  "worldRules": [],
  "characters": [],
  "antagonists": [],
  "volumePlan": [],
  "arcPlan": [],
  "chapterContracts": [],
  "foreshadowLedger": [],
  "timeline": [],
  "revisionMemory": [],
  "qualityState": {
    "status": "draft",
    "blockingIssues": [],
    "lastAuditId": null,
    "stateVersion": 1
  }
}
```

`creationBible` 中的每一项都要标记 `source`（用户输入、迁移规律、原创设计或审计修订）和 `confidence`。用户修改后创建新版本，已提交章节保留当时使用的版本号。

**首版 Bible 的 seed 映射（从当前创意简报新书迁移，避免从零开始）：**

| 当前 `pages/editor.js` 状态字段 | 首版 Bible 字段 | 处理 |
| --- | --- | --- |
| `outline.portableBlueprint` | `styleProfile + craftConstraints + taskConstraints` | 直接迁入，标记 `source: migration` |
| `outline.volumePlan` | `volumePlan` | 迁入并保留原文，后续可按分卷细化 |
| `state.foreshadows`（`planted/developing/...`） | `foreshadowLedger` | 逐条迁入，补 `confidence` 与 `source` |
| `state.knowledge.entities` | `characters + worldRules` | 角色 / 设定实体迁入，`attrs` 转为 `characters[].traits` |
| `creative-brief` 的 `forbiddenCopy` | `forbiddenCopy` | 原样迁入，作为首版禁止复制清单 |
| `outline.chapters[].synopsis` | `chapterContracts[].goal` | 首版合同只有目标，其余字段按 8.4 规划补全 |

seed 生成的 Bible 版本号为 1，`changeSummary` 固定为「由创意简报迁移的首版」；此后所有用户修订与审计修订都走新版本，历史章节保留其 `bibleVersion`。

商业模式不要直接覆盖 `creation_bibles` 的 JSON。建议拆成身份表和不可变版本表：

```text
creation_bibles:
  id, tenant_id, book_id, current_version, status, created_at, updated_at

creation_bible_versions:
  id, bible_id, version, payload_json_or_ref, payload_hash,
  source_brief_id, parent_version, change_summary, approved_by,
  created_by, created_at
```

大版本存对象存储，小型检索字段可冗余到 PostgreSQL JSONB；通过 `payload_hash` 确保章节可以复现当时使用的圣经。

#### `creation_state_snapshots`

保存每章提交后的可恢复状态：

```text
tenant_id, book_id, chapter_no, bible_version, state_version,
character_states, relationship_states, world_states,
timeline_state, open_foreshadows, recent_facts,
content_ref, content_hash, audit_status, workflow_id, created_at
```

#### `creation_audits` 和 `revision_tasks`

审计结果必须可追溯、可复现：

```text
audit_id, tenant_id, book_id, chapter_no, audit_type, severity,
finding, evidence, expected, actual, status,
model, prompt_version, schema_version, workflow_id, cost_units,
created_at
```

返工任务保存受影响的章节、场景、状态版本、允许修改范围和重新审计条件，避免每次失败都重写整章。

#### 商业运营与任务表

```text
tenants:
  id, plan_id, status, region, data_policy, created_at

projects:
  id, tenant_id, quota_policy_id, storage_policy, search_policy, created_at

memberships:
  tenant_id, user_id, role, permissions, created_at

workflow_runs:
  id, tenant_id, project_id, workflow_type, aggregate_id,
  status, idempotency_key, temporal_run_id, retry_count,
  input_hash, pipeline_version, started_at, finished_at

usage_ledger:
  id, tenant_id, project_id, workflow_id, meter_type,
  quantity, unit_price, currency, idempotency_key, status, created_at

outbox_events:
  id, aggregate_id, event_type, event_version, payload_ref,
  publish_status, attempt_count, created_at

index_versions:
  id, tenant_id, source_revision, index_type, model_version,
  status, document_count, error_count, created_at

model_usage:
  request_id, tenant_id, project_id, workflow_id, stage, unit_id,
  model, prompt_version, input_tokens, output_tokens,
  cached_input_tokens, retry_count, latency_ms,
  price_input, price_output, estimated_cost, status, created_at

deletion_jobs:
  id, tenant_id, project_id, scope, requested_by, policy_version,
  status, completed_steps, failed_steps, proof_ref, created_at, finished_at
```

所有商业表必须带 `tenant_id` 或能通过项目稳定关联租户。PostgreSQL 使用 RLS 作为第二道隔离，应用层权限校验不能作为唯一隔离手段。计费使用不可变用量账本，退款、冲正和赠送额度用反向流水表示，不修改历史账目。

### 6.3 证据账本和可追溯指标

`claims.evidence_text` 只能作为短摘录或展示缓存，不能替代独立证据账本。建议增加：

```text
evidence_ledger:
  id, tenant_id, run_id, claim_id, source_unit_id,
  source_object_key, start_offset, end_offset, excerpt_hash,
  evidence_type, extraction_version, confidence,
  verification_status, verified_by, created_at
```

“重要结论”按业务规则定义，而不是由模型自由决定。首版可将以下类型全部视为重要：人物生死 / 身份 / 关系变化，世界硬规则，关键事件及因果，伏笔埋设 / 回收，时间线锚点，分卷和全书转折，进入 `creationBible` 的任何规则。

指标定义：

```text
evidence_traceability
  = 有有效 source_unit_id + 合法偏移 + excerpt_hash 的重要结论数
    / 重要结论总数

evidence_coverage
  = 有 evidence_ledger 记录的重要结论数 / 重要结论总数

evidence_accuracy
  = 经人工黄金集确认正确的重要结论数 / 抽样重要结论总数
```

统计时保存分子、分母、抽样规则、pipelineVersion 和样本 ID，不能只保存一个模型生成的百分比。

### 6.4 Bible、状态和生成任务的并发语义

所有生成任务在启动时固定以下读取版本：

```text
bibleVersion
baseStateVersion
baseChapterRevision
promptVersion
modelVersion
```

正文先写入不可提交的 `draft_revision` 或对象存储产物，不直接修改正式知识图谱、伏笔和人物状态。提交使用乐观并发条件：

```sql
UPDATE creation_books
SET current_state_version = :nextVersion,
    current_chapter = :chapterNo
WHERE id = :bookId
  AND current_state_version = :baseStateVersion;
```

影响行数为 0 时，任务进入 `needs_rebase`，不能覆盖新状态；用户可以选择重新基于最新状态生成，或把草稿作为分支保留。默认相邻章节串行提交；只有互不依赖的规划任务或明确分支才允许并行。Bible 修改生成新版本，已经启动的任务继续使用旧版本，未启动任务读取新版本。

## 7. 千万字拆书如何实现

### 7.1 导入和单元切分

1. 读取 TXT、MD、DOCX、EPUB 等输入，统一编码、换行和确定性噪声。
2. 保存原文哈希、清洗后哈希、导入版本和字符偏移映射。
3. 优先识别章节标题；标题缺失时按段落和稳定字符窗口生成 `segment` 单元。
4. 过长章节切成带 `parentId` 的子单元，保留顺序和重叠边界。
5. 导入结束先生成完整单元清单，再开始模型任务。
6. 处理结束计算 `totalUnits`、`completedUnits`、失败单元、空结果和覆盖率。

硬性规则：单元数量为零、单元内容哈希不连续、字符区间重叠异常或存在未处理单元时，运行状态只能是 `needs_review` 或 `needs_retry`。

### 7.2 单元事实抽取

每个单元使用固定 schema 输出：

- 发生了什么；
- 哪些人物、地点、物品和势力出现；
- 人物目标、情绪、关系和状态变化；
- 新增或修改的世界规则；
- 时间、空间和因果信息；
- 伏笔埋设、强化、误导或回收；
- 不确定内容、冲突内容和证据片段。

返回后执行四层校验：

1. JSON 语法和字段类型校验。
2. 所有引用的 `unitId` 必须属于当前批次。
3. 关键字段的证据区间必须落在当前单元范围内。
4. 当前批次的输入单元必须全部有成功、失败或待复核结果。

数组不为空不代表成功。必须检查批次覆盖率和每条重要结论的证据完整性。

### 7.3 实体消歧和事实合并

采用“规则候选 + 模型复核 + 可回滚合并”：

1. 先用规范化、别名、共同出现窗口和章节距离生成候选。
2. 高置信度同名实体可以自动合并。
3. 低置信度或可能同名不同人的候选进入强模型复核。
4. 合并必须记录原实体、合并原因和证据；禁止依赖描述前缀做唯一判断。
5. 新事实不覆盖旧事实，使用 `valid_to`、`supersedes_id` 和 `state_version` 表示演化。

### 7.4 分层摘要和混合检索

推荐采用：

```text
单元事实 / 证据
  -> 章节摘要
  -> 故事弧摘要
  -> 分卷摘要
  -> 全书摘要
```

查询时混合使用：

- 本地模式使用 FTS5，商业模式使用 OpenSearch 中文倒排检索；
- 向量相似度检索，必须绑定 embedding 模型和索引版本；
- 实体和关系过滤；
- 时间范围过滤；
- 章节范围过滤；
- 分层摘要；
- 低置信度冲突列表。

商业模式由 PostgreSQL 保存事实，OpenSearch 保存关键词 / 向量检索，Neo4j 保存可重建的多跳关系投影。查询服务必须返回 `sourceRevision`、`indexVersion` 和证据引用，索引延迟或版本不一致时显示为 `stale`，不能把最终一致性伪装成实时一致。

### 7.5 规模化处理策略

#### A. 上传和预处理

1. 使用对象存储分片上传、断点续传和校验哈希，避免 API 服务器成为带宽瓶颈。
2. 预处理 Worker 只负责解压、编码识别、清洗、章节识别和单元清单，不调用模型。
3. 单元内容保存到对象存储，数据库保存偏移、哈希和 URI；重复文件按哈希去重。
4. 任何处理版本变化都生成新的 `pipelineVersion`，旧结果保持可读和可回放。

#### B. Fan-out / Fan-in

```text
一个 DissectionWorkflow
  -> 按章节 / 单元 fan-out
  -> 多个 ExtractTask 并行
  -> EntityResolveTask / EventMergeTask
  -> 按章节、故事弧、分卷 fan-in
  -> 全书聚合与质量门禁
```

每个任务使用 `tenantId:runId:stage:unitId:version` 作为幂等键，采用有限并发和租户公平调度。Kafka 至少一次投递、Temporal 可重试，但数据库唯一约束和输出哈希必须阻止重复写入和重复扣费。

#### C. 背压和资源池

- 为低成本抽取、强模型复核、正文生成、审计和索引建立独立队列。
- 以租户配额、模型供应商限流、GPU / CPU、队列年龄和失败率作为扩缩容指标。
- 普通租户共享资源池，大客户可购买专用队列和专用 Worker 池。
- 当模型供应商限流时暂停低优先级任务，保留已经完成的中间产物，不级联失败全书任务。
- 对每个阶段设置最大重试次数、死信队列和人工恢复入口。

#### D. 规模分层

| 级别 | 输入目标 | 运行方式 | 资源策略 |
| --- | --- | --- | --- |
| S | <= 1000 万字符 / 本 | 共享集群异步处理 | 默认队列、标准模型预算 |
| M | <= 1 亿字符 / 本 | 分片 fan-out、分层聚合 | 增加并发和专用索引分片 |
| L | <= 10 亿字符 / 工作区 | 多运行、多版本、跨索引分区 | 大租户专用资源和分阶段归档 |

这里的规模目标是容量设计边界，不代表模型会一次读取同等规模文本。单元、证据、状态和摘要必须始终可分页、可回放、可重建。

### 7.6 Token、成本和预算模型

每个模型请求都写入 `model_usage`，至少包含：

```text
request_id, tenant_id, workflow_id, stage, unit_id,
model, prompt_version, input_tokens, output_tokens,
cached_input_tokens, retry_count, latency_ms,
price_input, price_output, estimated_cost, status, created_at
```

单次请求成本按实际供应商价格计算：

```text
request_cost =
  (input_tokens - cached_input_tokens) * input_price / 1,000,000
  + cached_input_tokens * cached_input_price / 1,000,000
  + output_tokens * output_price / 1,000,000
  + embedding_cost
  + retry_cost
```

单本任务成本：

```text
book_cost = sum(request_cost)
  + object_storage_cost
  + search_index_cost
  + compute_cost
  + payment_or_platform_fee
```

估算必须按阶段拆开：单元抽取、实体消歧、事件 / 伏笔合并、分层摘要、创作规划、正文生成、审计和返工。至少输出“每 1 万字、每 100 万字、每 1000 万字”的成本区间，不使用单一乐观值。

当前已知的整书运行数据（1647 章、436 批、34480 claims、约 7 小时）应作为 `observed baseline` 写入运行报告，但在补齐输入 / 输出 token、请求数、重试数、失败数、缓存命中率和实际价格前，不得直接外推成本或 SLA。

预算控制规则：

1. 任务创建时根据字符数、阶段、模型路由和历史倍率生成预估成本。
2. 预计成本达到用户预算的 80% 时发出警告，达到 100% 时暂停新增模型调用。
3. 单阶段重试成本超过该阶段预算的 20% 时转入 `needs_review`，禁止无限重试。
4. 实际账本以供应商返回 token 为准；估算和实际差异超过 10% 时记录校准任务。
5. 缓存命中、失败请求和返工都必须进入账本，不能用“成功章节数”替代真实成本。

**账本采集点（当前代码落点）：**

| 采集点 | 说明 |
| --- | --- |
| `callMolanChat()` / `runDissectionChat()`（`server.js`） | 拆书、聚合、合同、审计所有模型请求都经此中转，统一在此写入 `model_usage`（token、retry、latency、status） |
| `pipelineChat()`（聚合层） | 分层摘要、人物 / 伏笔合并等聚合调用，补齐 `stage / unit_id / promptVersion` |
| `extractBatchFacts()` | 单元事实抽取，按批次和 `unitId` 记录，包含失败重试与缓存命中 |
| 编辑器正文生成 / 审计（`pages/editor.js`） | `streamChat` / `streamSkillPipeline` / `requestChapterAudit` 的 billing 回调已回传 usage，需统一落到 `model_usage`，带 `creationBookId` |
| 重构 / 重建（`/rebuild`） | 本地规则不产生模型成本，但需记录为零成本项，避免账本缺失被误读 |

每个采集点至少记录：`request_id, tenant_id/project_id(暂缺则 0), workflow_id(暂缺则 task id), stage, model, prompt_version, input/output/cached tokens, retry_count, latency_ms, status, estimated_cost, created_at`。

## 8. 从拆书结果创作高质量新书

### 8.1 第一步：生成 portable creative brief

`creative-brief` 不再只是压缩后的卖点、结构和模板，而应包含：

- 目标类型、读者和篇幅；
- 可迁移的节奏、冲突、奖励和悬念机制；
- 文风规则、统计证据、适用范围和置信度；
- 可迁移的结构抽象；
- 需要用户确认的未知项；
- 互相冲突的分析结论；
- 原书专属内容和禁止复制清单；
- 用户输入的原创方向和硬性限制；
- 每个迁移规律的 `evidenceRefs`。

简报必须通过“可迁移性审计”：如果一条规则同时包含原书人名、专有设定、原句或原书事件序列，则不能直接进入创作上下文。

### 8.2 第二步：建立原创迁移简报和偏离矩阵

偏离矩阵是高质量创书的关键，不是简单改名：

| 原书抽象功能 | 新书实现 | 必须不同的方面 | 验证方式 |
| --- | --- | --- | --- |
| 主角起点困境 | 新主角的具体困境 | 身份、资源、价值观、解决路径 | 角色卡和事件图比对 |
| 核心外部压力 | 新的制度、关系或环境压力 | 压力来源、升级方式、代价 | 冲突链审计 |
| 关键关系张力 | 新角色关系 | 权力结构、交换条件、反转原因 | 关系状态快照 |
| 奖励 / 成长机制 | 新世界中的回报机制 | 规则、成本、节奏、限制 | 世界规则审计 |
| 中段转折功能 | 新事件 | 因果链、地点、人物选择、结果 | 事件图差异检查 |
| 终局揭示功能 | 新谜底或新代价 | 信息来源和价值判断 | 全书结构审计 |

至少要求四类偏离同时成立：人物身份偏离、世界规则偏离、关键事件因果偏离、角色功能组合偏离。不能只替换名字和地点。

### 8.3 第三步：生成 `creationBible`

创作圣经按以下顺序生成：

1. 用户任务约束和原创方向。
2. 可迁移风格与工艺规则。
3. 禁止复制清单和偏离矩阵。
4. 新书 premise、主题和核心问题。
5. 世界规则、资源规则和代价规则。
6. 主角、配角、对手及其目标、缺陷、关系和成长代价。
7. 全书时间线、伏笔策略和质量门禁。

生成后先审计创作圣经，再允许进入分卷规划。任何缺少主角主动目标、主要阻力、代价机制、终局问题或差异化实现的圣经都应停在 `needs_review`。

### 8.4 第四步：分卷、故事弧和章节规划

规划必须从大到小，且每一层都要能回溯上一层目标：

```text
全书主题 / 核心问题
  -> 分卷目标、转折、高潮、终点
  -> 故事弧目标、阻力、升级、结果
  -> 章节目标、行动、信息变化、不可逆结果
  -> 场景目标、冲突、选择、现场结果
```

章节合同至少包含：

```json
{
  "chapterNo": 1,
  "arcId": "arc_01",
  "goal": "本章必须完成的叙事目标",
  "protagonistAction": "主角主动做出的选择",
  "opposition": "具体阻力和阻力来源",
  "informationChange": "谁知道了什么，读者知道了什么",
  "escalation": "冲突如何升级",
  "irreversibleResult": "本章结束后无法恢复的结果",
  "characterStateChanges": [],
  "foreshadowActions": [],
  "continuityInputs": [],
  "continuityOutputs": [],
  "mustAvoid": [],
  "endHook": "章末继续阅读的具体问题或压力"
}
```

场景合同再补充地点、出场角色、视角、当场目标、阻力、选择、信息和退出状态。一场只承担一个主要叙事功能，避免用一条提示词同时完成规划、写作和审计。

### 8.5 第五步：场景级生成

单次正文请求只读取当前需要的工作集：

```text
固定任务约束
+ 当前 creationBible 版本
+ 当前分卷和故事弧摘要
+ 当前人物 / 关系 / 世界状态
+ 当前时间线窗口
+ 未回收伏笔
+ 最近章节结尾事实
+ 当前章节合同
+ 当前场景合同
+ 可迁移文风规则
+ 用户已确认的修订记忆
```

不要将原书全文、原书整本拆书结果或不相关的历史状态发送给正文模型。生成后立即抽取本场景的新事实，等待本章级审计通过后再更新正式快照。

#### 8.5.1 工作集预算和场景协议

工作集使用 tokenizer 计算，不用字符数近似 token。首版可以使用以下相对预算，再通过模型和题材评测调整：

| 工作集部分 | 建议输入预算 | 必须内容 |
| --- | ---: | --- |
| 硬性任务约束 | 500-1000 tokens | 类型、视角、禁区、输出格式 |
| `creationBible` 摘要 | 1500-3000 tokens | premise、世界硬规则、人物核心目标 |
| 当前分卷 / 故事弧 | 1500-3000 tokens | 当前弧目标、阻力、升级和终点 |
| 状态快照 | 1500-3000 tokens | 人物、关系、时间线、开放伏笔 |
| 最近场景和上一章结尾 | 2500-6000 tokens | 直接承接所需的事实与文本 |
| 章节 / 场景合同 | 800-1600 tokens | 目标、阻力、信息变化、不可逆结果 |
| 文风规则 | 500-1500 tokens | 可执行规则和少量授权样本引用 |
| 正文输出 | 独立上限 | 由场景目标和用户字数设定 |

每次调用记录 `budgetPlan`、实际 token、丢弃字段、截断原因和质量结果。若工作集超预算，优先缩减旧摘要和低置信度检索结果，不能删掉硬规则、状态版本、合同和上一场景结果。

#### 8.5.2 场景级生成和提交协议

```text
读取 baseStateVersion / bibleVersion
  -> 编译 bounded working set
  -> 生成场景草稿（仅写 draft_revision）
  -> 抽取场景事实和状态候选
  -> 确定性合同 / 连续性 / 禁止复制检查
  -> 语义审计和质量评分
  -> 失败则创建 revision_task
  -> 通过后 CAS 提交章节版本和 state snapshot
  -> 更新可检索投影
```

流式输出只更新临时草稿和前端 autosave，不更新正式人物状态、伏笔状态、知识图谱或下一章上下文。场景之间通过 `sceneStateDelta` 连接：下一场景读取上一场景的已审计结果，而不是读取未审计的流式文本。章节提交失败时保留草稿和审计报告，不能让半章内容污染正式状态。

### 8.5.3 章节合同确定性验证器

以下字段应先用规则验证，再交给模型判断语义：

| 字段 | 确定性检查 | 语义检查 |
| --- | --- | --- |
| `chapterNo` / `arcId` | 存在、唯一、版本匹配 | 是否位于正确故事弧 |
| `goal` / `protagonistAction` | 非空、长度、至少一个主动动作 | 主角是否真正主动推进 |
| `opposition` | 非空且有阻力来源 | 阻力是否具体、有效 |
| `informationChange` | 至少一条新信息候选 | 信息是否改变读者或人物认知 |
| `irreversibleResult` | 非空且不同于输入状态 | 结果是否真正不可逆 |
| `characterStateChanges` | 实体 ID、字段和旧值存在 | 变化是否由正文证据支持 |
| `foreshadowActions` | 伏笔 ID / 动作枚举合法 | 埋设、强化、误导、回收是否成立 |
| `continuityInputs/Outputs` | 版本和引用存在 | 承接是否自然 |
| `mustAvoid` | 禁止项可匹配 | 正文是否实际违反 |

验证器输出 `passed / failed / not_run / needs_review`，`not_run` 不能自动通过。

### 8.6 第六步：审计、定向返工和提交

正文处理顺序：

1. 格式、长度、场景边界和视角检查。
2. 章节合同履约检查。
3. 人物目标、状态和关系变化检查。
4. 时间线、空间位置和世界规则检查。
5. 伏笔埋设、推进、误导和回收检查。
6. 文风规则和禁用模式检查。
7. 与上一章、当前故事弧和分卷目标的承接检查。
8. 原创偏离矩阵检查。
9. 失败时生成结构化 `revisionTask`，只重写受影响场景。
10. 审计通过或人工确认后，才写入 `creation_state_snapshots`、知识图谱、伏笔账本和章节调用表。

### 8.7 商业化质量服务

高质量不能只依赖生成模型本身，还需要独立的评测和运营闭环：

- 每个租户可以固定模型、文风包、审计严格度和质量预算；
- 平台维护提示词、schema、模型和评估集的版本，禁止静默替换生产版本；
- 生产正文先进入 `draft`，通过结构化审计后才能进入 `committed`；
- 用户接受、拒绝、修改和回滚都写入 `revisionMemory`，但不得未经用户允许直接作为跨租户训练数据；
- 对模型升级做 shadow run / A-B 评估，只替换通过黄金集和容量测试的版本；
- 把“质量分”拆为事实一致性、合同完成度、文风符合度、原创偏离度和人工接受率，不输出一个无法解释的总分。

## 9. 质量闸门和审计规则

### 9.1 审计结果不能默认通过

每个审计器都应返回：

```json
{
  "status": "passed | failed | needs_review | not_run",
  "severity": "info | warning | blocking",
  "findings": [],
  "evidence": [],
  "confidence": 0.0,
  "auditorVersion": "..."
}
```

`not_run`、空输出、引用无效、覆盖率不足和模型异常都不能映射为 `passed`。

### 9.2 结构化审计与模型审计分工

| 审计类型 | 优先实现 | 适合检查的内容 |
| --- | --- | --- |
| 确定性审计 | 规则和 SQL | 章节编号、状态版本、实体 ID、时间区间、必填字段、重复任务 |
| 事实审计 | 抽取结果比对 | 人物状态、关系变化、伏笔状态、世界规则 |
| 语义审计 | 强模型复核 | 合同是否真正完成、动机是否成立、转折是否有效 |
| 风格审计 | Skill + 规则 + 抽样模型 | 句式、节奏、视角和用户纠错偏好 |
| 原创审计 | 结构化差异 + 语义比对 | 禁止复制的实体、事件链、角色功能和连续顺序 |

### 9.3 长正文审计策略

不能只抽取开头、中段和结尾三个窗口。推荐：

1. 以场景为最小审计单元，完整抽取场景事实。
2. 以章节为单位合并状态变化并比对章节合同。
3. 以故事弧为单位检查升级曲线和伏笔回收。
4. 以分卷和全书为单位检查时间线、人物弧和主题闭环。
5. 对高风险章节执行全文语义复核，对普通章节使用结构化事实 + 定向抽样。

### 9.4 最小可用审计器

审计器必须能独立于生成模型运行，至少包含以下确定性规则：

```text
validateChapter(draft, contract, baseState, bible):
  checkRequiredFields(contract)
  checkBibleVersion(contract.bibleVersion)
  checkReferencedEntitiesExist(contract)
  checkChapterAndSceneOrder(draft)
  checkForbiddenTermsAndEntities(draft, bible.forbiddenCopy)
  checkTimelineAndLocationHardRules(draft, baseState)
  checkStateDeltaReferences(draft.extractedFacts, baseState)
  checkForeshadowActionReferences(draft, bible.foreshadowLedger)
  checkNoUncommittedStateMutation(draft)
  return findings
```

确定性审计最低规则清单：

- 合同必填字段、枚举、版本和实体引用合法；
- 章节 / 场景顺序、目标字数、视角和输出结构合法；
- 禁止复制清单中的规范名、别名、原句指纹和高风险术语不出现；
- 已死亡、未获得、未到达或尚未公开的信息不能无证据跳变；
- 角色位置、时间、关系和世界硬规则不能与当前快照冲突；
- 伏笔回收必须有目标伏笔、正文证据和回收结果；
- 生成草稿不能直接写入正式状态，必须经过提交事务。

模型审计只处理动机合理性、张力、信息有效性、文风和真正的伏笔功能，不替代可确定的字段和状态检查。

### 9.5 原创偏离审计

“换名复刻”不能只靠一个相似度分数。建议先做确定性指纹，再对高风险样本调用强模型和人工复核：

| 检查层 | 方法 | 结果用途 |
| --- | --- | --- |
| 禁止实体 | 规范名、别名、模糊匹配、拼写变体 | 命中即 blocking 或人工确认 |
| 原句 / 表达 | 授权原文的 n-gram、MinHash、局部编辑距离 | 命中高相似片段即阻断或重写 |
| 事件链 | 把关键事件转为 `角色功能-动作-阻力-结果` 指纹，比较连续子序列 | 发现顺序复刻和因果复刻 |
| 角色功能图 | 比较角色目标、权力关系、缺陷、交换和成长代价图 | 发现只改姓名的角色复刻 |
| 节奏骨架 | 比较开篇事件、转折位置、高潮类型和回收顺序 | 发现结构模板过度重合 |
| 语义相似 | embedding / 强模型对疑似段落做解释性比对 | 只做风险排序，不单独判定侵权 |

原创审计结果至少返回：

```json
{
  "status": "passed | needs_review | failed",
  "riskLevel": "low | medium | high | blocking",
  "matchedSourceRefs": [],
  "matchedPatterns": [],
  "divergenceFailures": [],
  "explanation": "具体说明重合在实体、因果、角色功能还是节奏骨架"
}
```

偏离矩阵中的每一行必须有可执行的 `sourceRef`、`newImplementationRef`、`differenceDimensions` 和 `checkResult`。模型不能自行宣称“足够原创”；高风险结果必须人工确认。

## 10. 对 GitHub 案例的借鉴与边界

### 10.1 NovelClaw

项目：[iLearn-Lab/NovelClaw](https://github.com/iLearn-Lab/NovelClaw)

借鉴：

- 将 `story_premise`、`style_guide`、`chapter_briefs` 作为分阶段输入。
- 保存 `entity_state`、`relationship_state`、`world_state`、`continuity_facts`。
- 使用 `revision_notes`、`working_set` 和章节级运行日志。
- 每章完成后形成状态快照，便于继续写作和审阅。

边界：

- 不能照搬“评估器异常时默认通过”的风险逻辑。
- 不把 novelty 分数为零的奖励逻辑当作原创性保证。
- 当前项目要把状态和证据落入 SQLite，而不是只依赖运行时对象。

### 10.2 LongWriter

项目：[THUDM/LongWriter](https://github.com/THUDM/LongWriter)

借鉴：

- `plan.py -> write.py` 的规划和写作分离。
- 将长任务拆成场景级或段落级子任务。
- 逐步把已生成结果和必要状态传给后续任务。
- 使用 JSONL / 中间产物缓存和断点恢复，避免失败后全部重算。
- 用幂等任务键控制重复调用。

边界：

- 借鉴其任务拆分和缓存思想，不直接引入训练长输出模型的方案。
- 长输出能力不能替代情节规划、状态审计和人工确认。

### 10.3 GraphRAG

项目：[microsoft/graphrag](https://github.com/microsoft/graphrag)

借鉴：

```text
文本单元
  -> 实体 / 关系 / claims
  -> 社区和分层摘要
  -> 局部检索 / 全局检索
```

这适合解决“局部细节”和“全书结构”同时需要的问题。本地模式可以用 SQLite 关系表、FTS5 和分层摘要降低部署门槛；商业模式使用 PostgreSQL 事实表、OpenSearch 混合检索和按需 Neo4j 图投影。是否启用图谱查询由离线评测和租户套餐决定，但不能让任何派生索引成为唯一事实源。

### 10.4 Graphiti

项目：[getzep/graphiti](https://github.com/getzep/graphiti)

借鉴：

- 事实有效期和时间过滤；
- 新事实替代旧事实但不删除历史；
- 每条关系保留来源和证据；
- 语义、关键词和图关系混合检索。

落地到 SQLite 时优先增加：

```text
valid_from
valid_to
supersedes_id
source_unit_id
state_version
```

### 10.5 LangGraph

项目：[langchain-ai/langgraph](https://github.com/langchain-ai/langgraph)

借鉴：

- 持久化工作流；
- 失败恢复和状态检查点；
- 人工审核节点；
- 可追踪的执行轨迹。

商业生产模式使用 Temporal 作为跨服务、长周期和人工节点的工作流底座；LangGraph.js 如果使用，只放在某个“模型推理节点”内部，不承担平台级任务调度、计费或数据一致性。SQLite 本地模式可以实现同等领域语义，但不能成为云端工作流的唯一恢复机制。

### 10.6 Temporal

项目：[temporalio/temporal](https://github.com/temporalio/temporal)

借鉴：

- 长时间运行工作流的持久检查点；
- Activity 超时、重试、心跳和补偿；
- 通过 Signal / Update 接收人工确认、暂停和修改；
- 工作流历史可回放，便于定位模型、版本和状态问题。

落地边界：

- Temporal 只负责流程编排，不保存原书正文、事实主库或计费账本；
- Activity 必须幂等，所有外部副作用都带 `idempotencyKey`；
- 工作流输入只放引用和版本，不把千万字内容塞进历史事件；
- 大 payload 放对象存储，Temporal history 保存 URI、哈希和状态摘要。

## 11. API、代码落点与实现顺序

### 11.1 建议 API

对外使用 `/api/v1` 版本化接口，保留现有接口适配层，逐步增加以下领域接口。所有写接口支持 `Idempotency-Key`，所有响应带 `requestId`、`tenantId`、`taskId` / `workflowId`、`status` 和版本信息：

```text

GET  /api/v1/dissections/:id/coverage
GET  /api/v1/dissections/:id/evidence
POST /api/v1/creation-books/from-brief
GET  /api/v1/creation-books/:bookId/bible
PUT  /api/v1/creation-books/:bookId/bible
POST /api/v1/creation-books/:bookId/plan
POST /api/v1/creation-books/:bookId/chapters/:chapterNo/generate
POST /api/v1/creation-books/:bookId/chapters/:chapterNo/audit
POST /api/v1/creation-books/:bookId/chapters/:chapterNo/revise
POST /api/v1/creation-books/:bookId/chapters/:chapterNo/commit
GET  /api/v1/creation-books/:bookId/state?chapterNo=...
GET  /api/v1/workflows/:workflowId
POST /api/v1/workflows/:workflowId/pause

GET  /api/v1/workflows/:workflowId/events
```

文件接口返回对象存储的签名上传地址，不让 API 服务器代理大文件。进度使用 SSE / WebSocket 推送，历史进度从事件或数据库查询。长任务使用工作流 ID 查询，不在 HTTP 请求中同步等待完整拆书或整章生成。

### 11.2 当前项目代码落点

- `server.js`：先作为兼容入口；逐步拆为 API、领域服务和 Worker，避免继续扩大单文件职责。
- `apps/api`：认证、租户、项目、拆书、创书、审计和对外 API。
- `apps/workers/`：`ingest`、`extract`、`resolve`、`aggregate`、`index`、`generate`、`audit` 和 `export` 独立 Worker 池。
- `packages/domain`：拆书、创书、状态、质量和计费领域模型。
- `packages/contracts`：JSON Schema、事件、API、工作流输入输出和迁移版本。
- `packages/model-gateway`：模型供应商、路由、预算、缓存、重试和用量计量。
- `packages/storage`：SQLite、PostgreSQL、对象存储、OpenSearch 和 Neo4j 适配器。
- `pages/editor.js`：`buildNovelFromDissection()` 改为创建 `creationBook + creationBible`；章节合同、审计和动态上下文改读新书状态快照。
- `completion-import.js`：增加批次覆盖率、失败单元、未知项和冲突项展示。
- `skills/extract-transform-fiction-style/`：继续负责文风提取，但输出必须带证据、置信度和适用边界。
- `test/`：增加无标题长文本、跨分片、重试幂等、创作圣经隔离、状态提交和审计门禁测试。

推荐使用 pnpm workspace 或等价 monorepo 管理应用和共享包；不要把提示词、schema、数据库迁移和领域常量复制到多个服务。

### 11.3 必须首先修复的链路

按「危险程度 × 依赖程度」排序，审计假通过修复依赖最小、风险最高，列第一：

1. **修复审计假通过（第一优先级，已核验存在）**：将无 `dissectionId` 时 `requestChapterAudit()` 的返回值从 `skipped + passed` 改为 `not_run + needs_review`；新书有 Bible / 状态快照则运行真实审计，无 Bible 则本地确定性审计，缺失则 `needs_review` 且 UI 明示，绝不静默 `passed`。
2. 创建新书时持久化 `creationBible`，不能只保存 `sourceType`。
3. `requestChapterContract()`、`requestChapterAudit()` 和 `refreshDissectionContext()` 改读 `creationBookId` 对应的圣经和状态快照；`refreshDissectionContext()` 去除首行 `dissectionId` 早退，改为读取新书 Bible / 状态。
4. 原书 `dissectionId` 只存入 `provenance.sourceDissectionId`，禁止作为新书正文检索入口。
5. 在 `creative-brief` 输出中保存证据、未知项、冲突项和禁止复制清单。
6. 将标题、简介、标记升级为完整章节合同和场景合同。
7. 审计通过后再同步 `knowledge`、`foreshadows`、`chapterCalls` 和状态快照。

**1.1 审计假通过修复的验收标准（Q1 门禁）：**

- 无 `dissectionId`（创意简报新书）时，`requestChapterAudit()` 禁止返回 `passed: true`；若存在 Bible / 状态快照，必须基于 Bible 运行真实审计；若 Bible 尚未建立，返回 `not_run + needs_review`，并在 UI 明示「该章尚未完成连续性审计」，由用户确认后才可提交。
- 新书同样必须生成本地确定性合同：无源时 `requestChapterContract()` 不得返回 `null` 静默跳过，应基于 `outline.synopsis + foreshadowLedger + knowledge` 生成最小合同（`goal`=章节规划、`mustAvoid`=Bible 禁止复制项、`foreshadowActions`=本书伏笔台账）。
- 评测指标 `false_pass_rate`（实际失败却标记 passed 的样本 / 失败样本）在 Q1 必须为 0，并纳入 `scripts/eval` 门禁。
- 回归测试断言：给出一条与本书 Bible 冲突的草稿（如引用了已死亡角色或已回收伏笔），审计必须返回 blocker 且 `passed=false`。

### 11.4 从当前单体迁移到商业架构

1. 先抽取 TypeScript domain contracts 和 repository 接口，不先按文件名拆微服务。
2. 新任务同时写本地兼容事件和生产 outbox，完成一小类任务的双读校验。
3. 将原文和大产物迁移到对象存储，数据库只保留哈希和引用。
4. 将 SQLite 数据导出为版本化快照，导入 PostgreSQL；按 `tenantId / projectId / runId` 回放并比对计数、哈希和状态。
5. 先把抽取和审计放到独立 Worker，再迁移聚合、索引和正文生成。
6. 通过 shadow run 验证新旧链路结果，达到覆盖率、事实准确率和费用差异门槛后切换流量。
7. 旧接口保留一个迁移周期，返回新 `workflowId`，禁止新旧任务互相写入同一状态版本。

### 11.5 现有账户、租户和状态迁移

商业化迁移不能只写“SQLite 导入 PostgreSQL”，必须定义归属：

| 当前数据 | 目标数据 | 迁移规则 |
| --- | --- | --- |
| `accounts` / 当前登录用户 | `tenants` + `memberships` | 每个已有账户创建一个默认个人租户，账户成为 owner；团队后续再增加成员 |
| 当前作品 / 小说状态 | `projects` + `creation_books` | 以现有 owner 的默认租户归属，保留原 ID 映射 |
| `dissections` / 拆书任务 | `dissection_runs` + `workflow_runs` | 写入 `tenantId`、`projectId`、原 pipeline 版本和迁移批次 |
| `sessions` | 身份提供商会话引用 | 不把 session 当业务数据迁移，过期后重新登录 |
| SQLite 原文和结果 | S3 原始对象 + PostgreSQL 元数据 | 先哈希校验，再导入；失败可重放，不覆盖原文件 |
| 用量 / 积分历史 | `usage_ledger` | 原记录只读导入；冲正使用新流水，不改旧账 |

现有状态到 4.0 状态的映射：

| 旧状态 | 新状态 | 处理原则 |
| --- | --- | --- |
| `queued` | `queued` | 保留任务输入和版本 |
| `running` | `running` 或 `needs_retry` | 若无有效租约 / 心跳则转 `needs_retry` |
| `failed` | `needs_retry` 或 `failed` | 按错误类型区分可重试和永久失败 |
| `interrupted` | `needs_retry` | 保留最后检查点 |
| `needs_review` | `needs_review` | 不自动升级为通过 |
| `completed` | `legacy_completed` | 只表示旧链路结束，重新通过新完整性门禁后才能 `approved` |
| `cancelled` | `cancelled` | 保留取消原因和操作者 |

所有旧记录增加 `legacyStatus`、`statusVersion`、`migrationBatchId`，禁止用一次 SQL 更新把旧 `completed` 批量伪装为新 `approved`。

本地模式与生产模式不做运行时双写。共享的是 domain contract 和存储适配器；迁移使用快照导出、导入、回放和 shadow comparison，避免一人维护两套实时写入链路。

## 12. 分阶段落地计划

### P0：领域契约和质量正确性

目标：先消除“看起来成功但实际不可用”的问题，并为后续迁移建立稳定边界。

- 统一 `unitId`、章节 / 段落 / 场景单元模型和 JSON Schema。
- 修复无标题文本和跨分片输入的全量覆盖检查。
- 批次结果必须验证每个输入单元，不再以“返回数组”作为完成条件。
- 移除硬编码 `validation.passed` 和异常默认通过逻辑。
- 引入 `creationBook`、`creationBible`、版本表和状态快照。
- 修复新书合同、审计和动态上下文对原书 `dissectionId` 的错误依赖。
- 把现有单体中的领域逻辑抽取到 `packages/domain`，为 SQLite / PostgreSQL 双适配做准备。

验收：中断和重试不丢单元；新书脱离原书查询仍可生成合同、审计并读取状态；所有失败结果显示为待重试或待复核；契约测试覆盖 API、事件和模型输出。

### P1：商业数据底座

目标：让生产环境具备多租户、可恢复和大文件能力。

- 接入托管 PostgreSQL，建立迁移、分区、RLS、备份和只读副本策略。
- 接入 S3 兼容对象存储，完成大文件直传、断点上传、哈希去重和生命周期。
- 建立 `tenants`、`projects`、`memberships`、`workflow_runs`、`usage_ledger` 和 outbox 表。
- 将原文、正文和大型中间产物从数据库行迁移为对象引用。
- 实现租户配额、角色权限、项目访问控制和用量不可变账本。
- SQLite 只保留本地模式和迁移工具，不让生产多实例共享 SQLite 文件。

验收：租户之间查询和下载互不可见；1000 万字符文件可断点上传和恢复；数据库故障演练可从备份恢复；重复请求不重复创建任务或扣费。

### P2：持久工作流和事件驱动处理

目标：让拆书和创书从单进程任务变成可横向扩展的生产流水线。

- 部署 Temporal，建立 `DissectionWorkflow`、`CreationWorkflow`、`ChapterWorkflow` 和人工审核 Signal。
- 部署 Kafka / Redpanda，定义版本化事件和事务 outbox。
- 建立 ingest、extract、resolve、aggregate、index、plan、generate、audit、export Worker 池。
- 每个 Activity 实现超时、心跳、幂等键、有限重试、死信和人工恢复。
- 接入模型网关，统一供应商、模型路由、预算、缓存、fallback、token 和费用。
- 使用 KEDA 按队列积压、任务年龄和资源指标扩缩 Worker。

验收：杀掉任意 Worker 后工作流可自动恢复；模型供应商短时不可用不丢失中间结果；单元任务可独立重试；至少一次消息投递不会造成重复事实和重复计费。

### P3：检索、图谱和容量扩展

目标：支持单书 1 亿字符、工作区 10 亿字符级 corpus，并保持可查询和可重建。

- 部署 OpenSearch，完成中文分词、关键词、向量和元数据过滤。
- 以 PostgreSQL 事实表为源，异步建立实体、事件、伏笔和证据索引。
- 对多跳关系查询建立 Neo4j 投影，记录投影版本和重建任务。
- 建立 embedding 版本、分块版本和索引版本，模型变更可增量重建。
- 使用分区表、冷热对象存储、分页 API 和分层摘要，禁止超大 JSON 一次性加载。
- 对大租户提供专用队列、索引分区和 Worker 池，避免 noisy neighbor。

验收：10 亿字符工作区可以按章节、实体、时间、关系和证据分页查询；删除并重建派生索引后结果可核对；压测达到目标并且队列积压可观测、可告警。

### P4：高质量原创创书平台

目标：把“拆书后生成新书”变成可审阅、可返工、可持续写作的商业能力。

- 生成 portable creative brief、原创偏离矩阵和禁止复制清单。
- 生成版本化 `creationBible`、分卷计划、故事弧计划、章节合同和场景合同。
- 使用场景级生成、章节级状态提交和跨章节状态快照。
- 增加连续性、人物、伏笔、文风、原创性和合同履约审计。
- 失败时生成定向返工任务，支持用户批准、驳回、局部重写和版本回滚。
- 将用户接受 / 拒绝 / 修改反馈写入本书的 `revisionMemory`，不跨租户混用。

验收：章节合同通过率达到目标；严重连续性错误为零；连续生成章节能够复用并更新状态；新书不直接引用原书专属实体和事件；人工审阅过程可恢复和可追溯。

### P5：商业运营和平台化

目标：让系统可以被真实用户购买、持续使用和稳定支持。

- 接入 OIDC 身份、团队成员、角色权限和审计日志。
- 建立套餐、额度、按量计费、优惠、退款和账单导出能力；支付渠道通过适配器接入。
- 建立租户级限流、并发上限、模型预算、存储配额和任务优先级。
- 接入 OpenTelemetry、指标、日志、链路、成本看板和用户可见错误追踪。
- 建立发布、数据库迁移、灰度、回滚、灾备和跨区域恢复流程。
- 提供公开 API、SDK、Webhook、任务状态订阅和私有化部署配置。

验收：可创建真实套餐和额度；超额任务有明确状态和账单；模型、队列、数据库、搜索和对象存储故障有告警和处理手册；SLO 和 RPO / RTO 通过连续演练。

### 12.1 实际执行顺序：质量轨道优先

P0-P5 是能力地图，不是必须串行完成的两年基础设施项目。小团队和首批商业用户应按以下顺序推进：

| 顺序 | 立即交付 | 价值 | 完成门槛 |
| --- | --- | --- | --- |
| Q0 | 当前实现对齐矩阵、旧状态映射、失败默认通过修复方案 | 防止重复开发和假成功 | 所有现有能力标记为已实现 / 部分 / 未实现 |
| Q1 | `creationBible` 持久化、Bible 版本、状态快照、CAS 提交 | 直接提升连续创作质量 | 两个并发任务不能覆盖彼此状态 |
| Q2 | 评测 fixtures、`scripts/eval` runner、成本账本、预算暂停 | 让质量和商业成本可测 | 版本晋级由 runner 门禁 |
| Q3 | 场景生成协议、确定性合同验证、原创偏离审计、prompt 注入隔离 | 直接降低生成错误和复刻风险 | blocking 漏检率达到门槛 |
| C0 | PostgreSQL、S3、模型网关、持久 Worker、租户 / 配额 / 账本 | 具备第一版商业生产能力 | 数据迁移、备份、RLS、成本和故障演练通过 |
| S0 | Temporal / Kafka / OpenSearch / K8s / Neo4j 按需引入 | 解决已证实的吞吐或检索瓶颈 | 每个组件都有 PoC、成本和恢复证据 |

Q0-Q3 可以在当前代码基础上完成，不应被 S0 的基础设施建设阻塞。C0 是首批付费用户前的最小生产底座；S0 只有在观测到明确瓶颈后才执行。

## 13. 测试和评测方案

### 13.1 必须覆盖的回归场景

1. 无章节标题的长文本不会被计为零章节。
2. 章节跨分片时，顺序、字符偏移和父子关系正确。
3. 批次漏返回一个单元时，任务不会标记为完整成功。
4. 模型返回空数组、错误 JSON 或无效引用时，任务进入待重试或待复核。
5. 同一幂等键重跑不会重复生成事实或重复计费。
6. 聚合失败不会写入成功摘要和通过状态。
7. 新书创建后删除或断开原书运行时上下文，仍可使用自己的 `creationBible` 生成章节合同。
8. 原书实体不会自动进入新书正文上下文。
9. 未通过审计的章节不能更新正式人物、伏笔和时间线状态。
10. 用户修订圣经后，后续章节使用新版本，历史章节仍能复现旧版本。

### 13.2 黄金测试集

建立小型但有人工标准答案的中文样本，至少包含：

- 多章节人物别名和同名人物；
- 跨章节关系变化；
- 非线性时间线和回忆段落；
- 多次误导后回收的伏笔；
- 章节标题缺失和极长章节；
- 需要多跳检索才能回答的问题；
- 合同履约和连续性返工样本；
- 原创迁移中“换名复刻”和“真正功能偏离”样本。

评测不只测字符串定位，还要测单文档定位、多跳人物追踪、伏笔回收判断、时间线排序、全书结构聚合、章节续写和连续性修订。可以参考 LongBench、RULER 和 BOOKSUM 的任务思想，但指标必须以本项目的中文小说样本为准。

### 13.2.1 黄金集的实际落地格式

黄金集由三类样本组成：

1. **授权真实样本：** 3-5 本有使用权的作品，每本标注前 20-30 章和关键后续回收章节。
2. **合成边界样本：** 同名人物、非线性时间、跨章节伏笔、错误 JSON、漏单元和恶意指令文本。
3. **项目回放样本：** 当前 1647 章运行中抽取的已脱敏单元、失败批次和人工修订案例。

真实样本不能直接从未经授权的网络小说进入评测仓库。每条标注保存来源许可、版本和脱敏状态。

建议目录：

```text
scripts/eval/
  fixtures/
    units.jsonl
    claims.jsonl
    continuity.jsonl
    foreshadow.jsonl
    originality.jsonl
  schemas/
    fixture.schema.json
  runner.mjs
  metrics.mjs
  reporters.mjs
  baselines.json
```

单条样本至少包含：

```json
{
  "sampleId": "book01-ch012-q003",
  "task": "entity_state | evidence | foreshadow | continuity | originality",
  "inputRefs": ["unit-0012", "unit-0013"],
  "expected": {
    "answer": {},
    "evidenceRefs": ["unit-0012:120-188"],
    "severity": "blocking"
  },
  "annotation": {
    "annotatorId": "reviewer-01",
    "status": "verified",
    "notes": "..."
  }
}
```

`runner.mjs` 的最小流程：读取 fixture -> 调用指定 pipeline / prompt / model 版本 -> 校验 schema -> 计算指标 -> 输出 JSON 报告和失败样本 -> 与 `baselines.json` 比较 -> 指标低于门槛则返回非零退出码。评测结果必须记录 commit、模型、promptVersion、schemaVersion、运行时间和费用。

首版指标至少包含：

```text
unit_coverage = 完成且有结果的 unit / 计划 unit
claim_precision = 正确重要 claim / 输出重要 claim
claim_recall = 找到的正确重要 claim / 标注重要 claim
evidence_traceability = 有效证据引用重要 claim / 输出重要 claim
entity_state_f1 = 人物状态字段的 micro F1
foreshadow_f1 = 埋设 / 强化 / 回收 / 未回收状态 F1
contract_pass_rate = 满足确定性 + 语义门槛的章节 / 评测章节
originality_block_rate = 正确拦截高风险复刻 / 高风险复刻样本
false_pass_rate = 实际失败但被标记 passed 的样本 / 失败样本
```

任何 `false_pass_rate` 上升、重要结论证据可追溯率下降或 blocking 问题漏检，都阻止模型 / prompt / schema 版本晋级。

### 13.3 运行前检查

每次提示词、模型或 schema 版本变更都执行：

```text
单元覆盖率 -> 证据可追溯率 -> 关键事实准确率
-> 结构摘要一致性 -> 合同通过率
-> 审计严重错误率 -> 原创偏离通过率
```

任何关键指标下降都要阻止版本晋级，并保留旧版本运行结果用于对比。

### 13.4 商业容量和 SLO 测试

压力测试必须使用固定版本的模型、提示词、embedding、分片规则和数据集，分别测试：

| 测试项 | 验收重点 |
| --- | --- |
| API 并发 | 500 RPS 非 AI 读写请求下的 P95、错误率和数据库连接池 |
| 任务提交 | 100 个并发重任务能进入队列，不因模型耗时阻塞 API |
| 单书拆解 | 1000 万字符从上传到全量事实完成的吞吐、成本和恢复时间 |
| 大书拆解 | 1 亿字符 fan-out / fan-in、分区、索引和聚合积压 |
| 工作区 corpus | 10 亿字符范围过滤、多跳查询、摘要和分页延迟 |
| 模型限流 | 供应商 429、超时、5xx、空输出和错误 JSON 的恢复行为 |
| 租户公平 | 大租户高并发不应让普通租户任务无限等待 |
| 索引重建 | OpenSearch / Neo4j 删除后可从 PostgreSQL 和对象存储重建 |
| 成本上限 | 任务、租户和套餐预算不会被重试或重复消息突破 |

建议生产 SLO：非 AI API 可用性不低于 99.9%，任务状态持久化成功率不低于 99.99%，普通任务进度延迟不超过 5 秒；实际数值以压测和供应商 SLA 校准。

### 13.5 故障、灾备和安全回归

商业版本必须把以下内容纳入自动化或定期演练：

- 随机终止 API、Temporal Worker、Kafka Consumer、索引 Worker，验证工作流恢复；
- 模拟 PostgreSQL 只读、主从切换、对象存储短时不可用和 Redis 清空；
- 模拟模型供应商限流、返回恶意超大 JSON、schema 漂移和服务降级；
- 验证租户 RLS、签名 URL 过期、越权项目访问和删除请求的最终清理；
- 备份恢复后校验原文哈希、事实数量、Bible 版本、章节状态和用量账本；
- 对外 API、事件 schema、模型网关和数据库迁移执行兼容性测试。

### 13.6 观测值、目标值和采用门槛分离

所有规模数字采用三列记录：

| 类型 | 含义 | 示例 |
| --- | --- | --- |
| `observed` | 已在固定代码、数据和硬件上真实测得 | 1647 章、436 批、34480 claims、约 7 小时 |
| `target` | 产品希望达到的工程目标 | 1000 万字符单书、任务提交 P95 <= 500 ms |
| `gate` | 允许采用某技术或发布版本的最低证据 | 3 次重复压测均通过、失败恢复 100%、成本误差 <= 10% |

当前运行数据只能作为 `observed baseline`，还需要补齐字符数、单元数、token、请求、重试、缓存、失败和费用后才可用于 unit economics。1 亿字符和 10 亿字符目标必须配套固定硬件、并发、模型版本、数据集、吞吐、延迟、费用和恢复时间报告。

### 13.7 测试分层升级：从源码匹配到真实行为

现有 `test/` 中大量用例（如 `test/dissection-graph.test.js`）通过 `assert.match(serverSource, ...)` 匹配源码字符串来证明"实现存在"。这类测试能防误删，但**不能证明数据真的落库、状态真的正确、审计真的阻断、失败真的可恢复、证据偏移真的准确**。按 Q0-Q3 顺序必须新增以下真实行为测试：

| 层级 | 测试方式 | 必须断言的行为示例 |
| --- | --- | --- |
| SQLite 集成测试 | 真实 `node:sqlite` + 临时库（需 Node 22.5+ 环境，云端或 CI 专用 job） | 构造一批 claims/实体/事件后调用落库函数，断言行数、状态、`source_start/end` 偏移在单元范围内 |
| 状态与审计测试 | 构造与 Bible 冲突的草稿调用审计器 | 断言 `passed=false` + blocker；断言 `not_run` 不会变成 `passed` |
| 任务回放测试 | 用真实 fixture 重放 `extractBatchFacts` / 断点续跑 | 断言失败批次重跑后不重复写 claims、不重复扣费、覆盖率单调不减 |
| HTTP API 测试 | 启动 `server` + 真实登录 token | 断言 `/creation-context`、`/chapter-contract`、`/audit`、`/coverage`、`/summaries` 返回真实数据与状态，而非空壳 |
| 并发提交测试 | 双任务同时对同一 `state_version` CAS 提交 | 断言只有一个成功，另一个进入 `needs_rebase` |

这些测试在本地 Node 20 无法运行 `node:sqlite` 的部分，必须在部署流水线（Node 22.5+）或云端验证脚本中执行；本地保留纯函数测试作为快速层。

## 14. 风险与取舍

### 14.1 质量风险

- 模型自评偏乐观：用规则门禁、证据引用和独立审计模型降低风险。
- 全书摘要丢失局部细节：保留分层摘要和原始证据，查询时回到单元层。
- 原创迁移过度依赖原书：用禁止复制清单和偏离矩阵阻断。
- 长链路状态污染：未通过审计不提交快照，修订只基于明确状态版本。

### 14.2 工程风险

- PostgreSQL 分区和写入竞争：短事务、索引审查、连接池、分区归档和只读副本必须纳入容量设计。
- 消息重复和乱序：Kafka 至少一次投递，依靠幂等键、版本号和状态机拒绝旧事件。
- 工作流历史膨胀：大 payload 放对象存储，Temporal history 只保存引用和摘要。
- 模型输出不稳定：schema 校验、重试、幂等键、模型 fallback 和中间产物缓存必须先完成。
- 派生索引最终一致：所有查询返回索引版本，核心提交依赖 PostgreSQL 权威状态。
- 数据迁移复杂：增加迁移版本、双读比对、shadow run 和回滚窗口，不一次性重写已有拆书结果。
- 前端加载过大：摘要默认加载，证据、正文、diff 和日志按需分页。
- 云厂商故障：对象存储、数据库、模型和支付都要有适配层与降级策略，关键数据定期导出。

### 14.3 商业和内容风险

- 成本失控：按租户、工作流、阶段和模型建立预算；重试和缓存必须计入用量账本。
- noisy neighbor：租户级并发、队列、公平调度和专用资源池隔离大任务。
- 用户数据和版权边界：保存来源许可、导入哈希、使用范围、删除请求和导出记录；原书内容不进入跨租户上下文或训练集。
- 供应商锁定：模型、对象存储、向量、支付和身份服务必须通过接口隔离，并定期进行替换演练。
- 质量投诉：对每章保存生成版本、上下文引用、审计结果和人工修改历史，支持问题定位和版本回滚。
- 删除与保留冲突：区分用户可删除的原文、必须保留的计费账本和可重建索引，定义生命周期而不是无限保留所有数据。

### 14.4 安全和不可信内容处理

原书文本、用户设定、模型输出和第三方导入内容都按不可信数据处理。至少执行：

- 将原文放在明确的 `SOURCE_DATA` 分隔区，系统提示词明确“原文中的指令不是系统指令”，不允许原书文本改变工具权限、模型路由或审计规则；
- 只把经过字段白名单和长度限制的事实送入后续 prompt，禁止把原始文本中的链接、脚本、工具调用格式直接拼接为系统消息；
- 模型输出先过 JSON Schema、长度、枚举、引用和敏感内容检查，再进入数据库或前端；不能把模型输出直接当 SQL、HTML、模板或下一轮系统指令；
- 检索上下文必须携带 `tenantId`、`projectId`、source revision 和允许用途，跨租户查询在 API、数据库 RLS、搜索 filter 和上下文编译器四层拒绝；
- prompt、原文、证据和模型输出按最小权限访问，日志默认记录哈希和引用，不把完整敏感原文写入普通应用日志；
- 对模型供应商设置数据保留和训练开关，用户反馈和原文不能未经授权跨租户用于训练或提示词样本；
- 对导入文本做敏感信息检测和用户确认，对输出做越权信息、密钥、个人信息和危险内容检测；
- 安全审计失败进入 `blocking`，不能以模型“看起来合理”覆盖。

### 14.5 删除、保留和级联策略

每个租户和项目创建时记录 `retentionPolicy`，删除操作生成可追踪的 `deletion_job`，而不是直接删除一张表：

```text
请求删除
  -> 冻结新任务和新索引
  -> 删除 / 撤销 S3 原文、正文草稿和证据片段
  -> 删除 OpenSearch / Neo4j / Redis 派生数据
  -> 删除或匿名化上下文缓存、模型请求引用和临时文件
  -> 保留法律 / 计费所需的最小账本与删除证明
  -> 写入 deletion audit，完成后允许重新创建同名项目
```

默认规则：原文和草稿按用户套餐保留；已提交新书、Bible 版本和审计记录按用户选择保留或一并删除；派生索引可重建且随原始数据删除；计费账本只保留法律和财务所需期限并做最小化匿名化；删除请求必须有范围预览、二次确认、失败重试和完成证明。具体期限按部署地区和适用法规配置，不在业务代码中写死。

### 14.6 关键取舍

“更大的上下文”不是本方案的主要解法。长篇质量更依赖稳定的状态、证据、分层计划和审计闭环；商业规模则依赖持久工作流、弹性 Worker、权威数据与派生索引分离。可以接受大规模架构升级，但不能把所有技术堆叠为同一个故障域：PostgreSQL、对象存储、Temporal、Kafka、OpenSearch 和图谱各自承担清晰职责，并且每个派生层都能重建。

## 15. 最终完成标准

以下条件全部满足，才算达到商业化生产门槛；在此之前只能称为试验版或内部版：

1. 1000 万中文字符单书生成完整、可校验的单元清单；1 亿字符单书可通过分片任务和分层聚合处理。
2. 10 亿字符级工作区 corpus 可按租户、项目、章节、实体、关系、时间和证据分页查询。
3. 文件通过对象存储分片上传，原文、正文和大型产物不依赖 API 单请求或数据库单行承载。
4. 任务中断、Worker 被杀、模型限流、索引失败和消息重复后能自动或人工恢复，已完成单元不重复处理。
5. 重要事实、人物关系、时间线和伏笔都能定位到证据、版本、租户和来源对象。
6. PostgreSQL 是权威事实源；OpenSearch、Neo4j、缓存和报表删除后可以重建并核对。
7. 失败、部分完成、冲突和未执行审计不会被标记为成功，严重问题为零才能提交章节。
8. 新书拥有独立版本化 `creationBible`，不依赖原书运行时数据也能继续创作。
9. 原书 ID 只用于 provenance，新书正文检索只使用自己的创作状态和允许迁移的规律。
10. 创书过程经过简报、偏离矩阵、圣经、分卷、故事弧、章节合同、场景合同、正文、审计和修订。
11. 生成下一章时能读取当前故事弧、人物状态、时间线、世界规则和未回收伏笔。
12. 多租户隔离、角色权限、配额、用量计量、账单、删除和导出流程可实际运行。
13. 非 AI API 可用性、任务状态持久化、成本上限、RPO / RTO 和容量目标通过自动化或定期演练。
14. 黄金测试集、契约测试、负载测试、故障测试和模型版本评估均达到预设指标并可回溯。
15. `scripts/eval` 能在固定 fixture 上计算覆盖率、证据追溯率、实体 / 伏笔 F1、合同通过率、原创高风险拦截率和 false-pass rate。
16. 每个模型请求和每个工作流都有 token、重试、缓存、索引、存储和费用账本；预算达到门槛会暂停任务。
17. 当前 `observed baseline`、产品 `target` 和技术采用 `gate` 分开记录，任何 1 亿 / 10 亿字符能力都有可复现压测报告。
18. Bible、章节草稿和状态提交具备版本、乐观锁、分支 / rebase 和回滚语义，autosave 不会污染正式状态。
19. 原书文本按不可信输入处理，跨租户上下文、prompt 注入、模型输出和敏感信息测试通过。
20. 删除、保留、导出、计费账本和派生索引级联策略可执行，并能生成删除完成证明。
