# 小说全套资料能力审查与优化方案

核查日期：2026-09-15。

本轮范围：当前 `molan-home` 源码只读审查、隔离测试、联网一手资料交叉核验。仅新增本报告；未修改业务代码，未部署、重启服务或调用付费小说生成。本文所有“建议/目标/验收”均不是已经实现的功能。

## 一、结论与证据边界

**当前不能完整、可靠地实现用户列出的小说创作全套资料，更不能承诺文学质量“完美”。**

已有可复用基础：创书参数、创作圣经、人物与世界设定生成、总卷章规划、正文编辑、通用知识库、简化伏笔、版本及审计/提交机制。主要问题不是缺一个更长提示词，而是：

1. 资料字段、编辑界面和正文生成之间的覆盖不一致。
2. 同一人物/世界/伏笔同时存在于多个副本，缺少明确的唯一权威版本。
3. 转换过程会丢字段、重置状态、丢稳定标识，关联不能可靠延续。
4. 故事时间、人物知识、事实和计划没有完整分层。
5. 审计与正式提交尚未完整绑定圣经版本、上下文和状态增量。
6. 缺少六类资料的完整维护、整包导出、恢复和端到端验收。

本报告把用户清单按可验收叶子组归为49项；这是需求编号，不是完成率统计。没有用“有数组”“有按钮”“模型能回答”替代完整支持。

### 实际验证

- 在独立临时 data/config 下执行8个指定测试文件：**124通过、0失败、0跳过**。
- 文件：`creation-main-flow`、`creation-plan-review`、`creation-flow`、`creation-retry`、`benchmark-editor`、`benchmark-pipeline`、`two-stage-creation`、`genre-cascading-selection`。
- 测试范围为库函数、VM、静态断言及模拟依赖；未运行浏览器端到端、真实HTTP服务或付费长篇生成。
- 另直接调用当前 `normalizeBiblePayload`，确认：
  - 主 `characters` 投影不保留输入的年龄等字段；并行 `characterLibrary` 却保留该年龄，属于副本不一致，不是断言所有原始信息都消失。
  - 输入伏笔ID没有进入输出 `foreshadowLedger`；输入 `paid` 被改为 `planned`。
  - 输入时间线被初始化为空。
  - 输入四条故事线只保留三条。
- 2026-09-10的668通过、P0/P4各一次真实生成失败，仅为历史结果，不是当前版本重新验收。历史整章精读、全量生成及真人盲评缺口继续保留。

## 四、联网交叉验证：哪些方向有依据

以下是来源结论，不是本项目已经达到的效果。来源目录见第十三节。

| 来源 | 可借鉴的结论 | 不能据此宣称 |
| --- | --- | --- |
| S1 Re3，EMNLP 2022 | 结构计划、持续提供故事状态、候选择优和事实修订可以组合使用 | 该论文的故事长度/模型结果等于百万字中文连载保障 |
| S2 DOC，ACL 2023 | 细化的分层大纲与生成控制相配合，而不是只保存一份大纲文本 | 增加字段或写长提示词就自动具有大纲控制能力 |
| S3 Lost in the Middle，TACL 2024 | 在其问答/检索实验中，信息位置影响长上下文利用 | 所有当前模型必然以同一比例遗忘，或单靠RAG可完全解决 |
| S4 Lost in Stories / ConStory-Bench，Findings ACL 2026 | 将长故事一致性单独评估，使用明确文本证据；论文实验指出事实与时间错误值得重点检查 | 流畅度、风格评分或一次模型审稿等于无矛盾认证 |

本项目的设计推论：采用“结构化资料＋显式关联＋版本事实＋按场景组织输入＋证据复核”，比继续扩大统一提示词更对症。此推论仍需在本项目中文题材和实际模型上验证。

## 五、目标架构：一个权威项目，多种视图

### 5.1 必须先区分五类内容

1. **设想**：灵感、备选人物、结局方案，不代表世界已经如此。
2. **计划**：预计在哪章发生，允许作者改动。
3. **已批准设定**：本版本世界/人物约束；可有作用范围、例外和有效时期。
4. **正文已确立事实**：来自具体文稿版本和文本证据。
5. **角色认知与读者可见信息**：某角色知道/误以为/听说的内容，不自动成为客观事实。

例如“乙说王城已毁”至少先记录“乙说了这句话”，不能未经判断直接把“王城已毁”写成世界事实。

### 5.2 不推倒重写，也不先引入图数据库

建议继续使用现有Node与SQLite，新增领域模块，由现有路由逐步转发。第一阶段采用结构化JSON承载各类型正文，关系和高频索引显式表化。是否需要全文/向量索引由实际检索和规模测试决定，不把新数据库当必要前提。

建议逻辑对象：

| 对象 | 职责 |
| --- | --- |
| Project / ProjectProfile | 作品身份、基础定位、题材能力配置、当前版本 |
| Entity | Person、Place、Faction、Rule、Ability、Item、Term等有稳定ID的资料 |
| Relation | 人物/势力/物品之间的有向关联，含有效期和来源 |
| PlotNode | 全书、卷、章、场景以及关键事件节点 |
| StoryEvent | 故事时间、参与者、发生地、前后状态和因果依赖 |
| Foreshadow | 计划/实际埋设、回收、延期、放弃和证据 |
| CanonFact / KnowledgeState | 客观事实与各角色认知分别记录 |
| ManuscriptRevision | 不可变文稿版本、正文哈希、所属场景、作者 |
| Issue / WritingTask | 矛盾工单、卡点、进度、修订与复核 |
| ChangeSet / Reference | 一次修改的影响范围及资料到正文的引用 |
| ExportManifest | 导出版本、清单、文件哈希和缺失提示 |

不要求一次建完所有新表。先让旧 `novels` 与 `creation_books` 明确映射同一projectId，建立唯一写入服务；再迁移人物、关系、伏笔和正文版本。

### 5.3 通用字段与约束

通用字段建议：`id`、`projectId`、`schemaVersion`、`revision`、`status`、`createdAt`、`updatedAt`、`sourceRefs`；有时效的事实另有 `validFrom/validTo`。扩展字段放入命名空间明确的 `extensions`。

- 名称可改，ID不能因改名而变。关系使用ID，不以姓名字符串充当主键。
- 同名、同姓合法；冲突检测检查指向是否歧义，不全局禁止共享汉字。
- 核心资料使用项目内引用约束，拒绝跨书串联和悬挂引用。
- 草稿不强制填满49项；“可进入本章起草”的必需项按题材和任务判定。
- 正常API不静默吞未知字段；迁移时未知旧字段保留在原始快照/扩展区并报告，不能直接丢弃。
- 超容量应分页、明确报错或让作者选择归档，不能通过 `slice` 无提示删除事实。
- 数据来源、版本和审核状态是独立维度；`generated`不等于`approved`。

## 六、六类界面的具体建设

统一入口建议为“作品资料中心”，按用户原清单分为六区，正文编辑器通过右侧资料面板引用同一数据，不再建立另一份可独立修改的拷贝。

1. **基础定位页**：独立短/长/营销文案，复合题材、主题、基调、读者与目标规模。所有改动可回看，影响文案和规划时显示提示。
2. **世界观页**：基础文档、规则表、地点树/地图、势力关系、能力体系、社会文化、历史事件、术语跳转。图形只是视图；底层关系不依赖图形坐标。
3. **人物页**：主角/配角/反派/路人使用同一实体类型、不同表单层级。整合现有角色库与圣经演绎字段；可手工新建、编辑、合并、归档及查看影响。
4. **大纲页**：保留总→卷→章，在章下增加执行性场景卡。每个场景关联人物、POV、地点、故事时间、目标、阻力、变化、伏笔动作；允许章内多视角。
5. **素材页**：道具、技能、环境素材、伏笔、台词、术语分型。地点客观属性与环境措辞素材分开；台词/名场面标记未使用、拟用、已用及来源。
6. **管理页**：进度看板、故事时间线、矛盾工单、文稿版本、番外后记与导出中心。明确“有正文”“已定稿”“已发布”不是同一状态。

所有区统一提供：创建、编辑、引用、关联查看、筛选、修订记录、归档/删除影响预览、撤销与恢复。批量操作必须展示变化和影响，不静默级联删除作者正文。

## 七、生成、审计和正式提交统一

建议流程：

```text
作品定位 → 必需设定确认 → 总纲 → 卷纲 → 近期章纲 → 场景卡
                                                    ↓
             按本章时间/人物/POV选择权威资料 → 冻结上下文
                                                    ↓
             起草候选 → 证据审稿 → 有限局修或作者修订
                                                    ↓
             对比与作者选择 → 保存草稿 / 申请正式采纳
                                                    ↓
             版本校验 → 同事务提交正文版本、事实增量与状态
```

### 7.1 统一的是提交契约，不是强制唯一写作风格

现有两阶段写作、benchmark、直接聊天、手工正文可以是不同起草入口，但最终必须区分：

- 保存草稿：允许不完美、待核验、作者临时突破设定；不得伪装成审计通过。
- 正式采纳：记录依据、适用版本、作者确认、事实变更；语义争议允许作者作出明确决策。
- 作者推翻旧设定：建立设定修订和影响评估，而不是无痕覆盖。

当前“待复核稿直接采纳”不应简单删除：作者有权写自己的稿。但必须清楚标记草稿/作者确认/机器通过，不能把消息改成ready就视为正式状态也已一致。

### 7.2 提交必须绑定整个被审计对象

建议审计凭证至少含：

`projectId + chapterId + manuscriptHash + bibleRevision + planRevision + stateRevision + contextHash + deltaHash + auditPolicyVersion`

- 提交前上述版本不一致，应返回需重新基线化，而不是拿旧审计配新圣经。
- 正式状态从已审核/确认的增量推导，不直接相信客户端任意 `characterStates/relationshipStates`。
- 缺失状态字段不能当作“清空所有旧状态”。
- 同一事务写文稿版本、状态增量、审计关联和提交回执；债务等外部文件通过持久化待办恢复。
- 断线先查询原请求结果；不要以新requestId自动再次生成或重复扣费。
- 普通保存和圣经PUT都要求客户端基线版本；旧客户端兼容应显式处理，不保持无版本覆盖的隐式旁路。

### 7.3 规划和事实变动后的失效传播

改第3章某事实时，系统应列出依赖它的第7章、某人物卡、某伏笔，而不是自动全书重写。相关审计标 `stale`，作者决定修文、改设定、延迟处理或保留有解释的矛盾。

## 八、时间、知识和连续性

### 8.1 三条时间轴

- 故事发生时间：支持真实/自定义历法、区间、相对时间和未知精度。
- 叙述顺序：正文先写回忆还是当前，不要求按故事日期排列。
- 系统修改时间：作者何时改了资料，不能拿它计算角色年龄。

年龄由故事时间和出生时间推导，允许大约/不明；地点移动要结合已批准交通方式、距离、耗时和特殊能力。闪回、转生、时间旅行、灵体等必须按世界规则判断，不能被通用现实规则一律否决。

### 8.2 分层记忆与选择

建议输入分为：

1. 当前有效的世界硬约束、选中题材要求。
2. 当前场景相关角色状态、关系和认知。
3. 本章任务、近期事件、到期伏笔、必要长期因果。
4. 可回查的文稿证据；可选风格素材。

优先按结构化ID、故事时间和依赖关系筛选，再补全文检索；需要语义召回时才引入向量检索。每次记录选中/未选条目及原因，检查远期关键事实是否进入上下文。

摘要只是派生索引，不覆盖原事实。计划端掌握秘密不表示正文POV也可掌握；读者已知、角色已知、作者知道须分开。

### 8.3 审稿状态不应强迫模型填写“全部checked”

区分检查是否执行、发现结果、适用性与未来待兑现项：

- 本章已检查且没有问题；
- 本章发现有证据的问题；
- 本章不适用，有理由；
- 未到回收期，有计划依据；
- 资料不足/执行失败，明确缺口。

未到第8章的伏笔不应在第1章仅因没回收而变成整章审计失败；但“未到期”不能成为无限拖延借口，要与当前计划、实际事件和延期记录绑定。

一致性问题至少标双侧证据、版本、时间及引用对象。机器缺少证据应待复核，不伪造引用；自然心理句、同姓、开放结局、平静收尾不应作为普遍错误。

## 九、题材适配与作者控制

建议“公共核心＋可选题材能力包”，而非为每种题材复制整个资料系统：

- 玄幻/科幻：能力、资源、升级、成本及例外。
- 悬疑：线索、假设、证言可信度、证据取得时间和知情矩阵。
- 古言/历史：家族谱系、时代/地域制度、礼法及历史事实与架空改动标记。
- 都市：职业、机构、契约和生活时间；需要现实事实核实时记录来源。
- 甜宠/治愈：人物边界、关系变化和情绪承诺；不硬塞战力升级或反派BOSS。
- 混合题材：合并能力包后提示冲突，由作者选择优先级。

应优先撤下L03中跨题材强制“金手指亮相、前三章打脸、章末钩子必须高强度”等全局指令，改为作者可选的叙事策略。原有风格指标可作描述，不作为文学合格证。

## 十、整包导出与安全迁移

### 10.1 两类导出

**阅读/出版稿**：正文、番外、后记、简介；按选择导出TXT/Markdown等，后续再扩展其他格式。

**资料备份包**：包含可再导入的结构化数据与可阅读文档，建议结构：

```text
project-export/
  manifest.json
  profile/
  world/
  characters/
  outline/
  materials/
  management/
  manuscripts/
  data/
  attachments/
```

manifest记录schema版本、项目ID、导出版本、文件哈希、关联清单。默认排除API凭据、账户/会话、其他作品及未授权范本文本。导入先校验路径、防目录穿越、大小、schema、哈希、ID冲突与引用，不直接覆盖现有项目。

### 10.2 迁移顺序

1. 清点当前novel state、bible、creationAssets和工作区副本，只读生成冲突清单。
2. 做一致性数据库备份和恢复演练；不能仅因备份命令退出0就认为可恢复。
3. 建立旧ID/姓名/章节序号到新稳定ID的映射；同名歧义交作者确认。
4. 导入到隔离目标，保留原始payload和所有未映射字段；不修改旧原文。
5. 比较实体数、正文哈希、关系/伏笔引用、状态及时间线；重复迁移应得到相同映射。
6. 新结构先影子读取、对比结果；避免长期双写造成新旧互相覆盖。
7. 通过项目级开关切换权威写入服务，再停用旧工作区独立写入。
8. 保留回退方案；切换后产生的新编辑必须有变更日志，不允许回滚时丢掉新稿。

代码建议渐进拆分：资料schema、仓储、迁移、上下文选择、审计、提交与导出成为小模块；现有路由保留适配层。不在同一阶段重写整个 `server.js` 和全部前端。

## 十一、实施顺序与退出条件

使用M0–M5命名，避免与历史范文对标P0–P4混淆；不以未经估算的固定天数承诺代替验收。

| 阶段 | 先做什么 | 退出条件 |
| --- | --- | --- |
| M0 数据止损与基线 | 保留人物完整字段、伏笔ID/状态、时间线；清除静默截断；明确草稿/正式状态 | 已知转换缺口有回归；历史资料未丢；每条写入路径与边界已登记 |
| M1 权威资料和基础维护 | 项目ID映射、schema、版本、人物/世界/关系/术语/定位表单 | 核心资料完整增改查、版本冲突、归档恢复；编辑器与资料中心一致 |
| M2 规划与时序关联 | 总卷章场景、出场表、时间/年龄、伏笔计划及事实 | 改名、移章、删章、回忆、跨卷兑现等关联测试通过 |
| M3 生成与正式提交 | 统一上下文冻结/版本审计/增量提交；作者例外流程；缺证据分级 | 所有起草入口遵守同一正式提交契约，失败/断线/旧版本不污染状态 |
| M4 管理、导出与恢复 | 卡点、矛盾工单、番外后记、资料整包、迁移切换 | 导出→新项目导入→再导出无关键字段/引用/正文丢失；恢复演练通过 |
| M5 中文长篇验收 | 题材固定任务、长距离事实、跨卷伏笔、真人阅读 | 单独报告工程完整性、语义一致性和阅读质量；失败与未评审保持可见 |

建议第一批真正实施的范围是M0＋M1的最小闭环，而不是先增加几十种风格流水线。

## 十二、验收用例与质量标准

### 必须成为自动化用例的关键场景

1. 49项资料各自完成创建→编辑→保存→重开；适用模块可明确标不适用。
2. 完整人物卡过归一化、转编辑器、导出再导入，年龄/背景/能力/演绎字段不丢。
3. 人物改名不改变关系、技能归属、出场表及伏笔关联；同名不同人不被自动合并。
4. 合并实体时重指子实体parent、关系、场景、资料引用并提供撤销。
5. 移动/删除/恢复章节后，章纲、场景、伏笔、合同、出场表和原卷归属可校验。
6. 伏笔ID、实际状态和计划时点不重置；延期、部分兑现、作者放弃均有依据。
7. 角色先说谎后证实真相，不把初次发言直接写成客观事实。
8. 双时间线、回忆、生日跨越、长途移动、架空时间规则按适用条件校验。
9. 旧圣经审计不能直接提交到新圣经版本；同正文但篡改delta/state应拒绝。
10. 保存缺少状态字段不清空旧状态；不带基线版本的旧客户端不能无痕覆盖。
11. 提交成功后丢回包、刷新重进、重放原请求，不重复生成/收费/推进版本。
12. 保存待复核稿不会伪造审计通过；作者明确采纳保留决策与风险记录。
13. 模型超时、坏JSON、假引文、超预算、未知事实不触发静默通过。
14. 改旧章后仅标记受影响依赖和审计过期，不自动覆盖后文。
15. 正文导出范围正确；资料包完整、无凭据、无跨书数据，损坏包被拒绝。
16. 数据迁移可重复执行、可回滚、恢复后正文哈希一致。

### 三种不同的“通过”

- **工程通过**：预先定义的测试集中无数据丢失、越权、重复提交、悬挂引用；这是测试范围内的证据，不保证未来零bug。
- **一致性通过**：人工标注集报告准确率/召回率、误报漏报、定位证据、知识/时间/关系各维结果；不只报总分。阈值应在评测前由作者与项目方确定。
- **文学体验通过**：读者可读性、人物可信、因果兑现、节奏及题材适合度，使用盲评/作者意见。自动指标和模型自评不能代替。

逐级增加真实长篇长度，例如短链路→多章→跨卷；同时用无需付费生成的结构化模拟数据测试高实体数、超长时间线和迁移性能。没有足够样本时报告“尚无证据”，不填造胜率。

### 本轮尚未验证

浏览器端实际CRUD、运行中用户服务是否加载当前代码、真实HTTP/数据库跨入口闭环、完整迁移恢复、49项整包往返、全量中文长篇生成及真人阅读。本轮124项通过不能覆盖这些目标。
