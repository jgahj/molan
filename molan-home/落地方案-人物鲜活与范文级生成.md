> 已入运行记录；前三章双稿择优已触发（第二稿被选中）。
> 数据核查：全文 20 字前缀段落去重 **0 重复**，"整段复制粘贴"指控不成立；但
> "无火息/胸口隐痛"等**状态复述**与**告示式设定**真实存在，属重复注入类问题。

## P0-1 人物演绎层（核心：让人物"活"起来）

### 现状与根因
人物卡只有 goal/flaw/arc（设定事实），起草模型拿到的是事实清单而非演绎指令；
章纲 intensity(8) 没有翻译成"本章情绪轨迹"；配角按剧情功能出场、无关系张力。
实测佐证：沈砚舟的 flaw"过度谨慎"已自发演成"查验封蜡/要求记录在案"（行为有了），
但**全程零情绪**（感受没写）——证明缺的是"演绎层"，不是"人物设定"。

### 1.1 人物卡五字段扩展

数据结构（`normalizeBiblePayload` 的 characters 条目追加，向后兼容旧卡）：

```json
{
  "name": "沈砚舟", "role": "主角", "goal": "...", "flaw": "过度谨慎", "arc": "...",
  "voice": {
    "samples": ["……（标志性台词 2-3 句）"],
    "taboo": "绝不会说的词：大段自白、‘我要变强’式口号",
    "habit": "短句收尾；把要求说成记录请求"
  },
  "tell": { "紧张": "摩挲炉牌边缘", "愤怒": "敲桌面一下即停", "压抑": "咽话+停顿一息" },
  "wound": "父亲沈玄策失踪+遗物被扣押（一提即痛）",
  "stance": { "toward": "主角", "current": "提防中带一丝同情", "evolution": "竞争→并肩" },
  "emotionStyle": "克制型（情绪用动作与沉默表达，破口时也只有一句）"
}
```

- 生成侧：核心包/资源扩展的提示词输出格式追加这五个字段（`creationPlanExpansionPrompt`
  resources 分支 + `handleCreationBooksCreate` 的 normalizeBiblePayload）。
- 存量书迁移：圣经工作台（`handleCreationBookRegenerateAsset`）对无 voice 字段的人物卡
  显示"补全演绎层"按钮 → 单卡重生成时按五字段输出 → `saveCreationBibleVersion` 存新版本。
- 前端：圣经工作台人物卡展开显示 voice/tell/wound；编辑器内只读。

### 1.2 章级"人物演绎简报"注入起草

在 `completion-editor.js` 的 buildContext：对 `characters`（本章出场人物）按卡片生成
演绎简报，替代现在的事实型罗列：

```
【人物演绎简报（本章只读）】
沈砚舟（视角人物）｜情绪轨迹：压抑(3) → 刺痛(6) → 压着火的决意(8)
  声音：短句收尾；把要求说成记录请求。禁语：口号式自白。
  破口规则：本章至少一处情绪破口——克制型人物也要有"泄出来的一瞬"（动作/失语/过度反应）。
  tell：紧张摩挲炉牌边缘。
宁照微 ｜立场：扶持但有账目原则 ｜情绪：关切藏在交易话术里
```

- 情绪轨迹推导：`起点 = 上章末主角状态（事实账本 currentState）`，
  `终点强度 = 章纲 emotionIntensity`，中段按 arc 阶段插值；由客户端拼装，无需模型。
- 注入位置：起草 system prompt 的 `人物演绎简报` 区块（与 styleKit/globalLedger/factLedger 并列）。
- 硬规则（起草提示词追加）：
  1. 每个出场人物的对白必须符合其 voice.samples 的句式习惯，违反 voice.taboo 即为失败；
  2. 主角情绪必须到达轨迹终点强度，且至少一处按 tell 方式外露；
  3. 配角出场必须体现 stance.current（哪怕一个动作/一句台词）。

### 1.3 配角张力治理

`creationPlanExpansionPrompt` chapters 分支追加：
"每个非主角出场人物必须携带：与主角的关系张力（扶持/竞争/提防/亏欠之一）+
一个与当前剧情无关的性格细节（怪癖/习惯）；无法承载张力的人物合并或删除。"

### 1.4 反派动机可见性（冷读审维度）

连续性/冷读审计提示词追加：
"反派/对手的行为若针对性明显（设局/扣押/刁难），必须在正文中留下可推断的意图线索
（动作、一句台词、一个取舍），禁止纯工具化出场。"

涉及文件：`server.js`（normalizeBiblePayload / expansion prompt / 审计提示词）、
`completion-editor.js`（buildContext 演绎简报 + 起草提示词）、`completion-import.js`（工作台重生成提示词）。

验收标准：重生成的第 1 章中，主角出现 ≥1 处符合 tell 的情绪外露；顾沉砚/霍千峦
出场带可推断立场；盲测 5 段对白能区分说话人 ≥3 人。工作量：2-3 天。

## P0-2 文本质量硬控制（治冗余/超字数/名词堆砌）

### 2.1 字数硬控制
- 审计确定性检查（`handleCreationBookChapterAudit`）：`contentLength` 偏离合同目标
  ±30% → issue(category='pacing', severity='warning')，正文已返回 contentLength ✓。
- 修订指令：`!audit.passed` 或超字数时，修订提示词追加
  "压缩/扩写至 1800-2200 字（当前 X 字），只做删繁与补场景，不改事实"。
- 起草提示词追加："目标 1800-2200 字；写完自检字数，超出立即删减过渡句"。

### 2.2 重复注水检测（确定性，零模型成本）
- 服务端对正文做：①段落 20 字前缀去重（≥2 次即 redundancy blocker 级 warning）；
  ②状态短语计次：正文中"无火息/胸口隐痛/炉底亮纹"类关键状态短语（从合同与
  事实账本提取）出现 >3 次 → redundancy warning。
- 起草提示词加"首现详写、后续只写变化量"原则。

### 2.3 名词密度与设定融入
- 冷读审（experience）追加两个量化子项：
  ①新专名计数（与圣经/账本既有实体比对，新增 >8/章 → warning）；
  ②每个新专名必须伴随"体感/代价/用途"之一，否则点名。
- 起草禁令："设定禁止以告示/契约全文/口述说明整段呈现；必须通过主角的损失与遭遇呈现"。

### 2.4 人名差异化校验
- 核心包生成后对 characters 做字形重叠检测：任意两人名共享 ≥1 个汉字
  （如 沈砚舟/顾沉砚 共"砚"）→ 要求模型重命名其中之一（挂在
  `creationBibleSeedValidation` 旁，确定性零成本）。

### 2.5 标题保留
- `creationStateFromResult` 用 plan.title 覆盖模型自拟 title；模型自拟名存
  creationNotes.alternativeTitles 供参考。

涉及文件：`server.js`（审计/门禁/扩展提示词）、`completion-editor.js`（修订指令）、
`completion-import.js`（creationStateFromResult）。

验收标准：重生成本章字数 1800-2200；redundancy/experience 类 warning 呈现给作者；
无告示式整段；人名两两不共享汉字。工作量：1-2 天。

## P2-4 题材规则蒸馏（范文规律内化）

### 现状：框架未建。目标：从 1034 本按题材蒸馏写作规则，升级默认写作 Skill。

- 阶段 1（数据）：按题材抽 20 本 × 跑批量拆书 authorDna/rules（复用现有
  批量拆解管线），产出 `data/genre-rules/<题材>.json`。
- 阶段 2（聚合）：同 axis 规则聚类，evidenceCount ≥5（跨 5 本）且
  confidence ≥0.7 才入选 → 生成 `data/writing-skills/<题材>-skill.json`。
- 阶段 3（挂接）：`ensureDefaultWritingSkill`（server.js）按作品题材加载对应
  题材 Skill（现有 default writing skill 机制直接支持多 Skill 切换）。
- 成本：20 本/题材 × 拆书费用；先做玄幻+都市两个题材试点。
- 风险：规则冲突（两本书的规则矛盾）→ 聚合时按 status=confirmed 数量取优，
  冲突规则标记 conflicted 不注入。

工作量：4-5 天（含试点验证）。

## 风险与对策

1. 范文注入导致抄袭 → 三道闸（匿名化 + 审校 + 结构 LCS/Jaccard）+ 注入样本
   与生成正文的 bigram 重合检测（加入审计确定性检查）。
2. 提示词膨胀超窗 → 注入总量预算制（范文 ≤1000 token、演绎简报 ≤800 token、
   账本 ≤3600 token），超预算按优先级裁剪。
3. 模型不遵守节奏/字数 → 全部有确定性审计兜底（本地计算，不依赖模型自觉）。
4. 本地/云端行为差异 → 本地验证通过后一次性走 `deploy_molan.py`，
   数据文件入发布白名单。
